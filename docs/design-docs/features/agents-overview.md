# Agents v2 — CLI substrate, hooks telemetry, isolated homes, registry

The shape of the agent layer: what an agent SAYS goes through the `tmm` CLI, what we OBSERVE arrives through hooks, and every managed agent lives in an isolated home materialized from the registry. The CLI itself is documented in `tmm-cli.md`; the runtime status model in `agent-status.md`; the lifecycle in `agent-lifecycle.md`.

## Rules and their reasons

### Configuration drafts have one owner (2026-09-10, #156)

AgentsPage owns the Agent/Team/Skill/MCP/global-instruction working copy, the
save operation and the exit guard. `config-draft.ts` defines the payload and
fingerprint once; expanding a team member does not make it dirty, and nested
MCP data is not mistaken for UI state. Save freezes payload and editor identity,
rejects duplicates and retains failed edits. The Settings embedding host uses
the registered exit callback, not an independent dirty flag. Keyboard submission
uses the same Save and skips IME events. Global reads are generation-scoped even
when reopening the same document. These rules replace the independent unguarded
close/save handlers found by #154. Exact geometry, shared controls and the
pending/return contract live in [design-language.md](design-language.md).

### Deletion confirmation owns its failure (2026-09-12, #167 batch 1)

Deletion errors were already visible in the baseline: AgentsPage appended the
shared editor error to the confirmation's consequence note. This change gives
deletion its own error state and a separate modal `role="alert"`; it is not a
fix for hidden error text or for the already-correct busy Back behavior.

Agent, Team, Skill and MCP deletion keep their captured kind/name and editor
generation until the mutation settles. Pending is set before awaiting; duplicate
activation, Escape, backdrop and the existing registered Back callback cannot
dismiss it. A rejected deletion remains retryable with an `error` alert inside
ConfirmDialog, separate from its consequence note and the editor's save error.
The caller explicitly supplies `trash`; neutral Discard supplies `check` and
keeps the existing `configKeepEditing` translation.

Deletion success ends `removing` and closes only its own confirmation/editor
before refreshing the catalog. Refresh is not a pending deletion: a newer editor
can open while it runs, and its completion must not reset a newer deletion's
busy state. `AgentsPage.mount.test.ts` asserts the separate modal alert and
reproduces the refresh blocking a newer editor. A committed host section change clears
the old view's pending state; its late failure/finally cannot affect a new
confirmation. The tests also preserve the pre-existing busy
Back, failed-target retry, save and draft-exit behaviors. Source contracts pin
the explicit glyphs rather than inferring them from danger tone. These are
real Svelte client mounts with controlled RPC promises, not native Back or
layout/paint acceptance; no feedback timers change in this batch.
Verified with Node 22.23.2, Svelte 5.55.5, Vite 6.4.2 and jsdom 30.0.1.
Disconnecting the caller's `error` prop made the deletion-alert test fail;
restoring it passed. No shared file was changed for that negative control.

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Agents v2 — CLI substrate, hooks telemetry, isolated homes

the project hub (`hub_*` RPCs, `src-tauri/src/server/hub_rpc.rs`, room `proj:<session>` in state.db's `hub_msgs` — `projects/rooms.rs`, board #107) is the agent collaboration layer. What an agent sends proactively goes through the `tmm` CLI (`src-tauri/src/bin/tmm.rs`: send/log/spawn — fail-soft exit 2 in ~20ms, NEVER blocks); normal final responses and status arrive through hooks into `projects/telemetry.rs`. Status is DERIVED (`running | waiting | idle`), never declared by an agent.

**`tmm task` is the one LOCAL subtree** (`src-tauri/src/tasks.rs`): background tasks as tmux windows with window-scoped `remain-on-exit`, so status + logs survive the command exiting. It opens no socket and is dispatched before `Config::load()` (which writes to config.toml) — because what an agent most often wants to background is the server itself. Retention is bounded (board #206): a finished window lives 30 minutes past `#{pane_dead_time}`, every `tmm task` verb reaps expired ones at its door, `stop` closes the window after printing the tail (`--keep` retains), and the skill prompt reserves tasks for long-running / asynchronous work — the foreground is the default (tmm-cli.md § Retention is bounded).

**MCP is NATIVE again, with kiro's toolSearch carrying the context cost** (owner 2026-08-28, reversing the same-day inspector-only design: "mcp 工具还是用原生的方式调用吧，给 kiro 的 mcp 工具开启 toolsearch"): registry MCP defs materialize into each backend's own config exactly as before (kiro `mcpServers`, claude mcp.json + `--strict-mcp-config`, codex `-c` overrides, grok toml, omp `mcp.json` in its isolated agent dir), and managed kiro homes get `toolSearch.enabled=true` + `minPct=0` + `minTokens=0` in `settings/cli.json` (canonical set `spawn::kiro_cli_settings`, backfilled by `refresh_hooks` on every start) so MCP schemas are ALWAYS deferred into a compact list and loaded on demand by kiro's own `tool_search` — the progressive behavior, natively.

**`tmm mcp servers|tools|schema|call|add` (the second local subtree, `src-tauri/src/mcp_cli.rs`) survives as a SKILL only** — `assets/skills/mcp-cli/SKILL.md`, an agent opts in via its skills list; build_prompt does NOT teach it (a spawn.rs test pins that).

**The skill store has BUILT-INS** (owner, 2026-08-28: "应该有一个默认的内置的skill…来源就是内置的"): `projects::BUILTIN_SKILLS` embeds `tmm-cli` and `mcp-cli` (assets/skills/*, `include_str!`) into the binary and `seed_builtin_skills()` materializes them into the managed store at server start with `source = "builtin"` — refresh re-syncs FROM THE RUNNING BUILD, save/delete refuse the reserved names (a deleted built-in would silently resurrect at restart; the UI hides delete and locks the source field), and a test pins seed + guards + heal-on-refresh. **`mem` was a built-in until 2026-11-04** (owner: "mem内置的工具都去掉吧，这个不需要了"): it is in `RETIRED_BUILTIN_SKILLS`, so the next start removes its row and files while the row is still the built-in's (`source = "builtin"`; a `mem` a person imported stays theirs), the seven seeds and the v18/v22/v32 backfills name `["tmm-cli","mcp-cli"]`, and a stored definition that still names `mem` skips it at spawn (an unresolved name is warned about and left out, never an error). Stored definitions are not rewritten (tenet 7); the owner clears the name from them. Pinned by `a_retired_builtin_leaves_the_store_but_an_imported_namesake_stays`.

**ONE url installs whatever it contains** (`skills_import` / `tmm skills import`, owner same day: "输入一个url就能装上"): `discover_skills` walks the fetched tree for every dir holding a SKILL.md (claude plugins and marketplaces need no layout table), `fetch_git_full` clones once with sparse-checkout disabled, each imported row's source points at ITS OWN subdir so per-skill refresh works, names come from the skill's frontmatter, and built-in names are skipped; the UI routes a name-less new skill through the importer, and the skill editor previews EVERY managed file (`skills_files`/`skills_file` — 256 KB cap, text only, path escapes rejected).

**The CLI door to a skill: `tmm skills load <name>`** (board #418, owner 2026-10-17: "tmm skills 可以通过命令行的形式加载…可以给 skill.md 和对应资源的路径"). Beside each CLI's own loader (kiro's and dsh's catalogs), any agent can load a skill from the shell: RPC `skills_load` (`skills::skill_load`) answers the managed root, the SKILL.md text and every other file as an absolute path with its size, from the same store and the same file walk (`managed_files`) the Skills page previews. It gives paths, not contents, so a large resource is never dumped. The paths are ABSOLUTE on the connected gateway's filesystem (`skill_root`: canonical, also when `TMM_STATE_DB` is relative, and an error, never a relative path, when it cannot be made absolute; review P2-B); reading a remote gateway's files is out of scope. SKILL.md is taken first, outside the budget, so the body and the preview's way back to it survive any truncation; at most 200 other files are listed, and `truncated` means a 201st was actually found; a directory or file that cannot be read makes the call an error, never a shorter list (review P2-A). The header's description is the SKILL.md FRONTMATTER's, read at load time with the store's own parser (`read_skill_meta`); the registry row's description, which `tmm skills list` and the Skills page show, is the declaration and may differ (review P2-C). Text output folds a description's whitespace to one line, and JSON keeps it as written. An unknown name answers its near matches (a substring either way, or the same first three letters) and exits 1. `tmm skills list` carries each skill's `root` too, so the list leads to the files. It is read-only and loads nothing INTO a running agent: that stays the CLI's own loader.

**ONE url installs whatever it contains** (`skills_import` / `tmm skills import`, owner same day: "输入一个url就能装上"): `discover_skills` walks the fetched tree for every dir holding a SKILL.md (claude plugins and marketplaces need no layout table), `fetch_git_full` clones once with sparse-checkout disabled, each imported row's source points at ITS OWN subdir so per-skill refresh works, names come from the skill's frontmatter, and built-in names are skipped; the UI routes a name-less new skill through the importer, and the skill editor previews EVERY managed file (`skills_files`/`skills_file` — 256 KB cap, text only, path escapes rejected). Its niche: per-call config reads make `tmm mcp add` + call work with NO restart, uniformly on every backend (inspector CLI from `$TMM_MCP_CLI`, default prefers an installed `mcp-inspector` binary — `npx -y` re-resolution measured 12s/call). `seed_mcp_config` still seeds `<ws>/.tmm/mcp.json` (merge, agent edits win) + `$TMM_MCP_CONFIG` at spawn so the skill path always works; `tmm mcp list|save|delete` (registry catalog) stay RPC. Registry agents (`reg_agents`, state.db v5) materialize into ISOLATED homes `<ws>/.tmm/agents/<name>/` via KIRO_HOME/CODEX_HOME/claude --settings/PI_CODING_AGENT_DIR so user-space config never leaks in; any agent may spawn (the can_hire gate was retired 2026-09-26), capped 8/project (`SPAWN_CAP`), window name = agent identity. Two delivery truths: an interactive CLI only reacts to what lands in its INPUT (hub_post types @mentions into agent panes — never into shells, they would execute it; `tmux::send_command` sleeps 200 ms between the text and the Enter because a TUI that gets the burst back-to-back treats the Enter as paste content and parks the line unsubmitted — measured on codex 0.148.0; and a kiro pane is never typed an `@`: kiro-cli opens its `@` FILE PICKER for any `@` before the cursor and an Enter while the picker has results SELECTS a file, so `[wake] @engineer …` became the attachment `m3-g2-engineering-appendix.md` and was never submitted (owner, 2026-10-20, board #436; the first case was `@kiro` → `runtime/kirocrew-artifact.json` on 2.18.1, 2026-09-03). The screen guard that sent Escape when the picker's footer was painted raced an async file search, so deliveries no longer rely on it: the delivery door types every `@` as `＠` for a backend with `Backend::at_opens_picker` (kiro), and the agent's config tells it so. A verbatim `/command` keeps its `@` and still gets that one-read guard before its Enter (`Backend::picker_open`, validator P1); hub-composer.md § A kiro pane is never typed an `@` has the measurement and the rule), and it does nothing until spoken to — which is now the DESIGN, not a problem to work around: a spawn with no brief passes NO first prompt and the agent waits (an invented line reads in the chat as words the user typed, and a contentless prompt makes an agent reason about nothing). A brief is the exception because it IS something to consume: `first_prompt()` delivers it stamped like every later message, which is also how an agent learns the wall time (`build_prompt` says so; a replayed system prompt cannot carry a date).

**The prompt teaches the communication flow, not the full CLI.** Inbound
messages are stamped and queued. The final response is captured by hooks,
recorded in the room and returned once to each agent whose request the turn carried.
`[reply]` inputs create no reverse edge, preventing ping-pong. `tmm send
"@name …"` starts a new question or handoff; a recipient-less send is rejected,
except `--status` ambient progress. `tmm log` supplies room history, backlog
messages are consolidated, and unclear context is verified before action.
Board handoff and spawn fit in one line each; everything else stays in
`tmm --help` and the CLI skill.

**A Team agent receives the conversation delta with its next @mention.** A
`[tmm team context …]` block comes FIRST and the current stamped request
LAST (board #279, owner 2026-09-29 10:49: "把这个放在前面，然后把真正给 Agent
发送的最后的消息放到它的后面"), so the last thing the model reads is what it
must answer. The block contains non-noise room messages since that target's previous delivery as
`sender -> recipients: body`. Explicit mentions and new hook-captured final
replies persist their exact recipients in the room message's `to` field;
historical replies without that route are reconstructed from the senders
waiting on the agent. Status and lifecycle rows are omitted. This is Team-only
(`launch.json.team`); solo managed agents keep the original one-line delivery.
The delta is bounded to 40 recent messages / 12K characters from the newest
1000 room rows, says when older context was omitted, excludes archived messages,
and labels itself background rather than instructions. The order moved
nothing a reader depends on (the consumer audit is on #279). The receipt
matches the whole typed line, which is what was typed. The reply edge reads
`[tmm chat …]` lines wherever they sit, and context rows never start one.
A held batch (#257) keeps each context right before its own line. The
activity log SHOWS the prompt ask first, because its 1024-char display cut
would otherwise keep only the context. That order comes from the producer,
never from reading the echo (orchestrator 2026-09-29 13:24):
`address::context_first` returns the typed text and `ask_at`, the byte where
the stamped line starts in it, and the delivery row keeps that offset
(`deliveries.ask_at`, schema v30; 0 when nothing leads the line). The receipt
matcher (`settled_by`) also returns WHERE in the echo it found each settled
row, mapped from its whitespace-free match back to the echo's own bytes, and
the stored text replaces each Team row's span in place with its
`address::shown` form (its line, then its context). Every byte outside those
spans (a person's words typed around our line, the break between held lines)
stays as it was, in order (orchestrator 14:03: no display loss). An echo that
settled nothing (a person typing, a pasted context block) is stored raw. An integer, not a display-text column: it duplicates no text and cannot
disagree with the `line` it splits; an offset that does not split it shows
the line as typed.

### Every agent lives in a tmux server somebody forked — two incidents and one near miss in a day (2026-10-12)

A managed agent is a pane in a tmux server, and that server belongs to whatever forked it: the user's shell, or our gateway running `tmm project up`. Twice in one day every session on the dev host was lost, and a third way was found before it fired — each by a different hand, each because something was allowed to act on a tmux server it did not create:

1. **05:51** — the Rust test suite, run in parallel, issued `kill-server` through a process-global socket another test had reset, and hit the default server (board #349).
2. **07:12** — a negative control on that fix put the bug back on purpose and ran in a developer's real shell, where `$TMUX` pointed at the real server (board #349).
3. **08:02, found before it fired** — the owner's tmux server sat INSIDE `tmux-mobile-dev.service`'s cgroup, forked there by the gateway, and only a hand-made `KillMode=none` drop-in kept `systemctl --user stop` from killing it; the gateway unit that replaced the dev unit forks tmux the same way and is restarted after every merge, with systemd's default `KillMode=control-group` (board #350).

The rules that came out of them, each in its own doc: tests reach tmux only through a socket they named, inside an isolated `TMUX_TMPDIR`, serially (testing.md); the gateway unit renders `KillMode=process` so a restart signals the gateway alone, the protection is applied to a running unit in place by `daemon-reload` and read back from the manager before any stop, and every stop or restart of a running unit of ours is refused until the manager reports it (tmm-cli.md § The gateway). The common shape, for the next mechanism that touches tmux: name the server you mean, and never let a restart or a stop of OUR process be a stop of the servers it happened to fork.

### Registry defaults are exactly the seven backend-native agents

`kiro`, `codex`, `claude`, `grok`, `omp`, `kimi`, `dsh` — one backend-native default per supported backend (the Manager flag they once carried was retired 2026-09-26; spawning is every agent's ability) with built-in `tmm-cli`/`mcp-cli` (`mem` retired 2026-11-04, above). All seven ship the terse 10x-developer sentence for their own backend and NOTHING else (board #344, owner: "这个提示词是我们自己的 tmm 配置，发布版本的默认配置不应该有这些"): no worktree location, no Git author rule, no co-author trailer. Those are one person's conventions, and a release hands every fresh install the same neutral persona; workflow rules belong in the app-wide `<config>/AGENTS.md` (§ The app-wide instructions lead every prompt), which leads every managed agent's prompt on every backend, and in the definitions a person has saved themselves. `reg_seed` seeds an EMPTY table and does nothing else: a stored definition is the user's declaration (tenet 7), so it is never rewritten — it used to upgrade a stored `kiro` whose text equalled an older shipped default, and the newer one ADDED a Git workflow and a personal trailer to definitions nobody had asked to change. Pinned by `registry_seed_never_rewrites_a_stored_definition` (the original terse text, the first verbose Git version, the worktree-and-trailer version that briefly shipped, a custom persona and the current default all come through byte-identical, down to `updated_at`) and by the seed test, which fails if ANY of the seven seeded prompts mentions a worktree, a trailer, a Git author or a commit. **The seed rule** (board #511, owner 2026-11-04 00:28: hardcoded defaults made a fresh install unusable or wrong): a shipped default, and every backfill migration that inserts one (v18 `omp`, v22 `kimi`, v32 `dsh`), names NO host-specific value. No model — empty is the CLI's or the user's own default, carried into the home (for claude the `settings.json` env's `ANTHROPIC_MODEL`, for kimi the user's `default_model`, for omp the user's `modelRoles`; see their sections) — and no inline MCP that needs a credential the install does not provide. Two incidents behind it: the `claude` seed pinned `global.anthropic.claude-fable-5-1[1m]` (2026-09-02 to 2026-11-04), a Bedrock inference profile only some accounts and regions have, so on first-party Anthropic or another account every turn of the seeded agent failed; the `omp` seed pinned `bedrock-extra/global.anthropic.claude-fable-5-1` (2026-09-07 to 2026-11-03), a provider only the owner's `models.yml` declares, and a host without it fell back to omp's bundled `anthropic/claude-opus-5-5` and answered `403 Invalid API key`. And four seeds plus the v22 insert carried `kiro-web-search==0.1.3` inline: it wraps Kiro's own search service and needs `KIRO_API_KEY`, which no seed carries, so on any other host every agent of those backends started an MCP that exited "missing API key" (and needed `uvx`). A pin or an MCP belongs in the stored definition, or a central MCP asset, of the host that has it. Seeding does not depend on what is installed: a definition is a declaration, and readiness marks a backend whose CLI is missing. Stored definitions are not rewritten (above), so an install seeded with an old pin or the shim keeps it until its owner changes it. Pinned by the seed test (all seven: no model, no inline MCP) and the v18/v22/v32 backfill tests. **dsh joined on 2026-11-05** (board #6, owner: "我记得以前我们还做了 dsh 的适配，但是配置里没有"): the dsh backend shipped with board #404 but no seed, so no install listed a dsh default; v32 backfills it once into existing installs in dsh's default input mode (`queue`), with the same neutral persona for DeepSeek Harness, whether or not dsh is installed. Kiro and OMP use their built-in search (omp ships a native `web_search` tool). `reg_list` fixes those names in that order before alphabetizing custom agents, so AgentsPage, spawn pickers and CLI all agree. Retired `docs`/`reviewer`, `*-default`, and `cc_builder` must not return as seeds or examples.

### Managed agent launch PATH is part of the recipe

the supervised server can have a service-only PATH even when the user's CLIs are correctly installed under `~/.local/bin`/`~/bin`/`~/.cargo/bin`/`~/.kimi-code/bin` (Kimi Code's installer puts its one binary in the last, board #224). Both project-agent and Team launchers prepend those standard user bins (plus the colocated `tmm` dir for project agents), dedupe, and persist the result; otherwise a Claude home can be perfectly rendered yet its pane only says `command not found: claude`, and restart faithfully repeats the failure. Claude's carry is the `env` object from `~/.claude/settings.json` plus its documented credential commands (`shared::claude_carry_of`, § Claude below): projects and Team copy only those into their explicit/isolated settings so Bedrock switch, region, model pins and the API-key helper carry while plugins/preferences do not. Empty Claude model means that inherited `ANTHROPIC_MODEL`, never a hardcoded `--model sonnet`. Supported Claude PRIMARY pins use the literal `[1m]` suffix (global Sonnet 4.6, `cc_builder` Fable 5.1); it MUST pass through `shell::quote` because bare `[1m]` is a zsh glob. ### A definition's secrets are files only the owner can read (board #448, 2026-10-22)

An MCP server's env values and literal headers are secrets, and they reached other local users four ways. kiro found it during #446: the reviewer's codex launch line carried an API key as `-c mcp_servers.<name>.env.<KEY>=…`, readable by anyone through `ps`. The same line sat in `launch.json` and the launch script (0644), the backends' MCP files were 0644, one agent home was 0755, and `state.db`, which holds the definitions, was 0644 in a 0755 directory. The rule now: a value never rides a launch line, and every copy is a file only our uid can read. Unix only: modes, `O_EXCL` and uid checks; no Windows ACL is claimed.

**codex's MCP servers are a profile file.** `render_codex` writes them into `<CODEX_HOME>/tmm-agent.config.toml` and launches with `--profile tmm-agent`. codex layers that file over the user's config.toml, below trusted project config and below `-c` (codex docs, Advanced Configuration § profiles, 0.134.0 and later).
- The file is built as structural TOML (`shared::codex_profile`, which since #455 also carries the model and effort) and keeps each field's meaning. Stdio: `command`, `args`, `env`. HTTP: `url`, `enabled`, `experimental_use_rmcp_client`. A `Bearer $VAR` Authorization header becomes `bearer_token_env_var`, a `$VAR` header becomes `env_http_headers`, and a literal header becomes `http_headers`.
- It is rewritten whole on every render, so a revoked server leaves nothing.
- The user's `*.config.toml` inheritance skips this one name. A link by that name, left by an older inheritance, is removed itself; its target is never touched. The whole inheritance (linking config.toml, `.env`, `auth.json` and the user's profiles, and that removal) acts on the codex home HELD through the private walk (`safe_fs::private_subdir`: `symlinkat`/`unlinkat`/`readlinkat` on that one `Dir`), so a codex home that is a link to an outside directory is refused before anything there changes (reviewer residual on d2c24e38).
- Measured on codex-cli 0.162.1: a profile's stdio env reached the server on a fresh launch and on `resume --last`, and no process's cmdline carried it.
- The other codex answers stay on the line (`-c`), because they must win over a project config.

**Limit: a trusted project decides where those credentials go.** Measured on 0.162.1, with a profile `[mcp_servers.fake]` (command A, a sentinel env):
- A trusted `.codex/config.toml` that sets only `command = B` for the SAME name: B started and received the profile's env, because the tables merge per key.
- A server under a DIFFERENT name: A kept the sentinel, and the other server got only its own env.

A project its owner trusts is above our profile by codex's design, and this is that trust boundary, accepted.

**codex's model and effort are the same profile** (board #455, non-negotiable 10; orchestrator ruling (a), no codex exception). `render_codex` writes the definition's `model` and `model_reasoning_effort` as top-level keys of `tmm-agent.config.toml` (`shared::codex_profile`, the one whole-file writer that also carries the MCP tables), and the line carries neither `--model` nor `-c model_reasoning_effort`. Measured on codex-cli 0.162.1 (2026-10-23, an isolated home with a dead provider; the footer names the pair codex will use):
- A fresh launch takes the profile's pair over the user's config.toml. A resumed session takes it too, by `resume --last` and by `resume <id>` (the same session, its earlier prompt on screen, no new rollout), and over a session-only `/model` pick. So a definition change reaches a restarted codex: every restart with a definition re-materializes (`refresh_agent`), rewriting the profile; a running pane picks it up at its next launch, like the MCP profile.
- An empty field omits its key: NOT SET at this layer, not "the backend default". codex's own config and resume rules decide: a resume whose profile names neither restores the session's last pair; naming one takes the configured value for both, the other from the user's config.
- The trusted-project boundary above holds for these keys too: a trusted `.codex/config.toml` naming a model or effort is above the profile and wins (measured on a fresh launch and on resume). The line used to beat it; the ruling accepts the same boundary as MCP.
- A person's `/model` choice saved as the DEFAULT inside a managed pane is written by codex into THIS file (measured; the user's config.toml is untouched), and the next render overwrites it whole. To give a managed codex another model, change its DEFINITION (the Hub's Agents page or `tmm registry save`); `/model` in the pane is for the running session only.
- A home whose definition is gone keeps its spawn-time snapshot, flags included (the existing rule); such an old line still works and is not migrated. A model is not a secret, so `Backend::line_is_private` does not refuse it.

**Every file a render writes is published privately** (`safe_fs::write_private`, behind `shared::write_atomic`/`write_owned`):
- The directory is reached from the ENTRY only (reviewer P1-A on 151b36eb). The prefix before the path's `.tmm` component, the project root, is opened from its canonical path, so a legitimate HOME alias is resolved there and only there. Then `.tmm` (ours, mode kept) and every component below it is opened one handle after the other with `O_DIRECTORY|O_NOFOLLOW`, verified to be ours, and made 0700 with `fchmod` on that handle. A link anywhere inside a home, even one to another directory of ours, is refused. A path with no `.tmm` component is refused in production; only a test's scratch directory is walked from its canonical parent. A directory we only pass through (`.tmm`, kept 0755) loses group and other write if it had them, and `publish` refuses any held directory still writable by another user or not ours: a handle protects the directory object, not the names inside a directory others can write.
- A temp file is created with `O_CREAT|O_EXCL` and made exactly 0600 by `fchmod` before the first byte, whatever the umask. It is written and fsynced.
- The target is checked with `fstatat` and no link is followed. Absent, or a regular file of ours, means it is replaced by `renameat`, and the directory is fsynced. A link, anything else, or another user's file is an ERROR and is left as it is.

Every step acts on the one held directory (the `safe_fs::Dir` walk, which #433's scope download also uses). So a directory whose NAME is swapped keeps receiving the write, and nothing goes through the new name. A user file copied into a home (grok's `auth.json`, omp's `agent.db` and `models.yml`) is read and published the same way (`shared::copy_private`); `std::fs::copy` kept the source's mode and followed a link at the destination. A source PIN, not a proof, keeps `std::fs::write`, `fs::copy`, `File::create` and `OpenOptions::new` out of `backends/`, `spawn.rs`, `live_config.rs` and `recipe.rs`. The recipe door's one write is this publication.

**A start whose privacy fails is refused** (reviewer P1-B on 151b36eb and its residual). The start does not go ahead when `refresh_hooks` cannot make the home private, when any backend's refresh write (`Backend::refresh` returns `Result`: hooks, profiles, settings, recipe migrations and backfills) or a copy into the home is refused, or when `refresh_agent` cannot re-materialize. Two layers, two rules. A backend's OPTIONAL refresh inputs (`Backend::refresh`: a hooks or profile file to patch, an optional source to copy): "nothing to refresh" (no file, not parseable, no optional source) stays `Ok(false)`, and only a failed write is an error. `refresh_agent`'s own inputs, the launch recipe and the definition it names (board #452 (a)): ABSENT keeps the old materials (`Ok(false)`: no `launch.json`, or the registry row, the root team, a sub-team on the member's path, the member or its base gone), while PRESENT but unreadable REFUSES the start, naming what it could not read (a `launch.json` that does not read or parse, a store read error, a team that does not expand, a member with neither a base nor an inline agent). The definition is resolved ONCE, keeping the cause (`spawn::resolve_provenance_def`); the fail-soft `effective_def` its other callers use is a wrapper over it. This is hardening: before it, those cases were taken for "nothing to refresh" and the start went ahead on the old materials, skipping the render. The validator's single unexplained restart on #452 is not attributed by this change. The error is the answer, and neither the old recipe nor the respawn fallback runs (`resume_slot` answers `refused`; `reconcile::create_or_keep` refuses before a window exists). The replay door itself (`spawn::recipe_parts`, behind both relaunch forms) also refuses a saved line that may not be replayed: an older build's codex line carrying `-c mcp_servers.…` values (`Backend::line_is_private`). Staging a managed agent's relaunch script privately is required too; the line is never typed directly instead.

**The workspace's own MCP file is private** (P1-C). `<project>/.tmm/mcp.json`, which `seed_mcp_config` keeps for `tmm mcp` and which holds the same values, is published privately when it changes and closed in place (mode only, its content and merge rules untouched) on the no-change path and at startup.

**A managed home is private.** At materialize and on every `refresh_hooks`, `safe_fs::private_home` walks `<root>/.tmm/agents/<name>` from the canonical project root: `.tmm` must be ours, and `agents` and the home are set to 0700. No link is followed.

**The store is private before SQLite opens it, or refused** (`safe_fs::private_db`, run in `Store::open`):
- Only the parent prefix is canonicalized, so a HOME alias resolves. The file name is never resolved.
- The app's own config directory is made 0700. A custom `TMM_STATE_DB` directory is only checked, never chmodded. The direct parent must be ours and not group- or other-writable. Every ancestor must be owned by root or by us, AND either not writable or sticky. Sticky relaxes only the write bit under a trusted owner, so a 1777 directory of another uid is refused. Otherwise the store is refused with "choose a private directory". SQLite opens by pathname and makes its sidecars by pathname, so the whole chain must be one no other user can change.
- Through the parent's handle, a new database is created empty at 0600 with `O_EXCL` before SQLite's first write. An existing one, and each `-wal`/`-shm`/`-journal`, is set to 0600 with `fchmod`. A link is refused untouched.
- SQLite opens the verified canonical parent plus the file name. Measured with the bundled SQLite under umask 022: WAL and SHM take the main file's mode, also when re-created after a checkpoint and a reopen.

**Old copies close at startup** (`projects::tighten_existing`, every server start, before the legacy import):
- The legacy team.db and its siblings are closed in place under the store's trust rule (P1-D): in a directory others can change it is NOT tightened and left as it is. Every existing file and sidecar, the store's included, is opened `O_RDONLY|O_NONBLOCK|O_NOFOLLOW` and verified on that fd (a regular file of ours) before `fchmod`, so a name swapped between the check and the open, or a FIFO, is refused without blocking. It is never reopened once imported.
- Each project's `.tmm/mcp.json`.
- Every managed home of every stored project is walked private, including a LIVE one, which `reconcile::create_or_keep` keeps without `refresh_hooks`.
- A failure, and anything that cannot be audited (the project list, a `.tmm/agents` listing or entry, a home whose marker cannot be read, a parent whose `stat` fails or that is not a directory), is logged as "NOT tightened — needs the owner: <path> (<why>)". Only NotFound is absent; an orphan `-wal`/`-shm`/`-journal` is closed even when its main file is gone. The exposure is not called closed.

What permissions do not do: a running process keeps the argv it was started with until it is restarted, and nothing here replaces rotating a key that was exposed.

### A definition read never carries an MCP value (board #451, 2026-10-23)

The files above close a secret to other USERS. One door still put it in an AGENT's context: `tmm mcp list` printed each central def whole, so an agent asking which servers exist got the kiro-web-search `KIRO_API_KEY` into its transcript, its provider's request, and anything it might quote. The same values came back from `registry_list` and `teams_list` (inline servers) and filled the Hub's MCP textarea. `tmm` reads only through those RPCs, so they are the one place to close it (`projects::mcp_mask`).

- **Every `env` and `headers` value is masked as `"<set>"`** at the three read doors; names, `command`, `args` and `url` stay. References are masked too (reviewer P1-A, orchestrator 03:09): whether `$VAR` is a reference depends on the consumer. An env value is literal text for codex, kiro, kimi, claude, omp and grok; only dsh reads it as `process.env`. Headers are references for kiro, kimi, codex and dsh and raw text for claude and omp. A central def has no backend, so nothing can prove a `$VAR` is not a password.
- **No reveal, anywhere.** There is no `--reveal`, and the editor shows the same marker (CLI/UI parity). The store keeps the values, and the materializers read the store (`spawn::mcp_defs`), never these answers.
- **A save keeps the value behind each `"<set>"`**, read from the row as stored NOW, inside the `with_store` section that writes it (P1-B). A rotation saved after the list is kept, not reverted. The match is by owner path: central (server, field, key), agent (agent, server, field, key), team (team, member, server, field, key); `env` and `headers` are separate. Refused, naming the path and never a value, with nothing written: a marker with nothing stored there (a new key, a rename, a value deleted meanwhile), two stored servers or members of one name, and an unnamed inline server carrying a marker. Duplicate inline server names are refused at the door anyway, because every materializer keys servers by name.
- **`"<set>"` is a reserved protocol string**, not a claim that no token could read so. It can never be entered as a new value; a value already stored as that text is kept as it is.
- **An unreadable stored field fails the whole list** (delta 2): a def that is not an object, an `env`/`headers` that is not an object, an agent `mcp` that is not an array of names and objects, team members that do not parse or a member that is not an object (wrapped in an array, encoded as a string, null: reviewer P1-A on the first commit). The answer is an error naming the row and how to repair it, never the text, never serde's message, never a half list. A full save carrying no marker needs no stored MCP read and repairs the row (the registry and team saves still read the row for `input_mode`). The doors accept only what they can list.
- **A refused list closes that kind in the Hub** (reviewer P1-B on the first commit). A marker-free save is the repair path, so a row read BEFORE the refusal, saved with only its persona changed, would put its old `"[]"` over the field the server just refused to list. So while `registry_list`, `teams_list` or `mcp_list` is refused (a JSON-RPC error, or a server without the cap), the AgentsPage shows the reason where those rows would be, offers none of them, opens no editor of that kind, and an editor already open keeps its text but cannot save and says why. A timeout or a lost link is not a refusal: the last list stays, as before. A successful read reopens it; the repair itself is a full save (`tmm … save`). Answers are ordered by request (reviewer P1-B residual, the #444/#447 ABA): each kind's read takes a generation when it starts, and only the newest read of that kind may publish rows, a refusal or a recovery, so an older success held in flight cannot lift a newer refusal and an older refusal cannot cover a newer success. A recovery clears only the editor error the refusal put there, and an editor's opening checks the refusal again when a discard question is answered.
- **A server's name is the materializers' key, verbatim** (P2): `" s "` is another server than `"s"`, so it keeps nothing of `"s"`'s values; member names follow the teams module (trimmed).
- **A client asks first** (P1-C). The server announces `mcp_masked` in its login caps. `tmm` (`rpc_needing`) and the Hub (`ws-api`, the #377 gate on the CURRENT connection) send none of `mcp_list|save`, `registry_list|save` and `teams_list|save` without it, because an older server would print the values and store the marker as a literal. A new client on an old gateway is refused ("update the server"); an old client is fixed only by deploying the gateway.

Scope: this closes accidental discovery through `tmm` and the Hub. It does not stop an agent with a shell from reading its own home's materialized MCP file (the CLI needs that file to start the server), and `args`/`url` are not filtered: secrets belong in `env` or `headers`. Nor are fields a definition does not declare (an unknown member or agent key is stored and listed as given, orchestrator on validator V2): a secret put in an undeclared field has been put in the open. A save door's parse error names where the shape broke (line, column) and never quotes what was submitted (`mcp_mask::no_echo`, validator V1: serde's own message carries the value).

### The omp backend: one relocatable agent directory (2026-09-07)

omp (oh-my-pi, the `omp` CLI) keeps its ENTIRE state — auth store
(`agent.db`, the `auth_credentials` table), `config.yml`, `mcp.json`,
sessions, extensions — in one directory that `PI_CODING_AGENT_DIR`
relocates (its settings docs; verified live on omp 18.0.6). So
`render_omp` needs no per-file plumbing: the isolated home IS that
directory. Four decisions, each measured rather than guessed:

* **Auth carries as `agent.db`, the model catalog as `models.yml`** — the
  grok lessons (auth.json, config.toml catalog): an isolated home without
  the credential store is a logged-out agent, and one without the user's
  `models.yml` cannot resolve a registry model that lives there. On the
  owner's host that file declares the Bedrock trio under `bedrock-extra`
  (fable-5-1 / opus-5 / gpt-5.6-sol — the bundled catalog lacks Fable 5.1,
  and its own gpt-5.6 entries 400 on Bedrock because the converse-stream
  transport sends the Anthropic `thinking` block to reasoning-marked
  models, measured 2026-09-07; the gpt entry is `reasoning: false` for
  exactly that reason). The user's `modelRoles` carry too, and nothing
  else of their `config.yml` (`omp_config_yml_from`): an unpinned registry
  model is the USER's default role, a pin overrides only `default`. Without
  this, an empty model meant omp's bundled `anthropic/…` default, a 403 on
  a host whose only provider lives in `models.yml` (2026-11-03, omp 18.15.0;
  pinned by `omp_config_carries_the_user_model_roles_and_nothing_else`). Env-keyed providers (Bedrock bearer tokens) need
  nothing and lose nothing. UI prefs and hooks deliberately do NOT carry.
* **The prompt is APPENDED, never replaced** — `--append-system-prompt
  <home>/system-prompt.md` (a file path; verified the contents reach the
  prompt). omp's builtin prompt teaches its own tool harness (hashline
  edits, LSP, subagents); `--system-prompt` would lobotomize the tools.
  Model → `config.yml` `modelRoles.default` (identity in config, kiro's
  lesson), mirrored as `--model` so a resumed session cannot keep its own
  (§ A managed agent's MODEL lives in its config); effort → `--thinking`;
  approvals → `--auto-approve`.
  `OMP_SKIP_SETUP=1` rides the launch env: a fresh home has no
  `setupVersion`, and omp 18.2.10 then opens its provider-setup wizard,
  where every typed line and `/command` lands (#243, measured 2026-09-27:
  a fresh home without it shows "Setup step 1 of 5", with it the prompt).
  Auth already carries, so the wizard has nothing to add.
  `config.yml` and `mcp.json` are files the render OWNS
  (`shared::write_owned`): no model role to write or an empty MCP set REMOVES
  the file on the next spawn. Skipping the write kept the previous render's
  file, so a restarted omp stayed on the old model and kept loading a
  revoked server (#241, validator, 2026-09-27; kimi's `mcp.json` likewise).
* **Telemetry is a generated TS extension**, `<home>/extensions/
  tmm-telemetry.ts` (omp auto-loads that directory), emitting CLAUDE-shaped
  payloads to the notify helper so the normalizer needs no third dialect —
  only the `omp` backend arm. **Every line the user typed is reported, the
  run's first and each one steered into a busy run, when and only when the
  message carrying it reaches the run** (board #4, measured on omp 18.15.0,
  2026-11-05). `input` fires once at submission ingress with the typed text,
  BEFORE omp interprets or queues it, so it alone is no receipt: a builtin
  command (`/hotkeys`) and a queued line withdrawn with Alt+Up fire `input`
  and never enter a run. A typed line that does enter a run ends as its own
  `message_end`: a `user` message whose text is the line (an idle prompt, and
  a steered line, which gets no new `agent_start`), or for `/skill:<name>
  args` a `custom` `skill-prompt` message whose `details.prompt` is the
  typed line (its content and `before_agent_start.prompt` are the expanded
  skill body). The extension holds the `input` texts (sources `interactive`,
  `rpc`) and reports one as `UserPromptSubmit` when a carrying message ends,
  matched by whitespace-blind equality, then forgets it. Only a message omp
  attributes to the user carries a typed line (`attribution: "user"`, omp's
  own field for who initiated a message, measured on an idle prompt, a
  steered line and a skill), so an agent redirect or injection with equal
  text never matches a stale held line. Held lines are never evicted: a
  queued line survives any amount of typing that starts no run (review
  round 1 follow-up: an early 64-entry cap could drop it). So each line is reported once, a line that never reaches the model is
  never attributed to another prompt, and a message nobody typed (a
  reminder, runtime context, another extension's) matches nothing. If omp
  ever rewrote a line, nothing would match and the line would be swept
  `unconfirmed`, never misattributed. `details.prompt` is typed in omp's own
  source (`SkillPromptDetails.prompt`, "the draft as submitted", v18.15.0
  `packages/tui/src/chat/messages.ts`) and optional; reviewer accepted it. `context` (every model call, a session-title side request
  included) is not read. Round 1 of the review (reviewer P1-R1, validator
  S2–S4) rejected the first version, which drained every held `input` at the
  next `before_agent_start`: it reported `/hotkeys` with a steered line,
  dropped the first of two queued skills, and attached a withdrawn line to
  the next prompt. Before #4 the prompt was read from the first `context`
  after `agent_start`, so a steered line was never reported: its row was
  swept `unconfirmed` 45 s after the turn and its sender missed the reply.
  The hub does for it what it does for dsh: the receipt settles (#249) and
  the sender joins the reply edge (#256). Pinned by
  `a_line_steered_into_a_busy_omp_is_reported_once_as_its_own_prompt` (S1),
  `only_what_the_user_typed_becomes_a_prompt` and
  `typed_state_is_reported_only_with_the_message_that_carries_it` (S2–S4),
  the generated extension under node replaying the measured events. Live on

  reply went to both senders. `agent_end` with
  `willContinue` is an auto-continuation, not a completion. `refresh_hooks` rewrites the
  whole file when this build's text differs.
* **Resume is cwd-scoped by construction** — sessions live per encoded cwd
  under the isolated dir, so `--continue` (breadcrumb, then newest session
  of THIS cwd) cannot cross projects; an exact id uses `--resume <id>`.

  reads the server's verdict and has no matcher): "omp" lives inside

### The input mode is a definition field, offered only where it was measured (board #245, 2026-09-27)

A line typed at a BUSY agent either waits for the turn to end and becomes the next prompt (**queue**) or goes into the running turn (**steer**). `reg_agents.input_mode` (v25, `queue` for every agent that existed then; owner 2026-08-20 for kiro, 2026-09-27 for the choice) sits next to model and effort, and each backend file renders it into its own config at spawn and on restart (`refresh_agent`); the repair path on `project up` has no definition, so it keeps a valid value and only backfills `queue`. `Backend::switches_input_mode` names where the choice exists; `backends_list` carries it as `input_modes`, the Agents editor shows the Select only there (with a hint when steer is chosen), and `registry_save` refuses `steer` elsewhere. The editor never rewrites a saved mode from the capability list (validator, #245): the list arrives on connect and may be missing, so the payload saves the draft's mode as it is, a saved `steer` keeps its field visible, a late list re-renders an open editor (`onServedBackends`), and only an explicit backend pick changes it (since #336: to that backend's default, see below). The list itself is fetched by `serverReady()`, the ONE handshake every connect path in `App.svelte` runs (boot with a saved token, reconnect, manual connect): at 1.0 the boot path called `probeHub` alone, so on the live app the field never appeared while the mount tests, which serve the list directly, passed (board #253; pinned by `App.source.test.ts` "every connect path runs the one server handshake…"). **A new kiro definition steers (board #336, owner 2026-10-15: "在启动 Agent 的时候如果是 kiro 默认就给我使用 steer 模式吧 不要用 queue 模式").** The default is the BACKEND's, defined once: `Backend::default_input_mode` (`kiro::DEFAULT_INPUT_MODE = "steer"`, `queue` for every backend whose file says nothing; pinned to be a mode `validate_input_mode` accepts), carried to the client as `backends_list.default_input_mode` so the client never mirrors it. It applies only where a definition is NEW, and since `registry_save` and `teams_save` are upserts, "new" is decided against what is STORED, in the same store section that writes (reviewer P1-B on 99e233c3): a save that names no mode (absent; for a registry def also null) keeps an existing row's mode, and an existing bare team member (same name) keeps its stored mode — including none, which has always meant `queue` and is left absent, so a team re-saved with only its description or a role changed is stored byte for byte; only a NEW row or a NEW bare member gets the backend default (`registry::unnamed_input_mode`, `fill_member_input_modes`). A kept mode the def's new backend cannot carry falls to that backend's default. The empty-registry seed gives each seed its backend's default. `tmm registry save` OMITS `input_mode` without `--input-mode` (reviewer P1-A): never a null, because an older server's `RegAgent.input_mode` has a serde default that covers a missing field and refuses a null. In the Agents editor a new agent and a new bare member start in the served default and FOLLOW it (a UI-only `modeFollowsDefault`, never in the payload) until the person picks a mode: a backend pick then moves a following draft to the picked backend's default, and a list that lands after the draft opened gives it the served default without making an untouched draft dirty; a picked or stored mode is never moved to a default, only a steer the picked backend cannot carry becomes queue (the #245 rule; reviewer P2 on 99e233c3). What is stored is never rewritten by a read or a seed (tenet 7, #344), so the owner's existing kiro definitions change only if he switches them. ### One definition of "an agent this app created"

`projects::managed_home` / `is_managed_in` — the isolated home `<ws>/.tmm/agents/<window_name>/` that `spawn` materialized, never the window name (a hand-started window can share it). **The marker is what spawn WROTE, not the directory existing** (board #112, 2026-09-09): `home_is_managed` requires `launch.json` (every backend writes it before the window exists) or the pre-recipe kiro `agents/<name>.json` (refresh_hooks backfills the recipe only at the NEXT start, and a continuously-running old agent must not be demoted meanwhile). The directory alone re-armed the gate: `agent_remove` deletes the home while the kiro process keeps running with `KIRO_HOME` in its env, and its next write re-created `settings/`/`sessions/` (observed 2026-08-19, `.tmm/agents/builder/` back with no config and no recipe) — so auto-post and `@all` delivery resumed for a window the user had ejected. No CLI re-creates either marker file. THREE gates share that one function and must never re-implement it: chat participants (`hub_agents`), stop-hook auto-post (`maybe_auto_post`), and pane delivery (`deliver_mentions` — without it `@all` types into a kiro the user started by hand). Measured on kiro-cli 2.16.2: the user-space install is close to inert anyway — `~/.kiro/hooks/tmux-mobile.json` is not read, and `kiro_default` is a BUILT-IN name, so a materialized `~/.kiro/agents/kiro_default.json` is shadowed (its hooks never fire; the same file renamed fires immediately). Managed agents work because their config is a *named* agent inside an isolated `KIRO_HOME`. Do not rely on the global path for observation. The kiro launch env is ONE definition, `backends::kiro::kiro_launch_env` (spawn recipe and the launch.json backfill alike): `KIRO_HOME` plus `KIRO_SKIP_MIDWAY_CHECK=1` (board #183, owner 2026-09-12: "kiro 启动 agent 会报提示…跳过这个提示，避免启动被阻塞住") — a managed pane is unattended, and kiro-cli's launch-time "Your Midway session has expired or is missing. Refresh it now with mwinit? [y/N]" parked the agent until a human typed; kiro-cli 2.21.4 reads that switch beside the prompt (`crates/chat-cli/src/launch/midway.rs`; no flag or setting exists), and skipping the check leaves kiro's own login untouched — Midway gates only internal endpoints. Existing agents pick the variable up when their recipe is next rendered (a spawn or a backfilled `launch.json`); a recipe already written replays as it was. Not reproduced on this host (the owner's cookie was fresh; a fake `HOME` and a fake `mcscli` did not trigger the check) — the prompt's disappearance is the owner's acceptance.

**An agent name is a plain word, checked once** (`agents::valid_name`, 2026-09-03 review): letters and digits of any script, `-` and `_`, starting with a letter or digit, at most 64 characters. The rule is the intersection of the four parsers the name passes through — a directory component under `.tmm/agents/` (so no `/`, `\`, `.`, `..`), a tmux window name that also lands inside targets (`session:name.pane` — so no `:` `.` `=` and no glob characters), a CLI argument (so no leading `-`), and an `@address` (so no whitespace or `@`). It is enforced where a name ENTERS: `registry_save`, `teams::validate` (team and member names), `spawn` (the final window name), `agent_remove`; and every `<ws>/.tmm/agents/<name>` path is built by `agents::home_dir`, which returns `None` for a name that fails — so `managed_home`, `is_managed_in`, `agents::detect_pane`, `spawned_by`, `team_of` and `refresh_hooks` all answer "not managed" for such a window. The case that made this a rule: `agent_remove("../..")` resolved to `<ws>/.tmm/agents/../..` — the workspace itself, which `is_dir()` — and `remove_dir_all` would have deleted the project. A whitelist, not a blacklist of separators, so the next parser that reads a name is covered too.

**The launch recipe is written before the window exists, and its write is a spawn error** (2026-09-03 review). `launch.json` is what makes a window ours on restart — `agents::detect_pane` reads the backend off it, `relaunch_line` replays it — and it used to be written last with its error dropped, so a full disk or a permissions slip produced a live agent whose restart took the generic launch path and came back deaf (the very regression the recipe was introduced to end). Record, then act: `spawn` writes the recipe after the env is final and before `ensure_session`/`new_named_window`, so a failed write leaves nothing running. The pre-recipe kiro backfill in `refresh_hooks` stays best-effort, because there the agent is already running either way.

**The recipe binds an agent to the gateway that launched it** (board #440). Besides `TMM_PROJECT`, `TMM_AGENT` and `TMM_MCP_CONFIG`, the env carries `TMM_SOCKET`: the local socket this gateway bound (`server::bound_local_socket`), or `''` when it has none. A restart, restore or fork replays it with the rest of the recipe. The agent's tmm then reaches THIS gateway outside the TCP auth lockout, and checks after login that it is this config's gateway (tmm-cli.md § Which transport). The empty value masks a stale one in the tmux environment. The reason is the binding and the masking, not secrecy: an agent's tmm already reads the token from the operator's config.toml through the inherited `XDG_CONFIG_HOME`.

**Restart means "come back up to date"** (owner, 2026-09-08: "现在我直接重启那个会话里的 agent 就可以生效了吗" — and the honest answer was no: the recipe replay is verbatim, so a restarted agent kept its spawn-time prompt forever, contradicting what global_prompt.rs promised). `hub_agent_restart` now calls `spawn::refresh_agent` before the replay: `materialize` — the factored-out disk half of `spawn` (prompt, backend config, skills, MCP seed, hooks, recipe) — runs again from the CURRENT registry def and app-wide AGENTS.md, preserving `spawned_by` provenance and `team`, and dropping the original brief (the conversation is resumed; the brief is history). **The def is resolved through the recipe's PROVENANCE, so uniquified windows and team members refresh too** (board #113, 2026-09-09): `refresh_agent` used to look the def up by WINDOW NAME, so `lead-2`, every team member and anything renamed kept replaying its spawn-time snapshot forever. `launch.json` now records `agent_def` (the registry def name behind a solo spawn) or `member` beside the existing `team` path — in the recipe, not a slots column: the recipe is the declaration, one place (tenet 7) — and refresh resolves through them: a team member re-derives its effective def from the CURRENT team via `teams::effective_def`, with the roster reconstructed from the sibling recipes in the workspace (the recipes ARE the declaration of which window carries which member; a sibling without one falls back to its member name, exactly the name spawn would have used). A def or team deleted after the spawn degrades soft — the spawn-time materials keep working, logged once per window — and pre-#113 recipes keep the old window-name lookup.

**A relaunch line is sourced, never burst, and every prompt is a file** (owner, 2026-09-08: "codex 重启好像有点问题…能类似 kiro 那样一个文件注入吗", then "类似的 Claude omp grok 是不是也是这种文件形式的"). Two halves of one incident: codex's prompt rode the launch line as a ~6 KB `-c developer_instructions=…` override, and the restart replay (`reconcile::run_slot_command`) typed that line with send-keys — tty shims mangle bursts ≳2KB (team/launch.rs), so the pane filled with prompt fragments. Now (a) every backend takes the prompt as a FILE in its isolated home: kiro's agent-config `prompt`, codex's `CODEX_HOME/AGENTS.md` (its native global-instructions file — ours to write because the home is isolated; config.toml there is a SYMLINK into the user's real home and must never carry our text), claude's `CLAUDE.md` in the isolated CLAUDE_CONFIG_DIR (verified live: a relocated dir's CLAUDE.md is read and obeyed), grok's `agents/<name>.md`, omp's `--append-system-prompt <file path>` — with tests pinning the codex and claude launch lines under 2 000 bytes; and (b) managed agent relaunches stage the line as a script in the agent's home and source it (`stage_relaunch_script`), exactly like spawn. Windows without an isolated home keep the direct send: their generic launch lines are short.

**Restart touches ONE agent** (owner, 2026-09-20: "对于已经停止的 agent，我 resume 的时候好像把当前 project 所有的已停止的 agent 都 resume 了", board #210). `hub_agent_restart` used to relaunch through the project-wide `projects::up`, which by design brings up EVERY missing settled slot — so restarting one stopped agent silently resumed every other stopped agent in the project. It now calls `projects::up_agent(project, window_name)`, which runs `reconcile::create_or_keep` for that slot alone: the same code `up` runs per slot (slot cwd, hooks refresh, `relaunch_line` with the slot's exact `agent_session_id`, staged script), so a targeted restart still resumes the exact conversation rather than a degraded `--resume`. `up_agent` does not stamp `last_up_at` (it is not a project `up`). When the slot is not in the store yet (a window younger than the capture loop's settle rule) or its window cannot be created, the fallback is a single fresh launch of that one agent in its own window and home — `spawn::respawn`, which starts what the WINDOW's recipe says (board #389, validator on #383's SHIP, 2026-10-15). It first asked the registry for the window name, which names a definition only for the first agent of its kind: a fork (`kiro-2`), a uniquified hire and a team member are not in the registry under their window names, so a restart inside the first two minutes answered "no agent named 'kiro-2' in the registry" after it had already killed the window, and the agent was gone until the slot settled. Now the definition is `effective_def` (the one resolver a refresh replays and a fork copies): a solo agent is launched by its recipe's `agent_def`, a team member by its team's definition with its own member slot, a fork of a member by the member's definition as a joined agent, a pre-#113 recipe by its window name; the spawner and the team are kept, and a definition that has been deleted refuses by name with the home kept. *The recipe is read, planned from and written inside ONE hold of the home's recipe section* (reviewer P1 on the first cut, which planned from `recipe_provenance`, a reader that takes no section, and wrote those values back: a team move that committed in between was undone, `team` back to the old team while `team_rev`/`team_told` described the new one — the read-before-lock class #384 closed for the writers). `respawn_materialize` enters the section, reads the recipe, resolves the definition from that read and materializes under the same hold, then releases it BEFORE `launch_window` opens the window: a move that commits meanwhile is waited for and kept, and the lock is not held across the slow tmux launch. Only a MISSING recipe (`read` → `Ok(None)`, a pre-#113 home) may be started by its window name; one that exists but cannot be read (malformed, an I/O error) refuses before anything is rendered or written — `Err`, not "absent" — because asking the registry for the window name there would rebuild the agent from whatever other definition carries that name. ### Fork: a new agent from a running one's effective definition (board #383, 2026-10-15)

Owner (#336 (b)): starting a new agent should have a fork mode — copy a running agent's configuration, no other parameters. `tmm agent fork <name> [--as <new>]` and the card's Fork item are one verb on one RPC (`hub_agent_fork`), and it launches through `spawn::spawn`, the one launcher (no second one: cap, model validation, home materialization, hooks are all the spawn's own).

*What is copied is a DEFINITION.* `spawn::effective_def` is the one function for "what definition is this running window", extracted from `refresh_agent` so a restart and a fork read the same thing through the same recipe provenance (board #113): a team member re-derives from the current team (base + role block), a registry spawn follows `agent_def`, a pre-#113 recipe falls back to the window name. So backend, model, effort, input mode, system prompt, skills and MCP come with it. A model or effort someone switched by hand inside the live CLI is NOT copied: it is declared nowhere, and declaration is truth (tenet 7).

*Nothing else travels.* The fork gets a fresh isolated home and a fresh conversation (`resume: false`, a launch line without `--resume`/`--resume-id`; never another agent's session, #379). The source's home — conversations, credentials — is never read as a fallback either: when the definition behind the source is gone (its agent or team was deleted) the fork is REFUSED, because a home holds a conversation and credentials, not a definition. The source is only read.

*Refusals, by name:* not an agent this app started; not running (a fork copies a running agent — start it first); definition deleted; the project at the spawn cap; an explicit `--as` that is invalid, empty, not a string or taken (an absent or null `as` is "not given", `tmm agent fork x --as` with no value is refused). The default name is the source's, uniquified (`reviewer` → `reviewer-2`) past every live window AND every existing home — a stopped agent's home is never clobbered — while an explicit name is used as given or refused, never silently changed.

*A new identity is claimed in the ONE launcher, by every caller* (reviewer P1-A, two rounds). Picking a name from a snapshot of windows and handing it to `spawn` let two forks of one source — two CLIs, two pages — choose `dev-2` together and write one home: two processes on one identity and one session directory (`connection.rs` runs hub requests concurrently, and `tmux new-window` does not keep names unique). The first fix made the fork's name check and home creation one step, but only between forks: a plain `hub_spawn(dev)` read the live panes, saw no `dev-2`, and took the home a fork had already claimed, and a failed fork could delete what the other request had begun to write. Now `spawn` itself reserves every NEW identity — a hire, a team member, a join, a fork — in one process-wide in-flight set (`reserve_name`, `Claim`): an automatic name steps past live windows AND names in flight, an explicit one that another request is creating is refused ("being created by another request"), and the reservation lives until the spawn returns. A fork additionally claims its home directory EXCLUSIVELY (`claim_first`: `create_dir` fails if it exists, under the same set), because a fork must never reuse a home: an auto name that collides picks the next, an explicit one is refused, and a directory that cannot be inspected or created is "cannot tell", which refuses and never reads as free. The claim is an owned `Claim` that travels in the `SpawnRequest`; dropped after a failed launch it gives back its name and removes its home with `remove_dir`, which REFUSES a directory that is not empty — material another request wrote there is never deleted on its behalf (the first cut deleted a home for lacking a `launch.json`, which proved nothing about who was writing); a launch that worked `commit`s and keeps the home. Deliberately not changed: an ordinary hire or a `tmm spawn --team` whose name already has a STOPPED slot of its own still starts it again in its own home, as it always has, and a restart or refresh reuses its OWN home — making those refuse an existing home would break starting a stopped team again, so the exclusive create belongs to the fork, whose whole point is a new identity. "Its own" is defined by the home's recipe and nothing else (`may_start_in`): the same registry def for a hire, the same team path and member for a team member; another agent's home, a fork's, a directory with no recipe yet, and a home that cannot be inspected ("cannot tell") are not.

*The handover from "being created" to "running"* (round 3). The name was decided inside the allocation lock, but from the windows read when the request began: a hire that read the panes just before a fork finished saw no `dev-2`, and once the fork's reservation was released (its window was open by then, but the stale list did not know) it picked `dev-2` and wrote into the fork's running home; a team spawn that planned `dev-2` for a member up front was accepted without any check against the windows at all. Now the allocation reads the windows AGAIN inside its lock (`live_now`, a fresh read of the windows): an automatic name skips what is live, in flight, or a home that is not the request's own slot; an explicit name is accepted only if it is not live, not in flight and not someone else's home — otherwise the request is refused and a team spawn reports that member, nothing is written over. The reservation is held until `spawn` returns, which is after the window exists, so a finished request hands its name to "live", never to "free"; and a failed claim removes its own EMPTY home BEFORE its name leaves the in-flight set, in the same critical section, so a request that reserves the name the instant it is released cannot reach the old directory just before it is removed from under it. Pinned by `…a_late_ordinary_spawn_skips_a_fork_that_has_completed_and_is_running` (timing 1, with the stale read that was the bug shown to reuse the fork's home), `…a_team_member_whose_planned_name_a_fork_took_is_refused_but_its_own_stopped_slot_is_started` (timing 2), `…a_home_is_the_requests_own_only_when_its_recipe_says_so` and `…an_old_claims_cleanup_finishes_before_a_new_claim_can_use_the_name` (200 rounds at a barrier). Pinned with two threads at a barrier on the same candidates (fork vs fork, and a fork vs an ordinary spawn, 30 rounds), a fork claim HELD while a hire gets the next name and an explicit team-spawn name is refused, a dropped claim that removes only an empty home it made, a home appearing after the candidates were chosen (bytes untouched) and an unreadable homes directory.

*An unanswered tmux is "cannot tell", never "nothing running"* (round 4). The fresh read inside the lock still turned a FAILED `list-panes` into an empty list (`unwrap_or_default`): if tmux hiccuped for that one call, a running `dev` whose recipe was the request's own looked like a stopped slot, its home was rewritten and a second window opened under its name; a fork's `--as` could equally land on a live shell window that has no home. "No windows" is now an answer only when tmux GIVES it: an empty list, or tmux saying the session does not exist (`tmux::session_confirmed_absent` — the project's session is not up yet, and the first spawn creates it, so that case must still start). Every other failure — a socket it may not open, tmux not run, words we do not recognise — is `Err`, and `reserve_name` / `claim_first` / `plan_fork_with` take `Fn() -> Result<Vec<String>, String>` and refuse with "could not ask tmux which agents are running (…); nothing was started, try again" BEFORE anything is reserved or any directory touched (`claim_first` reads before it even creates `.tmm/agents`). It is one read for the whole launcher — `panes_now` / `window_names_now`, the only `list_panes` call in `spawn.rs` — so the cap, the allocation, a team's plan and a team spawn cannot disagree about what a failure means (a source pin counts the calls). Pinned by `…only_an_answer_from_tmux_is_a_list_of_windows_and_everything_else_is_cannot_tell` (empty and confirmed-absent are empty; four unanswered kinds refuse), `…a_failed_live_read_refuses_every_allocation_and_touches_nothing` (the running home byte for byte, no reservation, no home, a workspace never used stays absent; an empty answer still starts), `…a_fork_whose_allocation_read_fails_claims_nothing` and `…the_launcher_reads_the_windows_only_through_the_one_honest_read`.

*The source is found by the source's name; the new prompt is written for the new one* (reviewer P1-B). `effective_def` takes the window name for two different things — finding a pre-#113 recipe's definition (the recipe names none, so the window name IS the def name) and the identity a team member's block is written for. A fork resolves with the SOURCE name and sets the new name afterwards: resolving with the new name reported "definition deleted" for a healthy `dev` whose fork `dev-2` is not in the registry.

*Team.* A fork of a team member JOINS the source's team: the recipe records the team ROOT (what a join records, #382) with an EMPTY `member` and `from_member` = `<team path>/<member>` naming the definition (a nested team's path is part of finding the member). It is not a second holder of the member's slot, because the team's roster is built from `(team, member) → window` over the recipes and a duplicate would make the roster point at either window by directory order; as a joined agent a team restart leaves it alone and a team stop includes it (board #382). It goes through the join's own machinery and not around it: `spawn` runs `check_join` for any request naming a team, `materialize` appends the ONE joined team block (`teams::joined_block`: the team, its current teammates with their roles, "you joined"), and `hub_agent_fork` types the join notice to the team's live members with the same `tell_team_of_join` a `hub_spawn --join` uses, the room line adding "— joined team t". The fork's own definition therefore carries the member's base, overrides, role, the enclosing teams' briefs and — for a member of a SUB-team — that sub-team's own description (the rules of the team it actually works in, one line, `description_of` being the one rule for what a team's text is, shared with the member's own block and the joiner's) but NO team section (`teams::forked_def`; `effective_def`'s block would be a second one, and a test pins the count at one). `from_member` is how its restart re-derives the member's CURRENT definition without taking the slot (`fork_member_def`), and how a fork of the fork finds it. A fork of a solo agent is launched by the registry def's name, so its recipe keeps `agent_def` and its restart follows the registry.

*UI.* One item, Fork (zh 复制一个: "fork" means nothing to someone who does not use git; the room line still says "forked x from y"), in `agentItems` — the one list the card menu, right-click and long-press share — for a running managed agent only, after Config and before Interrupt. One tap, no dialog, no confirmation: it cuts nothing and costs nothing until the new agent is given a task. Pinned by `spawn::tests::a_fork_of_a_solo_agent_launches_its_def_in_a_fresh_home`, `…a_fork_of_a_team_member_copies_its_def_and_joins_the_team_without_its_slot`, `…a_fork_of_a_nested_team_member_joins_the_root_and_keeps_the_member_path`, `…two_forks_that_reach_the_same_candidate_get_different_names_and_homes`, `…a_fork_and_an_ordinary_spawn_reaching_for_the_same_name_never_share_it`, `…a_claim_that_is_dropped_removes_only_an_empty_home_it_made`, `…a_home_that_appears_after_the_plan_survives_and_an_unreadable_homes_dir_refuses`, `…a_fork_of_a_pre_113_agent_finds_its_def_by_the_source_name_and_renders_the_new_one`, `…a_nested_fork_keeps_the_sub_teams_rules_and_has_one_team_section`, the `fork_as` tests (RPC and CLI), the `forked` lifecycle line in `hub.test.ts` (`sysParts`/`sysVerbColor`, the same vocabulary as `spawned`) and `…a_fork_is_refused_for_a_stopped_unknown_or_defless_source_and_names_are_never_clobbered`.

### Backend knowledge lives in one file per backend, behind one enum (board #101, 2026-09-09)

Six CLIs genuinely differ — configuration, hook dialect, status line, resume flags — and the owner's ruling is that the differences are legitimate; the defect was their ownership. ### A CLI's painted shape is matched by its structure, never by a fixed prefix (board #346, 2026-10-12)

`kiro::live_input_mode` read the pane with two `strip_prefix` calls, and kiro-cli 2.28.0 invalidated both at once: the Ctrl+S confirmation's bullet changed glyph (`●` → `•`) and the busy footer gained an elapsed segment. Both evidence paths went blind, so `switch_input_mode` pressed the key, watched a pane that HAD switched, and failed after 3 s with "the pane did not confirm steer mode" — the frontend then believed one mode while the pane ran the other, which is what the owner hit while agents were working.

A fixed prefix asserts every byte before the part that matters, so any repaint breaks it, and it breaks it SILENTLY: the matcher returns `None`, which is also what an idle pane legitimately returns. So a painted line is matched by the structure that carries the meaning — for the confirmation, a column-zero line of one bullet glyph from a named set plus exactly `Switched to <Mode> mode`; for the footer, the label at column zero and then the words after `· Type to ` and `· Ctrl+S to ` read as segments. The boundaries that keep the reading honest are kept as deliberately: column zero (an indented copy under a chat stamp or a tool head is someone quoting us), a closed bullet set rather than "any glyph" (the stamps `›`/`>` carry what was TYPED, and a delivery can quote the sentence verbatim; a new glyph is added to the set with the version that painted it), whole words rather than "the line mentions steer", and a footer that offers the mode it is already in treated as no answer. Every fixture carries the kiro version it was captured on, both builds' bytes side by side, and the capture command — a pane pasted into a note is not evidence a later reader can check.

**The same cause had a second reader (board #361, 2026-10-14).** `kiro::high_traffic` did `strip_prefix("● ")`, so kiro-cli 2.28's `• claude-fable-5.1 is experiencing high traffic. …` was never a hit and the auto-recovery of `recovery.rs` (last fired 10-11 01:36) was silent for every stop since the upgrade: 49 real blocks in nine panes' scrollbacks, all `•`, none `●`, each an agent that sat stalled until a person typed. ### The app owns managed agent configs, and drift is repaired at every start (moved from tmm-cli.md, board #102)

Hooks are how we observe an agent at all, so a config on disk must never be older than the build reading its events — agents spawned before `userPromptSubmit` existed kept a three-hook config, so deliveries had no receipt and the reply edge could not find its requester. `spawn::refresh_hooks(project_path, window_name)` rewrites the `hooks` key in place (kiro `agents/<name>.json`, claude `settings.json`, codex `codex/hooks.json`, grok `hooks/tmux-mobile.json`) and nothing else — the prompt carries the brief given once at spawn and cannot be rebuilt; it is a no-op when current and runs on EVERY start (`hub_agent_restart`, `reconcile` on project up). Each backend's hook set lives in ONE function (`kiro_hooks`/`claude_hooks`/`codex_hooks`/`grok_hooks`), shared by render and refresh so the two cannot disagree. Settings drift is the same disease: `kiro_cli_settings` is the canonical `settings/cli.json` content (`chat.disableTrustAllConfirmation=true` — an agent has nobody at its keyboard; plus the toolSearch keys above), written fail-loud at spawn, backfilled fail-soft on every start, and a key the app does not own survives untouched. A CLI reads its config at LAUNCH, so patching a file never repairs a running agent — restart is the only path, which is what the roster's restart button is for.

### The kiro backend on kiro-cli 2.22.1: one 3.0 profile for both engines, and the v3 door is the workspace (board #207, 2026-09-20)

Owner: "kiro 后续升级了 kiro-cli --v3 版本，你来帮我看一下后端是否都能用，各种配置以及参数兼容性，
以及一些状态嗅探等 … 保证我们顺利迁移". kiro-cli 2.22.1 ships two agent engines —
`--agent-engine v2` (its default and ours) and `v3` (KAS 0.66.4, the "next
generation Kiro agent") — and a 3.0 profile format. Everything below was
measured on private `KIRO_HOME`s and private tmux sockets; no running agent
was touched.

- **The profile is the 3.0 shape, for both engines.** `kiro_hooks()` emits an
  ARRAY of named hooks (`{name, trigger, action:{type:"command", command},
  timeout}`; our tool hooks carry no `matcher` — a bare `"*"` made the 3.0
  profile invalid, "agent not found", while no matcher means every tool) and
  the profile carries `permissions.rules = [{capability:"all", effect:"allow"}]`.
  The v2 engine accepts this shape and fires all four hooks (measured:
  userPromptSubmit, preToolUse, postToolUse, stop). `patch_profile` replaces
  the 2.0 object with the array and adds `permissions` only when absent;
  idempotent on both shapes. Why it matters: with
  `chat.enableAutoAgentUpgrade=true` (below) the CLI rewrites every 2.0 profile
  it finds to 3.0 and leaves a `.bak` beside it — writing 3.0 ourselves means
  the upgrade never runs on our homes. Measured: two `--agent-engine v3` starts
  on our profile, no `.bak`, byte-identical file.
- **Home settings** (`kiro_cli_settings`) gain `chat.enableAutoAgentUpgrade =
  true` — without it v3 parks an unattended pane on "Your agent configs are
  still in the 2.0 format. Upgrade?" — and `chat.defaultModel = <def.model>`:
  **v3 IGNORES the profile's `model`** and reads this key (or `--model`). The
  profile keeps `model` for v2; `ensure_kiro_settings(home, model)` mirrors the
  profile's model at every refresh, OMITS the key when the model is empty and
  DELETES a stale one when the model is cleared, so an old pin cannot outlive
  the config. The model still lives in CONFIG, never on the launch line.
  An unpinned model is the user's own `chat.defaultModel`, and `chat.agentEngine`
  is always the door's (§ A managed kiro forks the user's settings, 2026-11-04).
- **The engine door is one app-wide key**: `kiro_engine = "v2" | "v3"` in
  `config.toml` (`KIRO_ENGINE` overrides; default v2; anything else is v2 with
  a note). `render_kiro` appends ` --agent-engine v3 --trust-workspace` to the
  launch line only when the door is open — v2 is byte-for-byte what it was —
  and `refresh` reconciles the recorded `launch.json` at every start
  (`reconcile_engine_in`: add / replace / drop the segment), so an agent takes
  the new engine at its NEXT restart and one scratch agent can be flipped by
  restarting it alone. No per-agent field: that would be a schema and editor
  change nobody asked for.
- **The v3 trust menu is answered on the launch line** (board #487, owner
  2026-11-01: "好多session重启遇到问题了"). kiro-cli 2.34.0's v3 engine opens
  with "Trust this workspace? ❯ Trust, continue / Don't trust, exit" whenever
  the isolated `KIRO_HOME` has no `workspace-roots/<hash>/permissions.yaml`
  with `workspaceTrusted`, so a restored or relaunched agent whose home had
  never answered it sat on the menu until a human pressed Enter (the
  validator here, kiro-3 in sound-factory). Same class as #183 (Midway y/N)
  and #184 (codex's trust screen), and the same answer: the CLI's documented
  door, `--trust-workspace` ("Skip the Trust this workspace? prompt for this
  launch only (V3 only)"), rides in the engine segment, so it is on every v3
  line and never on a v2 one. The same reconcile brings it into a v3
  `launch.json` written before #487 at that agent's next start, right after
  the engine value; on a backfilled line the whole engine segment sits before
  the trailing `kick` (`… --agent-engine v3 --trust-workspace kick`), the one
  order every generated shape uses. That is order unification, not a parsing
  fix: 2.34.0 also skips the menu with the flags after `kick`, and `kick` is
  still the first input either way (validator, real panes). The fix depends on
  `chat.disableTrustAllConfirmation=true` staying in `kiro_cli_settings`:
  without it, a fresh home gets past the trust menu and stops on a second
  screen, "Warning: Kiro is running in trust all tools mode" (default
  `❯ No, exit`). A managed home has the setting from spawn, and
  `ensure_kiro_settings` restores it at every start. We do not
  seed `permissions.yaml`: the hash and the file are kiro's. Measured on 2.34.0, real panes, fresh homes
  with no `workspace-roots`: without the flag the menu; with it, the prompt
  `›  ask a question or describe a task`, and no `permissions.yaml` trust
  record (`workspaceTrusted`) was written, so the choice applies to that
  launch only. Other writes to the home were not part of the measurement.
- **v3 finds the agent through the WORKSPACE, not `KIRO_HOME`** — the finding
  that changed the plan. With a private home, the same profile was "agent
  … not found, using default" under any other name and from any other cwd,
  and found the moment it sat in `<cwd>/.kiro/agents/`; the earlier "works"
  reading came from a copy that had been dropped there. `KIRO_HOME` still
  supplies the settings (`chat.defaultModel` was honoured). So, only while the
  door is open, `ensure_workspace_entry` puts ONE symlink per managed agent at
  `<ws>/.kiro/agents/<name>.json` → `<ws>/.tmm/agents/<name>/agents/<name>.json`
  — the isolated home stays the single truth, v3 reads through the link;
  idempotent on every start; a file there that is NOT our link is never
  clobbered (spawn fails loud naming it; refresh logs); the link is removed
  with the agent (`agent_remove`) and when the door closes; OUR FILE's path
  (`/.kiro/agents/<name>.json`, one line per agent under one mark) goes into
  `.git/info/exclude` (local, untracked, idempotent) so an agent's `git add
  -A` cannot commit it — never the whole directory, which would hide the
  user's own agents from their `git status`. Measured: v3 follows the link (found, session

  `sess_<uuid>`, and **where they live depends on the kiro-cli build**: the

### The dsh backend: DeepSeek Harness 0.2.0-rc.2, an idle shell and one resumed turn per line (board #404, 2026-10-16)

The owner asked for DeepSeek Harness as an agent and chose the shape himself (10-16 10:51: "dsh 空的 shell 就行，你发送消息，相当于启动一个命令任务，并且恢复 session。结束后就空在 terminal 在那里"). dsh (`npm i -g @deepseek-ai/dsh`, bin `dsh`) ships web, desktop, headless, acp and sdk front ends and NO interactive terminal UI; the community TUIs are third-party plugins running inside the harness with its key, so we do not depend on one. Measured on 0.2.0-rc.2 in a scratch `DSH_HOME` and a scratch tmux session; dsh is a developer preview with announced breaking changes, so every fact below names that version.

**The pane is a shell, and a line is a command.** The launch line is `exec zsh -i` with `ZDOTDIR=<home>/zsh`: spawn SOURCES the launch script into the pane's own ordinary shell, and `exec` makes the managed zsh REPLACE it — the managed zsh is the pane's process (`#{pane_pid}`), and when it dies, however it dies (SIGKILL included), the pane dies with it: no ordinary shell is left for a chat line to fall through to (review P1-A2; `VAR=x exec cmd` exports the launch env in bash, zsh and sh, measured; pinned through the production launcher by `the_pane_ends_with_its_managed_shell_and_its_stale_ready_file_is_not_believed`); the rendered `.zshenv` turns off the system rc files and the rendered `.zshrc` IS the agent's front end: prompt `dsh › `, and an `accept-line` widget that turns a non-empty line into ONE visible command, `dsh --profile tmm [--session-id <id>] -- ${(q+)BUFFER}`. zsh quotes the buffer itself, so the text is never parsed as shell; `--` keeps a line that starts with `-` a task. A line that starts with `!` runs as a plain shell command — a person's way out, and the only one. Delivery is unchanged (tenet 9: one mechanism): it types or pastes the line and presses Enter like everywhere else, and a person typing into the pane does exactly what an agent's delivery does. Pinned by `a_delivered_line_is_one_quoted_argument_and_nothing_in_it_runs`, which runs the real `.zshrc` with a fake `dsh` in a scratch tmux pane through `tmux::send_command`: `' " $HOME` backticks `$(…) ; & | >`, a newline, a tab, `-n …` and `--help` all reach argv byte-exact and no canary file is created; a `!` line runs and starts no turn. Tab is bound to `self-insert` (a typed tab would otherwise run completion), and history expansion is off.

**One turn per run, one session per agent.** `dsh --profile <p> [--session-id <id>] -- <task>` runs one turn and exits; `--session-id` resumes exactly (the next turn answered from the previous one's context), an unknown id fails at once with no request. The plugin records the session id in `<home>/dsh/tmm/session`; the widget resumes it only if `sessions/*/<id>/` exists. The recipe's resume dialect is an env var the shell reads at start (`resume_command`): unset = a fresh conversation, `TMM_DSH_SESSION=recent` = keep the recorded one, `TMM_DSH_SESSION=<id>` = that one (a non-`session-…` value is refused). Each run cold-starts the harness (~1.7 s before the request).

**Isolation**: `DSH_HOME=<home>/dsh` relocates everything (profiles, sessions, storages, credentials, the user-global `AGENTS.md`); `DSH_AGENTS_HOME` points at the same directory so the user's `~/.agents/AGENTS.md` stays out (dsh-agent-instructions reads `$DSH_HOME/AGENTS.md`, then `$DSH_AGENTS_HOME/AGENTS.md`; identical files collapse). The prompt is `$DSH_HOME/AGENTS.md`. The profile `tmm` is four files written by `render_dsh` in the shipped headless template's shape (package.json naming `dsh-base` + `dsh-headless`, pnpm-workspace.yaml, an empty cordis.yml, cordis.patch.yml). The patch holds the model — `agent-default-model {provider: deepseek-official, model, reasoningEffort}`, model empty = the route's shipped `deepseek-flash`, effort one of `off|low|high|max` (the route's levels) — so nothing about the model is on the launch line; it also mounts the plugin, disables `session-title-llm` (an extra model request on every first prompt), and turns off the two request fields below (#408). **Native MCP and skills** (board #412, measured on 0.2.0-rc.2 with the real dsh against a loopback stand-in for the Messages API and a stdio echo server, zero model calls). The definition's MCP servers (`spawn::mcp_defs`, the ones kiro and claude get natively) are rendered as `dsh-mcp-client` rows in the patch's insert list (`mcp_rows`): stdio `command`/`args`/`env`, remote `streamable-http` `url`/`headers`; a value naming a variable (`${VAR}`, `$VAR`, `Bearer ${VAR}`) is read at launch (`!!js process.env.VAR`, the name validated as an identifier), every other value is a literal. The model sees each tool as `mcp__<server>__<tool>`. What dsh cannot express is refused at render, never guessed: a server name outside `[A-Za-z0-9_-]{1,32}`, or a server with neither a command nor a url. dsh scrubs ambient variables whose names contain KEY/PASSWORD/SECRET/TOKEN, and every ambient `DSH_*`, from a stdio server's environment, so a secret a server needs must be named in its `env` (a reference there is read in the dsh process, which still has it). Skills: the agent's own root `$DSH_HOME/tmm/skills` holds one link per skill of its definition, rebuilt at every render, and `skill-filesystem` scans it alone (`customSkillDirs`, `includeDefaultRoots: false`, `watch: false`: the owner's `~/.agents/skills`, the project's `.agents/skills` and dsh's bundled skills stay out, the AGENTS.md rule). dsh announces them in its own session catalog and loads them with its `skill` tool, so the prompt carries no second index (one mechanism). **Why the provider does not watch** (board #426, 2026-10-19, measured on 0.2.0-rc.2, the same binary that passed on 10-18): `dsh-tool-skill` emits the catalog only when `ctx.skills.snapshot()` is COMPLETE, and `skill-filesystem` starts a file watcher (an inotify instance) in every `list()`; when it cannot (`EMFILE`: this host's per-user limit is `fs.inotify.max_user_instances` = 128 and dozens of agents share it) the observation is incomplete and the model gets NO catalog, in every step of the run, while the `skill` tool still loads the skill by name. That is how the real-dsh test lost its catalog while nothing in dsh or our profile had changed (it failed alone, deterministically, for as long as the host was near the limit). The trade is real, not free: `dsh-skill` caches the complete catalog per revision and the watcher is what invalidates it when a skill directory changes under a RUNNING process, so `watch: false` drops that in-process invalidation (the native `fs/observed` invalidation and `skill` reading a skill's body directly stay). It is accepted because this integration runs ONE dsh process per turn: the next turn discovers the skills afresh, and the set of links itself (`$DSH_HOME/tmm/skills`) only changes at a full render or restart; within one long run an external edit of a skill's summary may keep the old catalog until the next turn. In exchange the catalog no longer depends on a host resource. (A healthy watcher is reused, `list()` only ensures one exists; it is a failure to start one that matters.) The patch now says `watch: false`. **Scope**: the line is in `profile_patch_yml`'s output, so a home gets it when its patch is rewritten (a spawn, a restart, or a model/effort change through `write_live_config`); merging the code or restarting the gateway does not by itself rewrite an existing home's profile. Pinned by the profile text test and by the real-dsh test, which asserts the catalog in the FIRST request. Each SKILL.md is checked against a validated subset mirroring dsh's `parseSkillFile` (`dsh_skill_name`; not a copy of its parser, so YAML edge cases can still differ): a `---` frontmatter mapping with an explicit `name` (dsh never falls back to the folder name) and `description`, the name in its lowercase rule, no legacy invocation keys, boolean invocation fields; a skill dsh would skip is refused with the reason and never rewritten, and its link is named by that frontmatter name. Pinned by `mcp_servers_render_as_native_dsh_rows_and_odd_ones_are_refused`, `the_skill_root_is_the_definitions_skills_and_odd_ones_are_refused` (revocation leaves no link, dangling or not; a SKILL.md without a name, with a bad name, a legacy key or a non-boolean policy is refused) and `the_managed_profile_gives_dsh_native_mcp_tools_and_skills` (a stdio and a Streamable HTTP server: both tools in the request, calls reaching both servers and their results coming back; an env and a header reference read from the launch env, and a `!!js`-looking literal with quotes and a newline arriving byte for byte; the skill in the catalog and its body loaded; a default-root skill absent). `tmm mcp` stays available as a skill, as for every backend. **Not seeded**: the six registry defaults stay as they are; a dsh agent is a definition someone saves (a default `dsh` agent is the owner's decision, orchestrator ruling 10-16).

**Owned files**: every file above, the plugin and both zsh files are rewritten through `shared::write_owned` at every render; `refresh` rewrites the plugin and the shell whenever this build's text differs (omp's rule for a generated file) and leaves a home without the `tmm` profile alone. Runtime state (`tmm/session`, `tmm/open`, `tmm/stop.json`, `sessions/`) is the harness's and the shell's, never rendered.

**Auth is the environment only.** The deepseek-official route reads `DEEPSEEK_API_KEY`, which the pane inherits from the interactive shell that launched it; no key is written into a home, a recipe or a test. A key the owner saved through the web UI lives in `~/.dsh/.credentials.yaml` and is NOT visible in an isolated home. With the variable unset, the plugin (config `requireEnv: DEEPSEEK_API_KEY`) reports the prompt, writes the turn's Stop as an error, prints ONE line — `DEEPSEEK_API_KEY is not set` — and exits before any request: the turn is recorded as failed at once (measured live; pinned by `a_missing_key_fails_the_turn_at_once_with_one_line`).

**Unattended, and no wider than the others.** headless has no channel to ask for an approval (measured: under `ask` the model gave up on an out-of-workspace write), so the launch env sets `DSH_PERMISSION_MODE=danger-full-access`, the shipped config's own switch for sandbox mode and approval policy `never`. The other managed backends already run that way: kiro `--trust-all-tools`, claude `--dangerously-skip-permissions`, codex `--dangerously-bypass-approvals-and-sandbox`, grok `--always-approve`, omp `--auto-approve`, kimi `--auto` (Never Ask, `default_permission_mode = "auto"`). Plainly: `danger-full-access` means no sandbox and no approvals, exactly as wide as claude's `--dangerously-skip-permissions` and codex's `--dangerously-bypass-approvals-and-sandbox`, and no wider than any of them.

**Only the model request leaves the machine** (board #408, 2026-10-16; measured on 0.2.0-rc.2 against a loopback stand-in for the Messages API, zero model calls). By default dsh adds two fields, outside model input, to every request to the DeepSeek API: `dsh_session_log` (`session-log-deepseek`: the session's events since the last accepted request, its header with the cwd, every tool result) and `dsh_plugin_packages` (`plugin-package-inventory-deepseek`: the active plugin packages). A managed agent would ship the operator's tool output to DeepSeek beyond what the model needs, so the managed profile patch sets `enabled: false` on both rows. Separately, OTel session telemetry (`session-telemetry-otel`, default `FEEDBACK_ONLY`: a session-log prefix to `dsh-otel-collector.deepseeksvc.com` after explicit user feedback) is removed by `DSH_TELEMETRY_DISABLED=1` in the launch env, dsh's documented opt-out (any non-empty value removes the row); it replaces the earlier `DSH_TELEMETRY_MODE=DISABLED`, one switch for one job (kimi's `telemetry = false`). Pinned by `the_managed_profile_sends_the_model_request_only`: the real dsh on the rendered profile sends ONE request (the title request is off too), with neither field; the shipped headless profile sends both, plus a title request. What still goes with each request is dsh's attribution: headers `x-deepseek-harness-user-id` (a random UUID per harness home, `$DSH_HOME/.anonymous-user-id`, so per managed agent; no switch) and `x-deepseek-harness-session-id`.

**The plugin, and why its name is fixed.** `<home>/dsh/plugins/tmm-telemetry/{package.json,index.mjs}` is mounted by absolute path (`- insert: [{id, name, config}]`). It sits in a directory whose package.json has a name and a version: with the plugin inventory on, the deepseek-official route fails every request with `REQUEST_EXTENSION` otherwise (measured both ways). The managed profile turns that inventory off (#408), and the identity stays fixed and neutral anyway — `tmm-telemetry` `1.0.0`, no workspace path, no agent name — so a profile that turns it back on still leaks nothing about the agent. The plugin listens to `session/event (session, ev)` for the agent's OWN session only: the first ROOT session the run sees (its header has no `parentSession` and no `origin: "subagent"`), and every later event is checked against it. dsh-base mounts in-process subagent spawn and fork by default, and their sessions emit the same events at profile root — a child's prompt, reply or `turn/end` never becomes the window's (review P1-B; dsh-headless's own json stream filters `session !== agent.session` the same way; pinned by `a_subagent_session_never_becomes_the_windows_turn`, a child seen first, a child ending before the root is interrupted, and a child event after the root ended). For the root: the first user-sourced `user/message` of a turn → `UserPromptSubmit {prompt}` (and a `tmm/prompted` mark); `tool/call` → `PreToolUse {tool_name, tool_input}`; `tool/result` → `PostToolUse`; the last `assistant/message` with text (reasoning parts are not the reply) is kept, and `turn/end` WRITES `{Stop, last_assistant_message, dsh_reason}` to `tmm/stop.json`. Payloads use claude's keys and go to the notify helper; every handler is wrapped so telemetry never breaks a run.

**One writer per run, in dsh's order, and nothing late reopens a turn** (review P1-C). The plugin publishes every envelope SYNCHRONOUSLY (`spawnSync` of the helper, killed after 3 s), in event order, so nothing is in flight when the process ends; the Escape handler runs on the event loop, never inside a publish. The shell publishes its envelopes the same way, bounded: a helper still running after 3 s is killed and the prompt stays usable. Each envelope carries `tmm_seq` (in the payload and as `TMM_HOOK_SEQ` in the inbox file name), a strictly rising microsecond number shared by plugin and shell through `tmm/seq`; the hub keeps a per-window high-water mark and DROPS any envelope not above it — a notifier that outlived its run, a helper killed past its bound and published anyway, a SIGKILLed run's last hook: a late copy can never reopen an ended turn or count as a newer one. An envelope that could not be published within the bound is kept in `tmm/unsent` and sent FIRST, under its own number, by the next publisher (the next run's plugin at start, or the shell), and everything newer waits behind it; so a killed Stop still ends its turn, before the next turn's prompt. Publication is believed only on a RECEIPT (review P1-C2): with `TMM_HOOK_SEQ` set the helper exits 0 only once the envelope is in the inbox and 1 otherwise (no pane, `mkdir`/`mktemp`/write/rename failed) — every other backend's hooks keep the fail-soft exit 0 — and the shell collects that exit status instead of only noticing the process is gone. Both producers write one envelope shape, `{"tmm_seq":<digits>,…}` with the number FIRST, so the shell retries a record the plugin queued. A prompt the plugin queued behind a backlog counts as published (it will be, in order); a prompt it could not publish is reported by the shell. The hub's mark is DURABLE (`meta`, one key per window, `telemetry::hook_mark`), and an envelope is accepted, and leaves the inbox, only once its turn fact, its effects (the reply, the flush) and that mark have all succeeded (review round 5, orchestrator rulings 16:00 and 17:30): a gateway restart cannot let a late copy back in. An unreadable mark, a failed turn-fact INSERT (stopped before any visible effect; a prompt's row and the retirement of its receipts are one transaction), a room post the room refused (retried alone, never the end fact) or a failed mark write keeps the envelope, and the window's later envelopes wait behind it. A crash between the effects and the mark reads the envelope again: the reply reaches the room at least once, not necessarily the requester's pane, the window every backend has (agent-notifications.md § Event Path). Pinned by `dsh_publication_failures_never_reopen_a_turn_or_hang_the_shell` (a prompt publish that fails and lands 4 s later from a surviving child, consumed before and after it; a prompt notifier hanging past the bound; a Stop notifier hanging past the shell's bound) `dsh_publication_receipts_keep_every_terminal_fact` (a shell Stop failing at once; its resend failing again, so the plugin's own prompt queues behind it and the shell retries both, oldest first; the REAL helper unable to write — each terminal fact published once, every turn answered once, its own sender), `the_helpers_exit_is_a_receipt_only_for_a_numbered_producer`, `the_helper_names_a_producers_sequence_and_the_inbox_honours_it`, `dsh_consumption_is_at_least_once_and_never_guesses_a_fence`, `a_numbered_window_waits_behind_its_unaccepted_envelope`, `a_failed_mark_write_keeps_its_envelope_across_a_restart` and `a_room_post_that_failed_is_retried_alone`; the late-copy case also restarts the gateway in between. A notifier that ignores SIGTERM is still bounded: the plugin kills with SIGKILL, the shell sends TERM, waits 10 ms, then KILL (`a_notifier_that_ignores_term_is_still_bounded`). The cost is a few milliseconds of the agent loop per envelope.

**The Stop is sent by the shell, when its prompt is back, exactly once per run.** The `zle-line-init` widget ends the run's turn by its exit status (`precmd` keeps `$?`): the plugin's own `stop.json` when there is one; else exit 130 (Escape, ^C) is an interrupt — `{Stop, dsh_reason: "interrupted"}`, no reply, `completed`; else any end without the plugin's Stop is a FAILED launch — `{Stop, dsh_reason: "error", dsh_exit: N}`, no reply, `failed` (measured: a missing executable is 127, the real dsh with no `tmm` profile exits 1 before any plugin or request). A run that never reported its prompt (it died before the plugin saw it) gets it reported here first, from the line the widget kept (`tmm/line`, JSON-escaped by the shell), so the delivery is acknowledged rather than swept `unconfirmed` (review P2-D; pinned by `every_run_ends_its_turn_once_and_a_failed_launch_is_failed` and `a_missing_dsh_executable_is_a_failed_launch`). Why the shell and not the plugin: held lines are typed on Stop, and typed while dsh still owns the TTY (raw mode, no bracketed paste) they would be swallowed or split into one turn per line — from `zle-line-init` they land in ZLE as one bracketed paste; and a run that was killed or crashed still ends its turn. The reply is the payload's `last_assistant_message`, so the one reply edge (agent-status.md) needs no fallback.

**A typed line reaches the pane only while its shell, or a steer run's reader, says it is ready** (review P1-A; #410). queue|steer is a choice since #410 (`SWITCHES_INPUT_MODE = true`, default `queue`), and `LOSES_BUSY_INPUT = true` in BOTH modes (`Backend::loses_busy_input`): ONE occupancy rule — `delivery::strict_occupied`, asked by the delivery decision and by every flush trigger (the Stop, the feed read, the next delivery, the server start, and the settled prompt of a dsh run) — says the pane is free only while the shell's ready file exists or, in steer mode, the run's reader claims the pane (§ Steer mode below), and dsh never takes the generic busy-steer path (`type_steered`, which owes no echo). The shell half (`Backend::input_ready`: `tmm/ready`, written by the shell once ZLE owns the TTY, removed when a line runs, and naming its owner — the shell's pid — so it is believed only when that pid is the LIVE input owner: alive AND the window's pane process, read from tmux at the moment of the decision; a file a killed shell left behind, or one naming any other process, is never readiness, `a_ready_file_is_believed_only_while_its_owner_lives`. Alive means it exists AND is not a zombie (`owns_input`, board #413), because a zombie still answers signal 0 and can read nothing. The cause of the one failure in 17 runs of `the_pane_ends_with_its_managed_shell_and_its_stale_ready_file_is_not_believed` is INFERRED, not measured: that failure was not captured together with a `Z` state, and a 300-run probe on an isolated socket never caught the window. It is consistent with tmux 3.6a's source, where a pane closes on its pty's EOF as well as on the SIGCHLD that reaps the shell, so the pane can be gone while its killed shell is still unreaped, and with the deterministic zombie fixture. The state is read from `/proc/<pid>/stat`, or from `ps -o stat=` where there is no /proc (macOS, neither built nor run there). `Z`/`X` is not an owner, and an observation that is not clean (ps failed, more or less than one state word, no leading state letter) is unknown, which is not an owner either. Out of scope: a pid reused by a new process, and a shell that dies right after the check. Pinned by the same owner test with a real unreaped child of the test process, and by `a_process_state_is_believed_only_from_a_clean_observation`) and no line typed there has echoed yet. Turn state is never taken for readiness: the hub interrupt ends the turn app-side before the shell is back, a Stop can be lost, and the receipt clock of a line in flight expires — none of them lets a byte into the raw TTY. zsh turns bracketed paste on only AFTER `zle-line-init` returns (measured, zsh 5.9: a paste inside the hook was split into one turn per line), so the ready work runs from a one-shot `zle -F` handler, and the prompt reads `dsh · ` until then and `dsh › ` after: the startup waiter's marker implies the ready file. The overdue release never types into a dsh turn; instead a held line past `HOLD_MAX_SECS` is reported ONCE (`held (the agent has not returned to its prompt): N lines will be typed when it clears`, the copy-mode report's `warned` mark), and stays held. A hold that cannot be written while the pane is occupied is `undelivered (the agent is busy and the line could not be held)`, nothing typed. A shell that finds the previous shell's run still open (the window was killed or the agent restarted mid-turn) ends that turn at its first prompt, as an interrupt. Pinned through production delivery by `a_busy_dsh_turn_holds_through_the_overdue_rule`, `a_failed_hold_for_a_busy_dsh_window_types_nothing`, `a_run_left_open_by_a_dead_shell_is_ended_by_the_next_one`, and end to end — real pane, generated plugin under node, the real helper and inbox, `deliver_chat_line` — by `a_busy_dsh_turn_holds_lines_and_ends_in_order`: a cold-start line and a busy line held across a feed-read flush and typed after the Stop as ONE prompt; the actual hub interrupt path with a line delivered before the shell is back (held, then typed); replies to each turn's own senders. Non-dsh queue backends keep the overdue release (`a_kiro_queue_window_keeps_the_overdue_release`).

**Escape interrupts.** While a run lasts the plugin holds the TTY raw; a lone ESC (what tmux sends for the `Escape` key) or ^C sends SIGINT to the process, dsh's own exit path: measured live in queue mode, back at the prompt in 83 ms, the turn ended with no reply, and the next resumed turn knew it had been interrupted (SIGINT writes no `turn/end`; the shell's Stop covers it). In steer mode a lone ESC is decoded by Node's key decoder, which tells it from the first byte of a sequence only after its escape-code timeout, so the interrupt takes ~500 ms longer; ^C is complete in one byte and stays immediate. Pinned by `escape_interrupts_a_run_through_the_plugin` and `a_steer_run_is_interrupted_by_escape_and_a_lone_hyphen_is_refused`.

**Steer mode** (board #410, design reviewed before code; dsh 0.2.0-rc.2, Node 22). A line typed while the run's root turn is open goes INTO that turn, through dsh's own door: `Agent.steer` puts it in the agent's durable next-step inbox, and the loop takes it at its next step boundary (a step that would end the turn continues with it; one pending after the last step gets one more turn in the same process), as a `user/message` with source `user`. The plugin is that door's only caller and the pane's only reader during a run (dsh-headless reads stdin only for the task `-`, which the shell now refuses with `not sent: a lone '-' is not a message`):
- **Bytes**: the plugin reads the pane raw with bracketed paste on (`ESC[?2004h`, off at exit) and frames it with Node's own key decoder (`readline.emitKeypressEvents`), no parser of ours. A LEDGER around the decoder says whether it is clean: every key's `sequence` must retire exactly the raw bytes at the head of the ledger; a key that does not (a replacement character for an invalid byte) taints the reader for good, and bytes the decoder holds without a key yet (half a sequence, half a character, a lone ESC before its timeout) stay in the ledger. Enter submits outside a paste (CRLF is one Enter), newlines inside a paste are text, a line past 256 KiB is `not sent: line too long`, never cut. The interrupt keys keep their meaning in every state, inside an unfinished paste and in a refused line too (review round 2, P1-C: a paste left open swallowed both, so the app showed the turn ended while dsh ran on): ^C always, and the decoder's lone `escape` (a paste or arrow prefix is never one); any other control byte inside a paste is kept as text (BEL, say), and a decoded escape sequence inside it (`ESC[31m`) is ignored, neither text nor an interrupt. A line with a NUL in it, typed or pasted, is refused whole as `not sent: unsupported control byte` before it is steered or handed off (review P1-A, round 2): NUL frames the hand-off record, and before this `safe<NUL>!touch …` reached the shell as two lines, the second run as a shell escape. What the reader retains is bounded by the same 256 KiB (review P2-B): a tainted ledger stops holding bytes, Node's decoder never holds a long sequence itself (measured: `ESC [` followed by 300 000 digits comes out as a key every few bytes, so an untainted ledger holds at most one short sequence), and the lines a run holds for later (read before its turn opened or after it ended, `makeHold`) share one budget; past it a line is reported not sent and the hand-off is no longer clean, so nothing after a dropped line runs out of order.
- **Admission**: each line becomes a real message from dsh's own factory (`createUserMessage` of dsh-llm, resolved from dsh's install through `realpath(process.argv[1])`: a plugin mounted by path cannot import it by name, measured), passed to the ROOT agent (`ctx.get('agents').roots()`, matched by session). `steer()`'s synchronous return is the hand-over: the pane shows `› steer: <first 80 chars>` with control characters made inert. A throw keeps the line (it goes to the hand-off below), never announced. The echo is best effort and never decides acceptance (`steerOnce`, review P2-A): a steer that returned is never handed to the shell as well.
- **Prompts**: the plugin reports EVERY root `user/message` whose `source.kind` is `user` as `UserPromptSubmit` (the run's first and each steered line); a user-ROLE message with another source (the skills catalog, a skill invocation, runtime context, a plugin's message) never is (`only_user_sourced_root_messages_become_prompts`). The hub then does what it does for any input that joins an open turn: the sender joins the reply edge (#256), and the delivery's receipt settles on the echo (#249). Admission is not a model-read receipt: a message an interrupt clears before it becomes a `user/message` has no echo, and its row is swept `unconfirmed` like any other.
- **Readiness**: the reader writes `tmm/steer-ready` = `<dsh pid> <run> steer` only while the root turn is open, the factory and the root agent are at hand, it owns the TTY raw and it ADMITS a new line (`admits()`: `clean()` — nothing undecoded, a lone ESC may be the hub's interrupt; no paste open; no refused line in progress; never tainted — AND an empty line. Review P1-B, round 2: an open human paste with no byte pending claimed the pane; round 3: so did a person's draft, typed or a paste closed before its Enter, and a hub paste was appended to it and submitted with it. A clean reader may still hold a draft, which is valid to hand back; it only admits nothing. The hub line is held, the person's Enter steers their exact line, and that prompt's own flush steers the hub line on its own), and removes it at the turn's end, at an interrupt and at exit. `Backend::input_ready` believes it only for THIS run of THIS pane: a live owner (`owns_input`) whose parent is the pane's process, the run the shell minted last at its accept-line (`tmm/run`), the mode the reader loaded (`tmm/input_mode`, rendered at spawn and restart, read at the start of each run). One steer is in flight at a time (`line_in_flight`); the next is typed when the previous echo settles, by the new flush trigger that runs after a dsh prompt is consumed and persisted, outside the turn-fact lock. Lines that arrive during the cold start are held, then typed once the run's prompt settled: the reader is whole BEFORE that prompt is published, because `apply` returns a promise that settles once the factory is loaded and dsh awaits a plugin's `apply` before the run's turn opens (measured on 0.2.0-rc.2: a 1.5 s apply delays `turn/start` and the first `user/message` by 1.5 s), so the prompt-settled flush finds the claim (review P1-C, round 2: the factory used to load in the background, and a flush that ran first held the line with no later trigger). A factory that fails to load leaves the run in queue behaviour: no claim, lines held for the Stop. A line held while the claim is withdrawn for a moment (a person's half character, open paste or draft) waits for the next trigger — the next steer's prompt, a feed read, the turn's end — and is never typed into a reader that is not clean. Bytes typed into the cold start anyway (a person) stay in the TTY's input queue across the switch to raw mode and are read then (M3, measured on the real dsh).
- **The hand-off** (orchestrator's ruling: the hub never types into the gap between the root turn's end and the shell's prompt, so this concerns a person, or a delivery that passed the gate as the turn ended). After the root `turn/end` the reader steers nothing more (a steer then could start a turn the process exits under). Complete lines read from then on, and the draft, go to `tmm/handoff` (NUL-separated, written by rename); the process's exit handler writes the FINAL record. The shell's `zle-line-init` reads and removes it: a record that is final and clean (no taint, nothing in the ledger, no open paste, no overflow, no refused line, nothing dropped) runs its complete lines one per prompt through the shell's own accept-line (the `${(q+)BUFFER}` quoting, never eval; run N's Stop is sent first, and no ready file is written while lines remain), then gives the draft back to the buffer. A handed-off line and a given-back draft are MESSAGES: the shell marks them (`_tmm_replay`), so a leading `!` is never the shell escape, which stays a person's own command typed at the idle prompt (review P1-A, round 2); a buffer the person empties is theirs again. The shell writes `tmm/ready` only with an EMPTY buffer (review P1-B, round 2): a draft given back is the person's until they submit it (its own run; a line held meanwhile goes to that run) or clear it (`zle-line-pre-redraw` writes ready then, and a line held meanwhile goes at the next feed read or delivery), so no delivery is ever typed into it. With an empty buffer, ready is written BEFORE the Stop is published, deliberately: publishing the Stop is what releases a held line (the stop flush), so that flush must find the shell ready — no sleep, no reliance on the consumer being slower — and ZLE cannot read a line typed now until the handler has published the Stop, so run N's Stop still precedes the prompt of the next run. That exact window is pinned by `dsh_publication_failures_never_reopen_a_turn_or_hang_the_shell` (run 3's Stop publication hung, the ready file seen, the turn still busy, the next line delivered in that interval, inbox order `[Stop, UserPromptSubmit]`, distinct recipients), and the non-empty-draft exclusion by `a_half_paste_or_a_given_back_draft_keeps_a_delivery_out`; orchestrator and reviewer signed off on this ordering on 9d1365ee, for an empty buffer only. Anything else — not final (a reader SIGKILLed), unclean, or half a paste — is shown as `not sent: …`, inert, and nothing of it runs. What is promised is exactly that: a clean, complete late line runs next; anything else is shown as not sent and never run. A reader killed before it wrote anything loses its draft, and so does one SIGKILLed DURING its turn: the record is written only from the turn's end on, not on every keystroke (review P2-B, round 2, choice: documented, not persisted — a write per key for every run buys back only a draft from a kill during the turn, and a window kill or restart takes the shell, and with it any buffer, anyway).
Pinned by `the_steer_reader_frames_bytes_and_hands_off_only_a_clean_state` (every split of a bracketed paste fed in full; an exit at every split before the rest arrives, also after a draft; invalid UTF-8 with an incomplete character or ESC in the same chunk; ESC, ^C, arrows, CRLF, several Enters in one chunk, backspace, overflow, the inert echo; round 2: a NUL pasted or typed, a NUL draft, an open paste with nothing pending, a draft that is clean but admits nothing, ^C and a lone ESC inside an open paste, other control bytes in a paste kept as text and a decoded sequence ignored, a tainted ledger holding nothing and an endless sequence held short by the decoder itself, the hold budget, an echo failure after a steer), `a_steer_claim_is_believed_only_for_this_run_of_this_pane`, `steered_lines_join_the_running_turn_and_every_sender_gets_the_reply` (two steers, one in flight at a time, the Stop answering all three senders once, receipts settled; a cold-start line held then steered; a multi-line message as one line), `a_line_typed_after_the_turn_ended_runs_next_only_from_a_clean_hand_off` (two lines and a draft, a canary, Stop before the next prompt; a delivery racing the end; half a paste; SIGKILL), `a_steer_run_is_interrupted_by_escape_and_a_lone_hyphen_is_refused`, round 2's `a_nul_or_a_bang_in_a_typed_line_never_runs_as_shell_code` (a NUL paste in the turn and in the gap, a handed-off `!` line, metacharacters, a given-back `!` draft, a NUL draft; seven canaries, no extra run), `a_half_paste_or_a_given_back_draft_keeps_a_delivery_out` (an open-paste claim with a hub send; a draft with the Stop's publication held, the Stop's flush and a later flush; the draft submitted as its own run, the held line steered into it) and `a_line_held_through_a_slow_factory_steers_the_run_once_its_reader_is_whole` (the factory held: no prompt, no claim; then the claim on file when the prompt is in the inbox, and that prompt's own flush steers the held line, both senders answered), round 3's `a_persons_draft_in_the_turn_keeps_a_delivery_out_until_it_is_entered` (a typed draft and a closed paste, each with a hub send held through a consume and a flush, then each line steered exactly and alone, receipts settled) and `an_interrupt_ends_a_steer_run_from_inside_an_open_paste` (the actual hub interrupt and ^C, each with a paste open: claim withdrawn, the process gone, no reply, the draft not sent, nothing run), and through the REAL dsh against the loopback stand-in by `the_real_dsh_takes_steered_lines_into_the_running_turn` (M3: a line typed into the cold start is read after the raw switch and steered; a steered line reaches the model's next request; three prompts reported).

**First prompt and vitals**: no positional prompt on a launch line that is a shell, so the brief is TYPED once the prompt is up (`FirstPrompt::Typed`, kimi's door); the ready marker is `dsh ›` without the prompt's trailing space, because `capture_pane_plain` trims the end of a capture and a fresh prompt is the last thing on screen (the first version, with the space, never matched). dsh paints no status furniture, so the managed shell paints ours (board #409, owner 2026-10-17: "dsh的上下文长度好像没看到显示"): the plugin builds a vitals row from dsh's own events, `[dsh] · <model> · ctx <used>/<window>`. The model and window come from the root session's last `request/context` (`contextWindow` 1000000 for deepseek-flash), and the context used comes from the step's `assistant/message` `usage`, as `inputTokens + cacheReadTokens + cacheWriteTokens`. dsh's `inputTokens` excludes the cache reads (measured on the live `deepseek` session: 11382 + 384 + 70 output = 11836 total), and output is not part of what the request carried. A step without usage keeps the last figure, and a subagent's events never reach the row. The plugin writes the row to `$DSH_HOME/tmm/vitals`; the shell's `precmd` prints it once, just above the prompt, and removes it, so a person at the pane sees it too. The figure is the LAST COMPLETED RUN's input, not a live one: nothing is painted while a run lasts. `sniff_dsh` reads the newest line that STARTS with `[dsh] · ` (column zero; claude's `[CC]` rule). That rejects an indented, prompt-prefixed or chat-stamped copy, not every copy: an output line that itself starts exactly with `[dsh] · ` is read too, and while a run prints, it is the newest (reviewer P2 on 98c24c96; closing it would take a screen classifier, which is not worth it for a display reading). The percentage is computed on the hub by `vitals::used_pct`, the one formula for a backend that reports counts (grok's header ratio goes through it too). It refuses non-finite, negative, empty-window and over-window input, keeps the old `used × 100 / window` rounding (23500 of 100000 is 24), switches to ratio-first only for a count too large for that product, and always returns 0..=100. No effort is read: dsh's levels (`off`…) are not the card's effort words.
