# Agent Status — derived state, telemetry, deliveries and recovery

How the four derived states (`running | waiting | idle | failed`) come out of hook facts, what the activity log keeps, how typed lines and automatic final replies are delivered, the pane-sniffed vitals, and the auto-`continue` recovery for transient model errors. Companion to `agents-overview.md` and `agent-lifecycle.md`.

## Rules and their reasons

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Status is the turn bracket, and pane activity is NOT work

the hooks report all four edges of a turn (`userPromptSubmit` opens, tools run inside, an ask suspends, `stop` closes), so `derive_from` is just "which boundary is newest" → exactly four states `running | waiting | idle | failed`, with `since` = the turn's START so a client can render "running 2m14s". Agents never declare state. The rule that had to go: `window_activity` newer than the last stop used to mean `working`, but an agent TUI repaints after answering (spinner, status line, cursor), so every finished agent read `working` forever. Pane activity now only speaks for a window that has produced NO hook facts at all (a hookless backend, a hand-started window). `Rec` keeps turn ends (`end`) and asks (`ask`) in separate fields for the same reason — one Option cannot answer "is a turn running" once a permission prompt overwrites a stop.

**kiro v3's post-turn `memory` calls are NOT work** (board #227, measured 2026-09-20; owner: "升级kiro-cli v3后，总是遇到一些结束了还一直显示在工作"). kiro-cli v3 (KAS) runs its memory auto-capture as `memory` TOOL calls after the turn's Stop — state.db showed the same shape on two agents (kiro-v3-roll:kiro, kirocrew-ppt:aws-expert): prompt → tools → `completed` → three `memory` calls 10–30 s apart with no new prompt; since a tool is a turn start, the newest one reopened the turn and the card said `working` until the next message (aws-expert sat there five hours). The agent ALSO calls `memory` inside a turn (`memory list/add`), so the tool's name is not the verdict by itself: `Backend::is_housekeeping_tool` (kiro: `tool_name == "memory"`; no other backend has one) names the tool, and the consumer records it through `telemetry::record_housekeeping_tool`, which counts it ONLY while the window's turn is open (`derive_from` says running/waiting) and drops it otherwise — no turn fact, no feed row. The generic rule (a tool without a prompt still opens a turn — claude/codex once delivered tools with no turn-start hook) is untouched; only the harness's own housekeeping is exempt. Pinned by `housekeeping_after_the_stop_does_not_reopen_the_turn` (telemetry) and `memory_is_the_housekeeping_tool` (kiro).

**Claude's `idle_prompt` is NOT an ask** (board #75, measured 2026-09-02: all 7 `input_required` rows in state.db sat exactly 60 s after `completed`): it is Claude Code's idle reminder fired AFTER the turn ended, and read as `input_required` it flipped every finished Claude agent to amber `waiting for you` a minute later. `consume_file` drops it before `normalize` (silently — already-spawned agents still emit it), and no matcher subscribes to it; `agent_needs_input` (a real question) stays `input_required`.

**How the four states RENDER on the card** (review, 2026-09-03): the dot speaks `stateDotColor` — accent in motion, `--status-warn` waiting/blocked, `--status-danger` failed, achromatic `--status-sleep` at rest — and `running` alone adds the `.live-dot` halo + breathe (`stateIsLive`, design-language.md). That left `waiting` — the one state that needs the HUMAN — as a 6px static amber dot beside a breathing neighbour, the weakest signal on the card. So the CARD carries it now: `stateNeedsYou(state)` (pure, pinned against `stateDotColor`'s amber states, and never true together with `stateIsLive`) puts `.acard.needs` on the card — the same `--status-warn` token as a 1px border + 1px inset ring (inset because the strip clips outward shadows) and a 9% wash — plus the word `needs you` (`blocked` keeps its own word) at `--fs-micro` beside the dot. Deliberately STATIC: the breathe means "a turn is open", and a suspended turn is not one; no new colour, no new mechanism — one token, worn by the card instead of only by the dot. Selection keeps its accent frame on top; the wash, the word and the dot still say waiting. `Hub.source.test.ts` pins the class, the gate and the token.

### A `tmm send --status` note is optional ambient progress

hooks bracket a turn but never say what it is FOR, so an agent may post
`tmm send "…" --status`. `hub_post` stores it as
`[tmm status working] <note>` from the agent, record-only: it never types into a
pane, never changes derived state, and never suppresses the final hook reply.

### The activity log is DURABLE, and a status note is a MESSAGE

tool calls, prompts, receipts and notes lived in a 120-entry in-memory ring, so a restart erased every tool lane while the messages around them survived — a feed with holes in it (owner, 2026-08-19: "重启就没了"). `activity` (state.db v9) is now the record: `push` inserts fail-soft (telemetry may never block what it observes), `recent_events` reads the DB (tail-first, `LOAD_EVENTS`) and falls back to the ring when there is no database, and a prune every 256 inserts keeps `KEEP_EVENTS` per session. Under `cfg(test)` both halves are off so `cargo test` cannot write invented sessions into the real state.db; the SQL is tested directly in `store.rs`. A progress note is a room message, not an event.

`statusNote()` keeps reading both `[tmm status …]` and historical
`[tmm done]` markers because rooms are durable. New completion messages are the
normal final responses captured by hooks; there is no separate done command.

### What we observe has an input half too

`userPromptSubmit` carries the submitted `prompt` (measured, kiro-cli 2.16.2), which is the only record of text typed at an agent's own keyboard and the only proof that a line `deliver_mentions` typed was accepted as a prompt — `send-keys` succeeding says nothing about that. `telemetry::record_delivery` QUEUES the typed line as a row of the `deliveries` table, the ONE pending queue since board #249 (see below) — as ONE slot, a second message typed at a busy agent erased the first's record, so when the agent finally submitted the first queued line nothing matched it: it came back as `via: local` and rendered as an "input" row while its message kept a hollow ring for ever — owner, 2026-08-20), `record_prompt` matches on CONTENT and removes exactly what it found (one submitted prompt can carry several queued lines and acks all of them; `feedBlocks` likewise marks EVERY message an echo contains, not just the newest; **the containment runs whitespace-BLIND on BOTH sides, and on the client it is TRUNCATION-aware** — the stored echo is cut at `MAX_PROMPT_CHARS` (1024) + `…` while the server matched the FULL prompt, so `feedBlocks` (`echoContains`) also accepts a body that starts inside a truncated echo and continues past its end (board #78, 2026-09-03: a 1041-character paste was acked by the hook yet kept a hollow ring for ever because the client demanded the whole body inside 1024 characters);  — `strip_ws`/`squashWs` remove every whitespace character, because a newline in the body never survives the trip: a TUI composer renders it as a space or its own wrap (owner, 2026-08-22), and tmux in extended-keys mode DROPPED the raw `\n` byte outright so the echo came back with the lines GLUED together — squash-to-one-space could not contain that (owner, 2026-08-24, measured in the translator room: `AgenticAI\nAgentic…` echoed as `AgenticAIAgentic…`). The delivery itself is fixed at the source too: `tmux::send_command` routes any text containing `\n` through `paste_text` — bracketed paste is the one channel that carries a newline INTO a composer, where send-keys loses it and a named `Enter` would submit the half-typed line) and emits a `prompt` event with `via: app|local`, `sweep_deliveries` reports what is still pending after 45 s as a `warn` — but **the ack clock does not run while a turn is OPEN**: a busy agent QUEUES what we typed (kiro says "Type to queue") and submits it when the turn ends — and every managed agent's definition says queue by default (`reg_agents.input_mode`, board #245: kiro's `settings/cli.json` `chat.defaultInterruptBehavior`, codex's keymap; which backends can switch, and what steer costs, is measured in agents-overview.md § The input mode) — so `overdue_rows` skips `running`/`waiting` windows and otherwise measures from the LATER of the typing time and the turn's end (a line HELD for a busy queue-mode agent, board #257, is not in the queue at all until it is typed: its row has `held = 1`, the echo match and the sweep skip it, and typing it resets its `ts`, so the clock starts then; see hub-composer.md § A busy queue-mode agent) (owner, 2026-08-19: "有一些queue的指令，没办法马上confirm，这个不用立刻就unconfirm"). A line typed at an IDLE agent keeps its own clock and a hookless window is still swept — both are tests. Client side, `feedBlocks()` consumes an `app` echo as a *delivered* mark on the message instead of repeating its text, keeps receipts and warnings visible at EVERY detail level (they are about a message the user sent, not opt-in telemetry), and folds a window's `tool` events into ONE lane-per-turn group so `+ tools` can be the default (a tool row keeps 2 KB of its ARGUMENT — it kept 80 chars, so every row ended in `…` after a third of a line with a blank wide screen beside it — and Pre/Post are collapsed to ONE row in `record_tool`, since both hooks are subscribed for backend coverage and an already-spawned agent keeps its old config): only that window's OWN rows end its run (its reply — attributed via the `windowOf` map — its prompt, the invisible echo of a delivered line, a note about it), because folding merely CONSECUTIVE events turned two concurrent agents into one group per call and read as churn (owner, 2026-08-19). A group is OPEN by default with a scrolling body capped at a CONFIGURABLE row count (`hubPrefs.stepsRows`, default `STEPS_ROWS` = 5 — owner, 2026-08-24: "最大显示的行数应该也变成一个可配置的参数…默认…5 行"; a Settings stepper next to the feed-level control, `clampStepsRows` pins 3–30 on both the setter and what localStorage hands back) and a "show all N" that lifts the cap; the ARGUMENT is never truncated — the lane is THREE columns and the MIDDLE one is the only scroller — `.st-scroll` (flex:1; min-width:0; overflow-x:auto) wraps the text in the MARKUP, the name and time are flex siblings BESIDE it, `.s-body` is overflow-x:hidden. Structure beats paint: the sticky-column build failed three ways (columns jumped 30px — sticky offsets measure from the scrollport's padding box; then painted `--surface`, a 3% wash that covers nothing; then still leaked into the lane padding beside the name, since a sticky column covers only its own box — "参数穿模到工具名左侧了"). `min-width: 0` is load-bearing (a flex child refuses to shrink below content without it); rows pan independently by accepted trade; `Hub.source.test.ts` pins the markup shape because an ellipsis hid the one thing you opened the lane to read (owner, 2026-08-20), and `.st-text` must stay `nowrap` and never `pre`: a tool detail contains real newlines, and `pre` would make one call a three-line row and break the cap's single-line math (`hub/Hub.source.test.ts` pins both) — every call is in the DOM, the cap is a viewport on it, so a live run cannot grow the conversation and the inner tail sticks to the newest call until the user scrolls up in it. No emoji in that surface: lifecycle lines carry the machine marker `[tmm] ` and the client renders them (`systemLine()` still accepts the old `⚡`/`✔` bodies — rooms are persisted); consecutive lifecycle lines fold into ONE `sys` capsule, and the chat-only level drops them (the app's record, not the conversation). Inside that capsule each line is its OWN ROW speaking ONE grammar — who, action, detail ("都用统一的 ui 来展示…包括 agent 的名字，状态，或者发送的指令", owner 2026-08-24): `sysParts()` parses every shape into `{who, verb, text, cmd}` (`removed k`, `spawned dev — brief`, `/model x → dev, rev` — the command splits at the LAST ` → `, the one `hub_command` appended), and each atom reuses a dialect the feed already has instead of inventing a third: the name wears the bubble header's ink (`.m-head` 650-weight accent), the action wears the status badge stripped to dot + coloured word (tinted by `sysVerbColor()` in the SAME progressive status language as `noteStateColor`/`stateDotColor` — accent = started moving, green = ended well, grey = at rest, amber = interrupted, red = destructive; both pure + tested, always a token so both themes read it), and a `/command`'s row keeps the typed line as ONE object in the inline-code dialect (mono, soft `--code-bg` wash, accent lean — splitting it into a micro-pill name plus loose args read as fragments, and drawn frames on the inner atoms read as chrome: owner, 2026-08-24 "带参数的渲染好像不是很好" then "不用这种边框的"), with the targets standing as the who. Two rules keep it honest: an unrecognised line shape keeps NO verb or name and renders whole (guessing would truncate the rest), and the per-row ellipsis sits on the text so a long detail cannot eat the badge.

### The deliveries table is the one pending queue (board #249, 2026-09-27)

Owner, 13:14: messages typed at a busy builder around 12:41 reappeared at 13:12 as `builder INPUT <sender>` rows. The CLI did nothing wrong: kiro 2.22.1 echoed every queued line whole, one per turn boundary (orchestrator's read-only root cause, `temp/input-row-rootcause.md` at the time). The server could not match them, because the queue had TWO copies that disagreed. Memory held at most 16 lines per window (`MAX_PENDING`) and evicted the oldest silently while its row stayed in the table; builder was sent about 23 lines in ten minutes, so the first 7 echoes found nothing and filed as `via: local`. After the 13:02 restart the fold (`hydrate`) rebuilt memory through an unordered map and cut it to 16, so a random subset survived, and a line already echoed was reported unconfirmed as well.

Now `record_delivery` only INSERTs a row, and `record_prompt` reads the window's rows in id order, runs the same whitespace-blind, duplicate-budgeted, truncation-aware match (`settled_by`, pure), and deletes what it settled by row id; a row counts as acked only if THIS echo deleted it. There is no count cap: the 24 h prune bounds the table. A restart no longer needs a fold. It needs only the old "a recovered line's clock starts now" rule, which is `recovery_mark`: the newest row id when this process first touches a session, and that moment. Rows at or below the mark wait `DELIVERY_ACK_SECS` from the mark, and newer rows wait from their own typing time (`overdue_rows`, pure). Each prompt hook now costs one indexed SELECT: 95 µs against 30 outstanding rows, compared with 12 µs from memory (release build, measured 2026-09-27), negligible at hook frequency. Pinned: 20 lines at a busy window all echo `app`; 30 across a restart keep their order and none is swept in the grace; three identical bodies settle one per echo and sweep one warn each. Negative controls: re-imposing a 16-row view fails the first two, and dropping the mark fails the recovery tests. The alternative (keep memory, make eviction delete and warn, fold in order) was rejected because two copies of one queue are the bug class (tenets 7, 9).

A restart in the middle of a long turn needs the turn too, not only the queue (validator, #249). With no facts the window derived idle, so 45 s after the restart the sweep reported every line the running CLI still held, and their late echoes filed as keyboard input. Recovery is not a second turn rule (orchestrator 14:55, tenet 8). On first touch of a session, `recover_open_turns` REPLAYS each window's newest persisted turn facts into a record this process has no facts for. `Store::turn_facts` returns the latest `prompt`, `tool` call, `permission_required`/`input_required` ask and end (`completed`/`failed`/`interrupted`), each keeping its row id as its order, and `derive_from` decides as it does live. So a tool-only turn is `running`, an open ask is `waiting`, a failed turn is `failed`, and an ended one is `idle`, never from pane activity. An interrupt (`hub_agent_interrupt`, an external end with no stop hook) writes its own `notif` `interrupted` row (validator 14:54) and replays as an end. That row is only a turn edge: the stop auto-post is driven by hook payloads, not the log, `current_turn_prompt` reads it as an end so no reply edge is recovered, and the feed draws nothing for it because the room already carries `[tmm] interrupted <name>`. A stop that fired while the server was down sits in the hook inbox and ends the turn when it is read. Kiro v3's post-stop housekeeping is never written as a tool row (#227), so it cannot reopen a turn. Pinned: `a_restart_mid_turn_keeps_the_turn_open_past_the_ack_window` (30 held lines, 46 s without a hook: no warns, all 30 echo as ours; a stopped window stays idle), `a_restart_recovers_a_tool_only_or_asking_turn` (tool-only running, ask waiting, tool after ask running, failed failed; only the ended turn sweeps its held line), `an_interrupted_turn_stays_closed_across_a_restart`, and the `hub.test.ts` "interrupt end row" case. Negative controls: dropping the end, tool or ask from the replay fails, respectively, the interrupt and stopped-window cases, the tool-only case and the ask case; drawing the interrupt row fails the client case.

### A steered kiro line has no receipt (board #249, measured 2026-09-27)

`chat.defaultInterruptBehavior = "queue"` sets the mode a kiro session STARTS in; kiro-cli 2.22.1 (`--agent-engine v3`) switches it for the session on Ctrl+S (`chat.keybindings.toggleInterruptBehavior`) or from its settings menu, and logs no switch. From 12:50 to 13:09 builder ran in steer: every line typed at the busy agent appeared in kiro's log as `_session/steer: appended steering …` and `[LiveSteeringHook] injected steering steer-…`, with no `session/prompt` and no `userPromptSubmit`, and the model's replies quote the same `steer-…` ids. The lines reached the model, but no hook ever echoed them, so at 13:13 the sweep reported each one `unconfirmed`. That report is correct: the only receipt channel we have is the hook, and a steered line bypasses it. What set the mode is unknown. No agent's tool calls sent keys to the pane, and `tmm` never sends C-s. We do not change the CLI (tenet 3). The queue/steer choice (#245) accepted this: a definition set to steer showed the cost in the editor, and its steered lines were reported `unconfirmed` once the turn ended (measured again on the #245 probe).

**A steered line owes no echo (board #276, 2026-09-29).** Owner, 09:03, on a steer-mode team flooded with `unconfirmed` notes: "对于 Steer 模式 你这里可以忽略吧 … 不用把它当做一个异常去处理". The report was accurate but useless: the line did reach the model, and nothing can ever confirm it. We do not read kiro's log for a receipt, because it is not a documented door (tenets 2 and 3; #245 already decided). At typing time the delivery knows both facts it needs: the window's turn is open (`turn_busy`) and the session runs steer (`delivery::input_mode`, #271). Such a line is typed into the running turn and gets NO pending row, so there is nothing for the sweep to report. This is the #250 copy-mode reasoning: a row that nothing can settle would exist only to carry an id. Instead one `steered` activity event names its message, and the feed uses it to draw no ring (the #264 command reading: no promise, just the time). The event is not a turn fact and is never drawn. Held lines flushed into a turn that now runs steer (an overdue flush) owe no echo either. The window is closed by ORDER, not by cleanup (validator/orchestrator 09:28): their rows are RETIRED in one transaction BEFORE the keys go in, so no typed line ever has a pending row, and a crash between the retire and the typing leaves nothing to sweep. A retire that fails types nothing, and the rows stay held for the turn's end. Typing that fails after the retire is the #250 `undelivered` warn. A hold that cannot be written in a steer turn also falls back to the steered path, not to a pending row. An IDLE steer-mode window still owes the echo, because the line starts a turn and the hook fires; so does every queue-mode window. Warns already persisted stay as they are. Pinned by `a_line_steered_into_a_busy_turn_owes_no_echo` (busy+steer: typed, no row, no warn; busy+queue: held; idle+steer: owed and settled) `one_message_steered_into_one_agent_and_owed_by_another`, `held_lines_steered_in_are_retired_before_typing_or_not_typed` (TEMP-trigger fault on the retire: nothing typed, both rows held; a lost moment after the retire: no pending row, one undelivered, no unconfirmed) and `a_hold_that_fails_in_a_steer_turn_is_steered`. Negative controls: without the steer branch the first test fails; with the old release → type → forget order the retire test fails.

**A second line before the first echo is steered too (board #281, 2026-09-29).** After #276 went live, five rows still leaked on lingting (architect 10:14:05, 10:21:08, 10:58:33; engineer 10:27:18, 11:00:01). The live state.db shows the same shape for each: two lines reached one IDLE steer window within about a second (a board note fans out beside the sender's chat line). The first got a row, started the turn and echoed at the same second (for example the 10:14:05.648 prompt edge carried `[board #13 reply]`). The second, `[board #12 reply]`, was typed before that edge reached us, so `turn_busy` still read idle and it got a row. But kiro was already in the turn in steer, so it fired no hook and was swept 80 s later. Now an idle steer window also counts as in a turn while a line typed into it owes an echo that has not come yet (`telemetry::line_in_flight`: a pending, unreported chat-line row younger than `DELIVERY_ACK_SECS`). It is derived from the one deliveries table with no marker of its own (tenet 8): the prompt edge settles the row, and then `turn_busy` answers. A first line the CLI never took stops counting on the sweep's own clock, so the two never disagree and no second timer exists. Queue mode is unchanged, since each of its lines echoes on its own turn. Pinned by `a_second_line_before_the_first_echo_is_steered_in_steer_mode` (lines 200 ms apart: one row, one echo, zero warns; queue control: two rows; aged row: owed again). Negative control: without the clause the test fails. The two reads and what follows them (the typing and the row, or the steered event) are one decision taken under the turn-fact lock (`telemetry::delivery_decision`), which `record_prompt` also holds. Without it, a line arriving between the prompt edge deleting the first row and writing its prompt fact read idle with nothing in flight and still owed an echo (validator 11:50). The app has one lock order: the window's delivery lock, then the turn-fact lock, then the pane send lock. No holder of the turn-fact lock takes a window lock: prompt settlement, the end edge, an interrupt and #264's command rows touch only the store, and the #257 flush runs after the end edge returns. Holding it while a line is typed costs other windows' hook processing one send (the 200 ms text → Enter beat) at most. Also pinned by `a_line_during_the_prompt_edge_waits_for_it_and_steers`: the echo is paused between its delete and its fact, and the second line waits for it and then steers. Negative control: without the decision lock the test fails.

### Receipts and warns name delivery rows; a warn does not settle (board #249, 2026-09-27)

The 12:41 message in the owner's screenshot was the one line the server DID mark `via: app`, and it still drew an INPUT row. `feedBlocks` could consume an app echo only by finding its message in the loaded feed, and that message was 184 rows back, outside the first 100-message page. The ONE correlation key is now the delivery row id (orchestrator's rule). `deliver_mentions` records the id of the message it types (`deliveries.msg_id`, v24), and every `prompt` echo lists the rows it settled and every `warn` the row it reported, as `{id, msg?}` (`ActivityEvent.deliveries`, stored in `activity.deliveries`). The client marks those messages delivered by id and consumes a settling echo even when none of them is loaded, notices included. It is a receipt, never keyboard input.

A report no longer settles its row. The sweep sets the persisted `deliveries.warned` mark (once per row, across sweeps and restarts) and leaves the row outstanding, because the line may still be sitting in the CLI's queue. A late real echo still matches it, settles it as ours and names it, and the client drops exactly the warn with that row id, never by text: two identical notices warn separately and retract separately. Rows that never echo leave with the 24 h prune. Rows before v24 have no references and keep the content match. Pinned: `an_echo_names_the_messages_it_settled`, `a_late_echo_settles_one_of_two_warned_identical_notices`, `a_reported_line_is_not_resurrected…` (warned once across a restart, then a late echo settles it as `app`), `duplicate_bodies_settle_one_by_one_and_sweep_by_row` (three sweeps and a restart, one warn per row), and `hub.test.ts` "a late echo retracts exactly the warn…". Negative controls: deleting in the sweep fails the late-echo tests; dropping the persisted guard fails the once-per-row test; retracting by text fails the client test.

### A line never typed is said at once (board #250, 2026-09-27)

A pane in tmux copy-mode swallows `send-keys` and `paste-buffer` alike, and a mode binding in the text (`q`, Enter) can end the mode, while tmux reports success. So `send_command` returned Ok, the line became a pending row, and 45 s later it read `unconfirmed` with nothing ever typed. That matches the signature of message 7735, though that instance cannot be proven after the fact. `send_command` now refuses a pane in a mode before typing anything and never cancels the mode (a person is reading there; orchestrator 17:00). The caller writes no pending row, because nothing was typed and no echo could ever settle it; a row would exist only to carry an id (orchestrator 17:21). There is no retry. `deliver_mentions` and `deliver_chat_line` emit the sweep's own `warn` kind at once on the target window: `undelivered (<reason>): <line>`. It carries no `deliveries` reference, since that field names real rows only (#249), so the client path is #249's unchanged: the warn is its own `.note.warn` row naming the agent, the reason and the line, it is never retracted, and the message keeps its hollow ring (orchestrator 17:03). Any other `send_command` error takes the same path, because no row speaks for that line either. `hub_command` warns the same way for every pane that refuses its `/command` (`undelivered (<reason>): /cmd` on that window), because an `all` where another pane took it answers success and records only the takers in the room, so without the warn the refused agent vanished (validator 17:35). When no pane took it, the RPC is also an error: nothing ran, so the composer's retry cannot repeat a success. Pinned: `send_command_refuses_a_pane_in_copy_mode_and_leaves_the_mode` (a `q` in the text does not end the mode; nothing typed; the other pane is unaffected), `a_mention_to_a_pane_in_copy_mode_warns_at_once_and_owes_nothing` (through `hub_post` to two agents: the reading pane gets one warn with the reason and the line and no `deliveries` key on the wire; the other is delivered and owed), `a_command_to_all_with_one_pane_in_copy_mode_warns_for_it_and_runs_the_rest` (real tmux: `all` succeeds for the free pane and records only it; the refused pane gets one warn with the command, keeps its mode, gets nothing typed; a single refused target is an error and warns), `hub.test.ts` "a warn about a line never typed…", `Hub.mount.test.ts` "a /command to All that one pane refused…" (the poll brings the warn in as one note naming alice and the command; the composer is not restored for a retry), and `Hub.mount.test.ts` "a line refused in copy-mode shows one warn note…" (the real Hub: one note naming alice, the reason and the line; the bubble's ring is the hollow `Queued` one). Negative controls: without the mode check both copy-mode Rust tests fail; without the `hub_command` warn the `all` test fails; without the client's warn note both mount tests fail.

### A prompt in the same second as the stop opens the turn (board #249, 2026-09-27)

Hook timestamps are whole seconds, and kiro drains a queued line within the second its previous turn stops. `derive_from` read `end >= start` as idle, so at 13:12:38 a running builder derived idle, the ack clock started, and 45 s later the sweep reported 15 lines the agent was still holding. Every turn fact (`prompt`, `tool`, `end`, `ask`) now also records its arrival order, and comparisons use `(second, order)`: a later arrival wins a same-second tie, and different seconds order exactly as before. The order is the persisted activity log's id order, not a counter that restarts with the process (validator): `arrival()` starts above the newest activity row id this process finds, and a turn edge recovered from the log keeps its own row id and moves the counter past it (`recovered_arrival`). So a stop observed after a restart sorts after the prompt it closes, even in the same second. Every turn fact (prompt, tool call, ask, stop, interrupt) also enters through ONE serialized entry, `turn_fact` (validator 15:07). Its activity row and its place in the live record are written under one lock and with one clock: the row's ts is the record's second, and the record's order is taken from ONE monotonic process counter (`order_of`) in the same critical section, right after the insert (orchestrator 15:48). Live order is insert order by construction, and a failed insert (fail-soft) only skips its row. Row ids are never a live order: mixing the two number spaces let a prompt tie with, or sort under, a stop whose write was lost (validator 15:47). The counter is seeded above the newest activity id this process finds, and a replay orders an earlier process's facts by their own row ids, all below the seed. Pinned by `live_turn_facts_take_one_increasing_counter` and `a_prompt_after_a_really_failed_stop_insert_reads_running`. The latter writes to a throwaway database and makes the stop's INSERT really fail with a temp trigger. SQLite consumes no id for a failed INSERT, so the next prompt's row gets exactly the id the stop would have had, and the same-second prompt still reads running. With the old row-id rule restored, it reads idle and the test fails. The log therefore orders turn facts exactly as the live record does, and a replay after a restart derives the state the window had. Before this, the prompt path took its order and then wrote its row while the stop path did the opposite, so a concurrent pair could land reversed. Tool deduplication is a DISPLAY concern and never drops a turn fact (orchestrator 15:44, validator 15:42–15:43). The Post half of a call is skipped, with no row and no record change, only when its Pre half is still the window's newest turn fact: the same call within `TOOL_DEDUPE_SECS` with no prompt, stop or ask after it. Any fact in between makes the second call a fact of its own. A tool right after a stop reopens a tool-only turn, and a Post after an approved ask is the turn's resume edge. Its row is written so the log replays it, and `feedBlocks` still collapses the consecutive identical row so the lane shows one call. The check reads the record under the same lock as the write (`turn_fact_unless`). Pinned by `tool_dedupe_never_drops_a_turn_fact` (tool → stop → same tool → running, live and replayed; Pre → ask → Post → running, live and replayed, one lane row; a plain pair is one row) and `hub.test.ts` "a Pre, an ask and the Post…". Dropping the stop or the ask from the check fails the matching case. Pinned by `the_log_replays_to_the_live_state_under_concurrent_turn_facts` (four threads interleave prompts, stops and interrupts in one second for 60 rounds; replaying the log through `replay_turn_facts` and `derive_from` matches the live state and the fact times). Without the lock it fails in 3 of 3 runs; a test-only 30 µs gap between row and order widens the race so the failure does not depend on luck. Pinned by `a_prompt_after_a_stop_in_the_same_second_opens_the_turn` (fails on the old comparison) and `a_stop_after_a_restart_sorts_after_a_recovered_prompt_in_the_same_second` (fails without the counter moving past a recovered id; also covers stop → restart → prompt in one second), and in a REAL second process by `same_second_order_survives_a_real_process_restart`: the parent writes an earlier process's edges to a scratch database and re-runs the test binary as a child against it (`TMM_TEST_CHILD_DB`), so the child's counter really starts fresh. Both cases pass there, and with the counter restarting at 1, as in the first cut, the child fails on "the later stop wins the same-second tie".

### A duplicated body is two promises, and a pane is typed into by one caller at a time (board #122, 2026-09-09)

Two siblings of the #120 keying fix, both measured first. **(1) Identical bodies.** `record_delivery` used to REPLACE a pending entry when the same line was typed again ("a re-typed line ... could never be acked twice") — but the pane really was typed into twice and the CLI submits twice, so the second `userPromptSubmit` echo found nothing pending and was filed as `via: local` keyboard input: the hollow-ring symptom from a third cause. Duplicates are distinct rows now (the deliveries table lost its `(session, win, line)` unique key in the v21 rebuild, heal-floored), and the echo matcher spends receipts COUNT-WISE, oldest first: each occurrence of the line in one echo settles one entry (`canon_prompt.matches(canon_line).count()`), a doubled-up submission settles both, and the truncation-aware reverse containment fires only for a line STRICTLY longer than the stored echo (an equal line already spent the forward budget — the first cut re-settled the sibling through that branch). Settling deletes ONE row by its id. **(2) Backpressure.** `send_command` is text → 200 ms beat → Enter; two unsynchronized callers (concurrent hub_posts, a board-notice storm) wove A-text, B-text, A-Enter, B-Enter — measured 2026-09-09: four racing sends to a `cat` pane arrived as ONE concatenated row, three submissions lost. The fix is one mutex per pane target inside `tmux::send_command` itself — every burst path (deliver_mentions, board notices, hub_command) addresses a pane as `session:window.pane`, so a burst serializes with the existing 200 ms spacing and no new mechanism; entries prune past 256. Both pinned: `identical_bodies_are_two_receipts_settled_one_per_echo` and the real-tmux `concurrent_sends_to_one_pane_never_interleave`.

### Telemetry is keyed by the window NAME, because the index is not an identity (board #120, 2026-09-09)

Every store in this file's domain — turn edges (`Rec`), deliveries (the durable table), the activity log, vitals readings, the recovery tracker — used to key on `(session, window INDEX)`, while the agent's identity everywhere else is the window NAME (managed_home, launch.json, the roster, @mentions). With `renumber-windows on`, killing a lower window shifts every higher index and a newcomer takes the freed number (measured 2026-09-09: `@788 "dev"` resolved 2 → 1 after the kill, `newcomer` took 3) — so one agent inherited another's open turn and receipts, and status painted the wrong card. The key is the NAME now, resolved ONCE at ingest: `tmux::resolve_pane_id` returns `#{window_name}` for the hook's `TMUX_PANE`, which also removed the index → list_panes → name round-trip in the auto-post path (the race where a rename between hook fire and consume lost the post). Transient tmux TARGETS (send-keys, capture-pane) still use a fresh index off list_panes — momentary use is fine; storing under it was the bug. On the wire, `ActivityEvent.window` and the `hub_rooms` states keys carry the name (`<session>:<name>`); state.db v20 adds `activity.win` (old rows read back their index as a decimal string) and rebuilds `deliveries` on a `(session, win, line)` unique key — an old pending row keyed by its index can never match a name-keyed echo and is swept once as unconfirmed, the honest reading of a cross-upgrade delivery. Pinned by a real-tmux test: after the kill the same pane resolves to the same identity, dev keeps its open turn, and the newcomer derives idle.

### A burst of old-stamped prompts after a long turn is the CLI's own queue draining, not a redelivery (board #111, 2026-09-09)

Right after the 04:33 server restart (the first after #107's migration + 4936-row import), kiro's pane submitted three lines stamped `03:23` within one minute — read at first as the server re-typing a long-confirmed delivery. The activity log says otherwise, and every server-side hypothesis was ruled out on evidence: the room store holds exactly ONE copy of the 03:23 message (seq 4907; nothing was re-posted 04:33–04:36), the `deliveries` table was untouched by the v19 migration (the queue only matches echoes and never types), and the 04:34 rows are `prompt` hook events — the kiro CLI SUBMITTING lines from its own input queue, not tmux receiving them again. What actually happened: kiro's turn ran 03:23→04:33 (the whole #100/#107 build), every message delivered in that window sat queued in the CLI (`chat.defaultInterruptBehavior = "queue"`, above), and the CLI drains ONE queued line per turn boundary — so kiro's replies at 04:34:37/48/59 each released the next 03:23-stamped line. Three DIFFERENT messages once each, not one message three times; the restart was a coincidence of timing. The server's half behaved exactly as designed: each line typed once, and the late echoes still acked their deliveries because the ack clock does not run while a turn is open (the rule directly above). The `[tmm chat <time>]` stamp is what made the staleness legible to the reader — which is the stamp's job. No code change; the layer is the CLI's documented queue behaviour, and we do not modify a CLI's harness (tenet 3).

### A sub-agent thread's event is the agent's own work, never the window's turn (board #169, 2026-09-11)

codex 0.153.4 runs `spawn_agent` children as threads INSIDE the parent's process, and the managed `hooks.json` fires for every thread on the same pane. Read naively, a child's `UserPromptSubmit` was THE window's turn start: the parent's brief to its child rendered as a codex INPUT row nobody typed (owner 2026-09-11 03:46, "很多消息好像没有正确识别到"), matched no pending delivery (`via: local`), and — the damage that mattered — `start_turn` replaced the window's reply edge with the brief's (nobody), so when codex's real turn ended its final reply reached no one: `tmm log --grep 'codex: [reply]'` held not one line while kiro and claude posted every turn. Measured in a scratch CODEX_HOME with hooks dumping every payload (parent spawns one child, waits, closes; 13 hooks): every event carries the ROOT `session_id`; child events carry `agent_id` + `agent_type`, parent events neither; the child ends with `SubagentStop`, never `Stop`; the parent's `Stop` does carry `last_assistant_message`. The rule, applied at the door (`consume_file`, before the tool/prompt classification, dialect on `backends/codex.rs::subagent_thread`): a payload from a sub-agent thread is the agent's own work like a tool call — its brief is a `Subagent` step in the tool lane, its tool calls stay tool rows, and NOTHING from a child opens or closes the window's turn, becomes its prompt, auto-posts, or writes its conversation id. Pinned by `a_subagent_brief_is_a_tool_row_and_leaves_the_turn_alone` (reply edge survives, one prompt, one Subagent row), the codex dialect test with the measured payloads, and the feed test that a `Subagent` row is a step, never an input. The missing spaces inside briefs are codex's own writing (verbatim in its rollout), not our rendering. One exception, measured next (board #170, same scratch method with `-a on-request -s read-only` and a child told to write a file): a child's `PermissionRequest` {agent_id, agent_type, tool_name: "Bash", tool_input: {command, description}} is shown in the PARENT's TUI as a blocking modal ("Would you like to run the following command? Thread: Agent (…)") until the human answers — so it IS the window's ask and derives `permission_required` like the parent's own; the door lets exactly that child event through (`a_subagent_permission_request_is_the_windows_ask`).

### Hook-sourced final replies carry one reply edge

`userPromptSubmit` parses stamped `[tmm chat …] sender:` envelopes and stores
the senders for the current turn (`address::requesters`). A normal request
creates the edge; an automatic `[reply]` or legacy `[done]` envelope does not.

**The human is on the edge too, as a RECORD, never a delivery** (board #289,
owner 2026-09-30: "过滤所有 to human 的消息"). Before, `requesters` dropped
`human`, so an agent's answer to the human was stored with `to = []` and "was
this reply to me" could not be read back. Now a stamped `human:` line counts,
and so does a prompt with no stamp at all, which only a person typing into the
pane produces (a `/command`, which the app types for any sender, and the legacy
spawn kick excepted). That reading rests on one premise: everything the app
itself types into a pane carries a `[tmm chat …]` stamp (chat lines, board
notices, wakes, briefs; validator 11:34 checked each). A new automatic input
without a stamp would be recorded as the human's request, so it must be
stamped too. The final reply's room row therefore names `human` in
`to`; `HubRoomPoster` (`server::post_final_with`) types `[reply]` only to
`address::pane_targets`, which drops the human, because the human has no pane
and reads the room. The live
edge and the recovery path read the same parser and the same stored
`activity.requesters`, so they agree; rows recorded before #289 keep their old
`to` (no human) and are not rewritten. Pinned by
`the_human_is_a_requester_but_never_a_pane_target` (address.rs),
`a_reply_is_recorded_to_the_human_and_typed_only_to_agents` (server/mod.rs:
the poster itself, recorded to both, typed to lead only), and the human rows of
`a_stop_payload_posts_the_agents_final_answer_to_the_room` and
`a_later_input_in_the_same_turn_joins_the_reply_edge` (live and recovered).
Negative controls, each measured: dropping `human` in `requesters` fails three
of them; the poster typing to every edge target fails the poster test.

**The edge accumulates within a turn** (#256). An input that arrives while the
window's turn is open (codex steer, anything typed mid-turn) ADDS its senders,
deduplicated and in arrival order; only the turn's end consumes the edge.
Two questions, two sources (orchestrator, #256 review 03:07). Whether the turn
is OPEN has ONE answer, `telemetry::turn_busy`: `derive_from` (`running` or
`waiting`) on the same recovered record the status reads, never a second query
(validator's counterexample: completed, then a tool call, is a tool-only turn
that `derive_from` reads as running; a prompt-only query called it closed).
WHO the edge holds is the senders of the prompts since the window's last
`completed`/`failed`/`interrupted` (`telemetry::for_each_turn_input`). A
tool-only turn is open but has no requester yet, so its first input starts the
edge. The in-memory edge memoises that fold (parsed from the full prompt; the
log keeps a 1024-char copy) and is stamped with the turn EPOCH
(`telemetry::turn_epoch`: the arrival order of the window's newest end fact,
in the same record). A memo from an earlier epoch belongs to a turn that ended
— one an interrupt closed takes no edge — so it is dropped and the members are
re-folded from the log. `start_turn` asks `turn_busy` alone whether to join; no
prompt count takes part in that decision. Every END edge closes the reply edge,
not only a Stop (orchestrator 03:50): `hub_agent_interrupt` drops the window's
edge (`AgentNotificationHub::end_turn`) where it records the interrupt, so a
tool-only turn that follows cannot answer the interrupted requester; the epoch
covers an end that call never sees (a persisted interrupt replayed after a
restart). Recovery reads each prompt row's stored requesters
(`activity.requesters`, v27, parsed from the full prompt by
`address::requesters`, #257), and parses the display text only for rows from
before that column — the text is cut at 1024 characters, and a combined prompt
of held lines can put a requester past the cut.
Incident (2026-09-27, `temp/stall-analysis.md`): `start_turn` REPLACED the
edge with the newest input's senders, so a `[reply]` landing mid-turn erased
the real requester. 27 of 404 turns in 14 hours lost their requester; one was
the #248 final SHIP orchestrator had asked validator for, which reached nobody
for 3h27m. A turn whose end is never observed (an Escape typed in the pane
itself fires no hook) keeps its requesters for the next input, the same limit
status derivation has.

When a managed window's stop hook fires, `maybe_auto_post` always records the
final response in the room. `TeamRoomPoster` then types
`[tmm chat <ts>] <agent>: [reply] <final>` into each stored sender's pane with
the ordinary delivery-receipt bookkeeping. The `[reply]` marker makes delivery
one hop, so two stop hooks cannot ping-pong. An agent is never its own reply
target (board #275): a prompt it sent itself, a self-wake, returns nothing,
because the answer would be typed back into the same pane
(`an_agent_is_never_its_own_reply_target`).

The managed-home gate excludes hand-started agents, final text is capped at
`MAX_REPLY_CHARS = 6144`, and reply targets are removed when used. If the
server restarts mid-turn, the edge is rebuilt by STREAMING every prompt newer
than the previous turn end and keeping only the distinct senders: a newest-N
page dropped the turn's first requester once it held more than N inputs (#256
review), and a never-ending turn (grok, #252) must not be loaded whole. Memory
is bounded by people, not inputs: an edge holds at most `MAX_REPLY_TARGETS`
(32) distinct requesters, keeping the earliest, so the requester who opened
the turn is never the one dropped. An
input after the restart joins the rebuilt edge. `tmm send` does not suppress the final response:
it starts a separate question or handoff.

### Historical auto-reply design (superseded 2026-09-08)

when a managed kiro window's stop hook fires, `consume_file` in `agent_notifications.rs` automatically posts the agent's final reply (`assistant_response` on the v2 engine; on kiro-cli 2.22.1's v3 engine the Stop payload carries NO text and `Backend::reply_fallback` reads the last `assistant` entry with a letter or digit — KAS closes a turn with a `"..."` placeholder row (#213) — of the global session file `~/.kiro/sessions/*/<session_id>/messages.jsonl` — board #207, agents-overview.md) to the project room. Four invariants prevent this from misfiring; violating any one breaks the system silently so they are enforced in code, not just in prompts: **(1) Same-turn dedup** — `userPromptSubmit` resets the per-turn flags per window; a `tmm send` sets `sent_this_turn` (the agent already spoke INTO THE ROOM this turn); if the flag is set at stop time the auto-post is skipped so one turn never produces two messages. A `tmm done` does NOT set it: the summary is a report ABOUT the work while the stop hook carries the answer itself, and treating done as send made every turn that ends with the REQUIRED `tmm done` lose its final reply — the chat showed a one-line `[tmm done]` and the answer nowhere (owner, 2026-08-21: "kiro grok 都好像没看到最后返回的消息"). Instead `hub_done` records the summary (`mark_done_this_turn`) and `reply_is_the_done_summary` skips the auto-post only when the reply IS the summary verbatim — the one real duplicate. That reset is the ONLY one, so the turn-start hook has to be installed **in every config that can auto-post** — ALL FOUR backend hook sets in `projects/spawn.rs` (`kiro_hooks`/`claude_hooks`/`codex_hooks`/`grok_hooks`; claude and codex shipped without it until 2026-08-22 and their agents lost the auto-post after their first `tmm send` — `refresh_hooks` backfills on every start) as well as the global `kiro_default.json`. Ship `stop` without `userPromptSubmit` and the flag is sticky: the prompt tells the agent to report progress with `tmm send`, and the first such call kills the auto-post for every later turn of that window.

**(2) Record-only** — every hook-sourced post is passed to `hub_post` with `record_only = true`, which prevents `deliver_mentions` from running; if an auto-post body contains an @-address and delivery were allowed, that would type into the peer's pane, trigger the peer's stop hook, which would auto-post back — a ping-pong loop. Skipping the sender's own window does not prevent this: the peer's window is what triggers the loop, so the fix must be at the call site.

**(3) Managed-only gate** — `maybe_auto_post` checks that `<project_path>/.tmm/agents/<window_name>/` exists before posting; the global `kiro_default.json` (used by direct and adopted windows) also carries the stop hook, so without this gate any kiro the user starts by hand would start posting into project rooms.

**(4) Reply budget** — `MAX_REPLY_CHARS = 6144` is the chat-path ceiling (the old 240-char `MAX_SUMMARY_CHARS` retired with the unread-notification UI, 2026-09-01 — the room is the one notification surface). Wiring: `RoomPoster` trait in `agent_notifications.rs`, implemented by `TeamRoomPoster` in `server/mod.rs`, injected once at server startup via `notifications.set_room_poster(...)`. `None` on mobile (degrades silently — no auto-post).

### Historical done feedback edge (superseded 2026-09-08)

`tmm spawn` records `spawned_by` in the launch recipe, `build_prompt` NAMES the briefer ("briefed by your teammate lead" — the anonymous "your teammate" left the agent with nobody to report back to), and `hub_done` delivers a non-empty summary into the live managed spawner's pane (`[tmm chat <ts>] <name>: [done] <summary>`, same `record_delivery` bookkeeping as an @mention). Reason: every other completion channel is record-only — the `[tmm done]` room line and the stop-hook auto-post wake nobody — so a lead that spawned two builders never learned they finished and could not schedule (owner, 2026-08-29). The prompt also casts the summary as ONE OR TWO LINES — the full reply is auto-posted separately, so a long summary re-told the whole answer as a near-duplicate bubble.
