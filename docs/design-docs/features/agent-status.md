# Agent Status — derived state, telemetry, deliveries and recovery

How the three derived states (`running | waiting | idle`) come out of hook facts, what the activity log keeps, how typed lines and automatic final replies are delivered, the pane-sniffed vitals, and the auto-`continue` recovery for transient model errors. Companion to `agents-overview.md` and `agent-lifecycle.md`.

## Rules and their reasons

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Status is the turn bracket, and pane activity is NOT work

the hooks report all four edges of a turn (`userPromptSubmit` opens, tools run inside, an ask suspends, `stop` closes), so `derive_from` is just "which boundary is newest" → exactly three states `running | waiting | idle`, and the colour word `failed` is not one of them: orchestrator's ruling on #354 (2026-10-15) keeps it in the status-colour language as a word only `app/ServerList` (a dead server's red dot is a true fact) and an agent's own `[tmm status failed]` note speak, while no derivation produces it for an agent — the one language must not fork, and the owner's complaint was the agent card. `since` is the turn's START, so a client can render "running 2m14s". Agents never declare state. The rule that had to go: `window_activity` newer than the last stop used to mean `working`, but an agent TUI repaints after answering (spinner, status line, cursor), so every finished agent read `working` forever. Pane activity now only speaks for a window that has produced NO hook facts at all (a hookless backend, a hand-started window). `Rec` keeps turn ends (`end`) and asks (`ask`) in separate fields for the same reason — one Option cannot answer "is a turn running" once a permission prompt overwrites a stop.

**kiro v3's post-turn `memory` calls are NOT work** (board #227, measured 2026-09-20; owner: "升级kiro-cli v3后，总是遇到一些结束了还一直显示在工作"). kiro-cli v3 (KAS) runs its memory auto-capture as `memory` TOOL calls after the turn's Stop — state.db showed the same shape on two agents (kiro-v3-roll:kiro, kirocrew-ppt:aws-expert): prompt → tools → `completed` → three `memory` calls 10–30 s apart with no new prompt; since a tool is a turn start, the newest one reopened the turn and the card said `working` until the next message (aws-expert sat there five hours). The agent ALSO calls `memory` inside a turn (`memory list/add`), so the tool's name is not the verdict by itself: `Backend::is_housekeeping_tool` (kiro: `tool_name == "memory"`; no other backend has one) names the tool, and the consumer records it through `telemetry::record_housekeeping_tool`, which counts it ONLY while the window's turn is open (`derive_from` says running/waiting) and drops it otherwise — no turn fact, no feed row. The generic rule (a tool without a prompt still opens a turn — claude/codex once delivered tools with no turn-start hook) is untouched; only the harness's own housekeeping is exempt. Pinned by `housekeeping_after_the_stop_does_not_reopen_the_turn` (telemetry) and `memory_is_the_housekeeping_tool` (kiro).

**Claude's `idle_prompt` is NOT an ask** (board #75, measured 2026-09-02: all 7 `input_required` rows in state.db sat exactly 60 s after `completed`): it is Claude Code's idle reminder fired AFTER the turn ended, and read as `input_required` it flipped every finished Claude agent to amber `waiting for you` a minute later. `consume_file` drops it before `normalize` (silently — already-spawned agents still emit it), and no matcher subscribes to it; `agent_needs_input` (a real question) stays `input_required`.

**A turn that ended without saying anything is REST too, and is answered by ONE nudge** (board #355, 2026-10-15). Three incidents on two kiro agents (validator 10-12 16:22, 10-13 00:21 and 14:27; builder-3 16:35) were reported; the room log holds 27 such lines between 2026-10-12 16:40 and 10-15 10:40 from eight agents (validator, builder-3, builder, builder-2, orchestrator, and laminar-log's editor, writer, researcher). Every one is kiro-cli v3's own sentence — "(No assistant response was recorded for the preceding turn. This placeholder was inserted automatically to preserve message alternation — it is not a reply the assistant produced.)" — which the Stop hook hands over as the reply and the room posts as the agent's words. It is what the CLI writes when a turn produced no assistant message. The causes the orchestrator observed differ and are hypotheses, not all measured: a single `execute_bash` that hit the CLI's 1 700 s tool limit (the validator's NC batches), a tool-heavy turn ending at ~75% context, a status line reading `Midway: expired` (a 29-minute turn at 29% context), and — not an empty turn at all — a `[wake]` line delivered to an idle agent that did not read it as "continue" for three hours. The effect is one: the agent is at rest with its work half done, the delivery landed, the hooks derived `idle` correctly, and nothing told it to resume; a person noticed 30 minutes to 3 hours later. Not every placeholder is a stall: of the five incidents in the room's last-1000-lines window, the agent spoke again within 0, 1, 1, 7 and 13 minutes, because ending a turn to wait for a background task is also a turn with no message. So the answer is a fact plus a narrow, once-only nudge, not an alarm. **The fact** is on the status: `backends::Backend::is_empty_reply` (kiro only — the sentence is the CLI's, other backends write the agent's words or nothing) marks the completion when the reply IS that sentence, whole, whitespace normalised and nothing before or after (`kiro::is_empty_turn_reply`; a prefix match was the first cut and the review caught it: the sentence followed by the real result, half of it, or a reply that quotes it would have been read as empty, and the agent that had answered nudged — the decision types into a pane, so it matches the whole text or nothing). The text is the 31 byte-identical `assistant` rows (`operationType: "Say"`) in `~/.kiro/sessions/*/messages.jsonl` written 2026-10-12..14 by kiro-cli 2.28–2.31 (the host runs 2.31.0; the store does not record which CLI wrote a row, so a per-row version cannot be stated); a captured stalled turn is replayed through the real lookup (`a_captured_stalled_turn_is_read_back_as_the_placeholder`: no-body Stop → the isolated home's `messages.jsonl` → the constant), `telemetry::record_notification_with` records it IN THE SAME WRITE as the end (the mark is the arrival number that end takes; a separate "and it was empty" step could land on an interrupt written in between, which the first cut did and the review caught), and the idle it derives carries the detail `last_turn_empty`, spelled and shown like `last_turn_failed` (hover row, touch facts, `tmm agent list`): no new state, no colour, and a later real end or a new turn simply stops matching. **The nudge** is `projects::stalls`: `NUDGE_AFTER` (5 minutes) later, if the agent is STILL at rest after that very end, holds an issue assigned to it in `doing`, and was not told to wait, it is typed one `[reply]`-shaped line naming its open item(s) and asking it to continue or say what blocks it. **Told to wait** is `waiting_from`: a pending wake that addresses it — by name or by `@all`, through `wakes::addressed_to`, the one reading the card's "next wake" uses too (the first cut matched only the name and would have nudged an agent that had agreed to continue after an `@all` wake) — or any task still running in the project (a task does not record who started it, so any running task counts and fewer nudges is the safe error). A source that COULD NOT BE READ is not "nothing pending": `wakes::pending` and `tasks::list` read an error as an empty list, which is right for a screen and wrong for a decision to type into a pane, so the nudge asks `wakes::try_pending` and `tasks::try_list` and, like an unreadable board, types nothing when either fails. **The last check is made where the line is typed.** The queries between the early check and the typing take time, and a prompt, an ask, an interrupt or a line sent to the agent can arrive in that gap — the first cut checked, queried, then delivered, and the delivery would queue or steer the "continue" behind the new input and never cancel it. `delivery::deliver_if` asks `telemetry::nudge_still_due` (that empty end is still the newest, the agent still at rest after it, no line typed and not yet echoed, none held) INSIDE the window's lock and the turn-fact lock, in the same step as the decision and the typing, in the app's one lock order (window lock → turn-fact lock → pane send); a prompt that arrives while it is asked waits for the whole step, and any change drops the nudge silently. ONE per run of empty turns, and the allowance is spent by a line DELIVERED, not by a timer set: two empty turns before any nudge send exactly one, for the latest (the first cut spent it when the timer was scheduled, so the second end was never answered); a nudge that itself ends empty earns no second (that would be a retry loop); only a turn that ends with a REAL reply forgives it. **Reply quality is three-valued** (`backends::EndQuality`): the placeholder, a real reply, or nothing usable. A Stop with no body, a blank body, or a session file that cannot be read arrives as "no text", which is not "the agent spoke" — the second cut read it that way and an unknown Stop reopened a spent allowance (spent → unavailable → placeholder nudged again with nobody having said anything) — so such a Stop neither marks the end empty nor forgives. The spend is also keyed to the RUN it was decided in (`nudge_run`, bumped by each real reply), so a write that arrives late cannot charge a newer run. There is ONE timer per agent, held by a LEASE: `telemetry::arm_nudge` returns a token (`nudge_owner`, 0 = free), `nudge_wait` and the thread's drop guard release only a lease that is still their own, and a second empty end before the timer fires becomes the end the same timer answers, so the sleepers are bounded by the windows. The first lease was a bool and an old timer's drop guard, running after a new empty end had armed a new timer, cleared the new timer's flag — a third empty end then armed a second live timer; the Gone-step release stays, because dropping it reopens the gap where an empty end landing between "decided it is done" and "thread ended" finds the flag set and is lost. It is a thread and not `wakes::schedule` on purpose — a wake is a persisted room message that fires unconditionally, and what makes this nudge due (which end was empty, whether the agent has moved on) is memory only, so a wake that outlived a restart could not re-check any of it. Nothing resumes arbitrary work, nothing is persisted (a restart forgets a pending nudge — the running state is a disposable projection), and the placeholder is still posted and delivered along the reply edge as before, so the requester still sees that the turn said nothing. **Two smaller facts of ours:** an agent's `[wake]` for a finished task now ends with what to do about it ("Continue the work this task was for: read the output and post the result."), because a bare "task X exited:0" read as news; and the agent-side rule stands — never run more than ~20 minutes of work in one tool call, start it with `tmm task start --wake` and read the result in a later turn. **Not ours:** a tool that times out should return to the model rather than end the turn, and a final message should not be dropped at high context or on an expired login; those are kiro-cli's, and the capture belongs in an upstream report (the owner decides; the fix here is the visible fact and the single nudge). **Not verified:** a reproduction. The empty turn could not be forced on demand in this session (it needs a 1 700 s tool call or a high-context turn), so the evidence is the room log and the orchestrator's observations, and the nudge is tested against the status machine, not against a live kiro-cli. **Choices, with their reasons (orchestrator's rulings 2026-10-15; each is a default, not a law).** `NUDGE_AFTER` is 300 s: long enough that the agent that simply started something and stopped has started again (of the five incidents in the window above, the agent spoke again within 0, 1, 1, 7 and 13 minutes), short enough to save the half hour the incidents lost. Any running task in the project suppresses the nudge, because a `Task` does not record who started it and a missed nudge costs less than "continue" typed into an agent that was told to wait. The nudge is on by default: the owner's complaint was exactly the silent stall. It is kiro only, because the placeholder is the only sentence we recognise. Not persisted: which end was empty and whether the agent has moved on are memory only. **Evidence.** The three incidents are the reported ones; the 27 room-log lines are the count; and the shape was seen live on the agent that built this (builder-2, 2026-10-15 — four turns ended with the placeholder, 10:40, 13:11, 13:27 and 14:1x, each right after a tool result with no closing text, at moderate context). Each recovered by itself because the next message arrived within minutes; none was forced. Pinned by `an_empty_end_is_rest_and_names_itself_in_the_detail`, `projects::stalls` tests (`one_nudge_per_run_of_empty_turns`, `two_empty_turns_before_a_nudge_send_exactly_one_for_the_latest`, `a_timer_that_finds_the_agent_moved_on_releases_itself`, `an_interrupt_after_an_empty_stop_does_not_inherit_its_emptiness`, `it_is_still_due_only_while_nothing_has_happened_since_that_end`, `a_nudge_the_pane_refused_spends_nothing`, `it_leaves_alone_an_agent_with_nothing_open_one_told_to_wait_and_one_that_moved_on`, `an_all_wake_is_waiting_and_an_unreadable_source_is_not_nothing`, `a_newer_input_between_the_check_and_the_delivery_drops_the_nudge` with its positive control), `an_old_timers_release_cannot_free_a_newer_timers_lease` (no sleeps: Gone, a new end arms, the old drop runs, a third end must not arm), `only_a_real_reply_reopens_the_allowance_and_a_late_spend_cannot_charge_a_newer_run`, `agent_notifications::tests::only_a_real_reply_reopens_a_spent_nudge_through_the_real_fallback` (spent → no session / blank / unreadable → placeholder = no second nudge; spent → real reply → placeholder = one), `the_production_fire_path_delivers_through_the_gated_entry` (a source pin: the unit tests stub the delivery, so the one line that hands the gate to `deliver_if` is pinned in the source, and the validator's live timing rows cover the pane), `delivery::tests::a_gated_delivery_is_checked_and_typed_in_one_step_against_the_prompt_edge`, `wakes::tests::a_wake_addresses_its_names_and_everyone_for_all`, the `normalizes_backend_events` case (the sentence is empty for kiro only, and not when quoted inside a real reply) and `a_task_end_wake_says_how_it_ended_and_addresses_only_its_target`.

**A failed turn END is REST, not distress** (board #354, 2026-10-15). Owner: "我发现在 Agent 的卡片上有时候会显示红色的小点，好像是因为时间过长，但大部分情况下我发现是网络连接超时或者它的一个状态响应 … 不用显示红点了". There used to be a fourth state: a `StopFailure` end derived `failed` and stood — immune to pane noise — until the next turn started. The signal was honest about the hook and dishonest about the agent: the common failure is a network timeout or a transient model error the CLI has already recovered from, so a card cried alarm for minutes about an agent that was simply resting, and the one colour reserved for "something is wrong" stopped meaning anything. A turn that ended is `idle`, however it ended. Nothing is hidden: the `failed` stop is still a row in the activity log and an event in the feed, and the derived `idle` carries the detail `last_turn_failed` — spelled like the ask details (`permission_required`) because a detail is shown verbatim — so the hover row, the touch facts block and `tmm agent list` all still say which agent's last turn failed. It is the COLOUR that is gone, not the fact. `failed` stays in the status-colour language for the things that really are still failing (an unreachable server in `app/ServerList`, an agent's own `[tmm status failed]` note, which is a report rather than a derivation), which is why `stateDotColor` keeps the word while no agent state produces it; `stuck` was deleted from both readers with this issue — nothing has produced it since the Team-supervisor era, and an unknown word is already quiet by rule. Pinned by `a_failed_stop_ends_the_turn_and_names_itself_in_the_detail` (state, detail, `since`, and that a new turn carries none of it), the restart-replay case in `a_restart_recovers_a_tool_only_or_asking_turn` (a failed end replays to `idle` and still sweeps its held line), and `hub.test.ts` "no agent state is painted as distress".

**How the three states RENDER on the card** (review, 2026-09-03): the dot speaks `stateDotColor` — accent in motion, `--status-warn` waiting/blocked, achromatic `--status-sleep` at rest, and since board #354 no derived agent state is `--status-danger` at all — and `running` alone adds the `.live-dot` halo + breathe (`stateIsLive`, design-language.md). That left `waiting` — the one state that needs the HUMAN — as a 6px static amber dot beside a breathing neighbour, the weakest signal on the card. So the CARD carries it now: `stateNeedsYou(state)` (pure, pinned against `stateDotColor`'s amber states, and never true together with `stateIsLive`) puts `.acard.needs` on the card — the same `--status-warn` token as a 1px border + 1px inset ring (inset because the strip clips outward shadows) and a 9% wash — plus the word `needs you` (`blocked` keeps its own word) at `--fs-micro` beside the dot. Deliberately STATIC: the breathe means "a turn is open", and a suspended turn is not one; no new colour, no new mechanism — one token, worn by the card instead of only by the dot. Selection keeps its accent frame on top; the wash, the word and the dot still say waiting. `Hub.source.test.ts` pins the class, the gate and the token.

### A `tmm send --status` note is optional ambient progress

hooks bracket a turn but never say what it is FOR, so an agent may post
`tmm send "…" --status`. `hub_post` stores it as
`[tmm status working] <note>` from the agent, record-only: it never types into a
pane, never changes derived state, and never suppresses the final hook reply.

### The activity log is DURABLE, and a status note is a MESSAGE

tool calls, prompts, receipts and notes lived in a 120-entry in-memory ring, so a restart erased every tool lane while the messages around them survived — a feed with holes in it (owner, 2026-08-19: "重启就没了"). `activity` (state.db v9) is now the record: `push` inserts fail-soft (telemetry may never block what it observes), `recent_events` reads the DB (tail-first, `LOAD_EVENTS`) and falls back to the ring when there is no database, and a prune every 256 inserts keeps `KEEP_EVENTS` per session. Under `cfg(test)` both halves are off so `cargo test` cannot write invented sessions into the real state.db; the SQL is tested directly in `store.rs`. A progress note is a room message, not an event.

`statusNote()` keeps reading both `[tmm status …]` and historical
`[tmm done]` markers because rooms are durable. New completion messages are the
normal final responses captured by hooks; there is no separate done command.

### What we observe has an input half too

`userPromptSubmit` carries the submitted `prompt` (measured, kiro-cli 2.16.2), which is the only record of text typed at an agent's own keyboard and the only proof that a line `deliver_mentions` typed was accepted as a prompt — `send-keys` succeeding says nothing about that. `telemetry::record_delivery` QUEUES the typed line as a row of the `deliveries` table, the ONE pending queue since board #249 (see below) — as ONE slot, a second message typed at a busy agent erased the first's record, so when the agent finally submitted the first queued line nothing matched it: it came back as `via: local` and rendered as an "input" row while its message kept a hollow ring for ever — owner, 2026-08-20), `record_prompt` matches on CONTENT and removes exactly what it found (one submitted prompt can carry several queued lines and acks all of them; `feedBlocks` likewise marks EVERY message an echo contains, not just the newest; **the containment runs whitespace-BLIND on BOTH sides, and on the client it is TRUNCATION-aware** — the stored echo is cut at `MAX_PROMPT_CHARS` (1024) + `…` while the server matched the FULL prompt, so `feedBlocks` (`echoContains`) also accepts a body that starts inside a truncated echo and continues past its end (board #78, 2026-09-03: a 1041-character paste was acked by the hook yet kept a hollow ring for ever because the client demanded the whole body inside 1024 characters);  — `strip_ws`/`squashWs` remove every whitespace character, because a newline in the body never survives the trip: a TUI composer renders it as a space or its own wrap (owner, 2026-08-22), and tmux in extended-keys mode DROPPED the raw `\n` byte outright so the echo came back with the lines GLUED together — squash-to-one-space could not contain that (owner, 2026-08-24, measured in the translator room: `AgenticAI\nAgentic…` echoed as `AgenticAIAgentic…`). The delivery itself is fixed at the source too: `tmux::send_command` routes any text containing `\n` through `paste_text` — bracketed paste is the one channel that carries a newline INTO a composer, where send-keys loses it and a named `Enter` would submit the half-typed line) and emits a `prompt` event with `via: app|local`, `sweep_deliveries` reports what is still pending after 45 s as a `warn` — but **the ack clock does not run while a turn is OPEN**: a busy agent QUEUES what we typed (kiro says "Type to queue") and submits it when the turn ends — and every managed agent's definition says queue by default (`reg_agents.input_mode`, board #245: kiro's `settings/cli.json` `chat.defaultInterruptBehavior`, codex's keymap; which backends can switch, and what steer costs, is measured in agents-overview.md § The input mode) — so `overdue_rows` skips `running`/`waiting` windows and otherwise measures from the LATER of the typing time and the turn's end (a line HELD for a busy queue-mode agent, board #257, is not in the queue at all until it is typed: its row has `held = 1`, the echo match and the sweep skip it, and typing it resets its `ts`, so the clock starts then; see hub-composer.md § A busy queue-mode agent) (owner, 2026-08-19: "有一些queue的指令，没办法马上confirm，这个不用立刻就unconfirm"). A line typed at an IDLE agent keeps its own clock and a hookless window is still swept — both are tests. Client side, `feedBlocks()` consumes an `app` echo as a *delivered* mark on the message instead of repeating its text, keeps receipts and warnings visible at EVERY detail level (they are about a message the user sent, not opt-in telemetry), and folds a window's `tool` events into ONE lane-per-turn group so `+ tools` can be the default (a tool row keeps 2 KB of its ARGUMENT — it kept 80 chars, so every row ended in `…` after a third of a line with a blank wide screen beside it — and Pre/Post are collapsed to ONE row in `record_tool`, since both hooks are subscribed for backend coverage and an already-spawned agent keeps its old config): only that window's OWN rows end its run (its reply — attributed via the `windowOf` map — its prompt, the invisible echo of a delivered line, a note about it), because folding merely CONSECUTIVE events turned two concurrent agents into one group per call and read as churn (owner, 2026-08-19). A group is OPEN by default with a scrolling body capped at a CONFIGURABLE row count (`hubPrefs.stepsRows`, default `STEPS_ROWS` = 5 — owner, 2026-08-24: "最大显示的行数应该也变成一个可配置的参数…默认…5 行"; a Settings stepper next to the feed-level control, `clampStepsRows` pins 3–30 on both the setter and what localStorage hands back) and a "show all N" that lifts the cap; the ARGUMENT is never truncated — the lane is THREE columns and the MIDDLE one is the only scroller — `.st-scroll` (flex:1; min-width:0; overflow-x:auto) wraps the text in the MARKUP, the name and time are flex siblings BESIDE it, `.s-body` is overflow-x:hidden. Structure beats paint: the sticky-column build failed three ways (columns jumped 30px — sticky offsets measure from the scrollport's padding box; then painted `--surface`, a 3% wash that covers nothing; then still leaked into the lane padding beside the name, since a sticky column covers only its own box — "参数穿模到工具名左侧了"). `min-width: 0` is load-bearing (a flex child refuses to shrink below content without it); rows pan independently by accepted trade; `Hub.source.test.ts` pins the markup shape because an ellipsis hid the one thing you opened the lane to read (owner, 2026-08-20), and `.st-text` must stay `nowrap` and never `pre`: a tool detail contains real newlines, and `pre` would make one call a three-line row and break the cap's single-line math (`hub/Hub.source.test.ts` pins both) — every call is in the DOM, the cap is a viewport on it, so a live run cannot grow the conversation and the inner tail sticks to the newest call until the user scrolls up in it. No emoji in that surface: lifecycle lines carry the machine marker `[tmm] ` and the client renders them (`systemLine()` still accepts the old `⚡`/`✔` bodies — rooms are persisted); consecutive lifecycle lines fold into ONE `sys` capsule, and the chat-only level drops them (the app's record, not the conversation). Inside that capsule each line is its OWN ROW speaking ONE grammar — who, action, detail ("都用统一的 ui 来展示…包括 agent 的名字，状态，或者发送的指令", owner 2026-08-24): `sysParts()` parses every shape into `{who, verb, text, cmd}` (`removed k`, `spawned dev — brief`, `/model x → dev, rev` — the command splits at the LAST ` → `, the one `hub_command` appended), and each atom reuses a dialect the feed already has instead of inventing a third: the name wears the bubble header's ink (`.m-head` 650-weight accent), the action wears the status badge stripped to dot + coloured word (tinted by `sysVerbColor()` in the SAME progressive status language as `noteStateColor`/`stateDotColor` — accent = started moving, green = ended well, grey = at rest, amber = interrupted, red = destructive; both pure + tested, always a token so both themes read it), and a `/command`'s row keeps the typed line as ONE object in the inline-code dialect (mono, soft `--code-bg` wash, accent lean — splitting it into a micro-pill name plus loose args read as fragments, and drawn frames on the inner atoms read as chrome: owner, 2026-08-24 "带参数的渲染好像不是很好" then "不用这种边框的"), with the targets standing as the who. Two rules keep it honest: an unrecognised line shape keeps NO verb or name and renders whole (guessing would truncate the rest), and the per-row ellipsis sits on the text so a long detail cannot eat the badge.

### The deliveries table is the one pending queue (board #249, 2026-09-27)

Owner, 13:14: messages typed at a busy builder around 12:41 reappeared at 13:12 as `builder INPUT <sender>` rows. The CLI did nothing wrong: kiro 2.22.1 echoed every queued line whole, one per turn boundary (orchestrator's read-only root cause, `temp/input-row-rootcause.md` at the time). The server could not match them, because the queue had TWO copies that disagreed. Memory held at most 16 lines per window (`MAX_PENDING`) and evicted the oldest silently while its row stayed in the table; builder was sent about 23 lines in ten minutes, so the first 7 echoes found nothing and filed as `via: local`. After the 13:02 restart the fold (`hydrate`) rebuilt memory through an unordered map and cut it to 16, so a random subset survived, and a line already echoed was reported unconfirmed as well.

Now `record_delivery` only INSERTs a row, and `record_prompt` reads the window's rows in id order, runs the same whitespace-blind, duplicate-budgeted, truncation-aware match (`settled_by`, pure), and deletes what it settled by row id; a row counts as acked only if THIS echo deleted it. There is no count cap: the 24 h prune bounds the table. A restart no longer needs a fold. It needs only the old "a recovered line's clock starts now" rule, which is `recovery_mark`: the newest row id when this process first touches a session, and that moment. Rows at or below the mark wait `DELIVERY_ACK_SECS` from the mark, and newer rows wait from their own typing time (`overdue_rows`, pure). Each prompt hook now costs one indexed SELECT: 95 µs against 30 outstanding rows, compared with 12 µs from memory (release build, measured 2026-09-27), negligible at hook frequency. Pinned: 20 lines at a busy window all echo `app`; 30 across a restart keep their order and none is swept in the grace; three identical bodies settle one per echo and sweep one warn each. Negative controls: re-imposing a 16-row view fails the first two, and dropping the mark fails the recovery tests. The alternative (keep memory, make eviction delete and warn, fold in order) was rejected because two copies of one queue are the bug class (tenets 7, 9).

A restart in the middle of a long turn needs the turn too, not only the queue (validator, #249). With no facts the window derived idle, so 45 s after the restart the sweep reported every line the running CLI still held, and their late echoes filed as keyboard input. Recovery is not a second turn rule (orchestrator 14:55, tenet 8). ### A prompt in the same second as the stop opens the turn (board #249, 2026-09-27)

Hook timestamps are whole seconds, and kiro drains a queued line within the second its previous turn stops. `derive_from` read `end >= start` as idle, so at 13:12:38 a running builder derived idle, the ack clock started, and 45 s later the sweep reported 15 lines the agent was still holding. Every turn fact (`prompt`, `tool`, `end`, `ask`) now also records its arrival order, and comparisons use `(second, order)`: a later arrival wins a same-second tie, and different seconds order exactly as before. The order is the persisted activity log's id order, not a counter that restarts with the process (validator): `arrival()` starts above the newest activity row id this process finds, and a turn edge recovered from the log keeps its own row id and moves the counter past it (`recovered_arrival`). So a stop observed after a restart sorts after the prompt it closes, even in the same second. Every turn fact (prompt, tool call, ask, stop, interrupt) also enters through ONE serialized entry, `turn_fact` (validator 15:07). Its activity row and its place in the live record are written under one lock and with one clock: the row's ts is the record's second, and the record's order is taken from ONE monotonic process counter (`order_of`) in the same critical section, right after the insert (orchestrator 15:48). Live order is insert order by construction, and a failed insert (fail-soft) only skips its row. Row ids are never a live order: mixing the two number spaces let a prompt tie with, or sort under, a stop whose write was lost (validator 15:47). The counter is seeded above the newest activity id this process finds, and a replay orders an earlier process's facts by their own row ids, all below the seed. Pinned by `live_turn_facts_take_one_increasing_counter` and `a_prompt_after_a_really_failed_stop_insert_reads_running`. The latter writes to a throwaway database and makes the stop's INSERT really fail with a temp trigger. With the old row-id rule restored, it reads idle and the test fails. The log therefore orders turn facts exactly as the live record does, and a replay after a restart derives the state the window had. Before this, the prompt path took its order and then wrote its row while the stop path did the opposite, so a concurrent pair could land reversed. Tool deduplication is a DISPLAY concern and never drops a turn fact (orchestrator 15:44, validator 15:42–15:43). The Post half of a call is skipped, with no row and no record change, only when its Pre half is still the window's newest turn fact: the same call within `TOOL_DEDUPE_SECS` with no prompt, stop or ask after it. Its row is written so the log replays it, and `feedBlocks` still collapses the consecutive identical row so the lane shows one call. The check reads the record under the same lock as the write (`turn_fact_unless`). Pinned by `tool_dedupe_never_drops_a_turn_fact` (tool → stop → same tool → running, live and replayed; Pre → ask → Post → running, live and replayed, one lane row; a plain pair is one row) and `hub.test.ts` "a Pre, an ask and the Post…". ### A duplicated body is two promises, and a pane is typed into by one caller at a time (board #122, 2026-09-09)

**The edge accumulates within a turn** (#256). An input that arrives while the
window's turn is open (codex steer, anything typed mid-turn) ADDS its senders,
deduplicated and in arrival order; only the turn's end consumes the edge.
Two questions, two sources (orchestrator, #256 review 03:07). Whether the turn
is OPEN has ONE answer, `telemetry::turn_busy`: `derive_from` (`running` or
`waiting`) on the same recovered record the status reads, never a second query
(validator's counterexample: completed, then a tool call, is a tool-only turn
that `derive_from` reads as running; a prompt-only query called it closed).
WHO the edge holds is the senders of the prompts since the window's last
`completed`/`failed`/`interrupted` (`telemetry::for_each_turn_input`). A
tool-only turn is open but has no requester yet, so its first input starts the
edge. The in-memory edge memoises that fold (parsed from the full prompt; the
log keeps a 1024-char copy) and is stamped with the turn EPOCH
(`telemetry::turn_epoch`: the arrival order of the window's newest end fact,
in the same record). A memo from an earlier epoch belongs to a turn that ended
— one an interrupt closed takes no edge — so it is dropped and the members are
re-folded from the log. `start_turn` asks `turn_busy` alone whether to join; no
prompt count takes part in that decision. Every END edge closes the reply edge,
not only a Stop (orchestrator 03:50): `hub_agent_interrupt` drops the window's
edge (`AgentNotificationHub::end_turn`) where it records the interrupt, so a
tool-only turn that follows cannot answer the interrupted requester; the epoch
covers an end that call never sees (a persisted interrupt replayed after a
restart). Recovery reads each prompt row's stored requesters
(`activity.requesters`, v27, parsed from the full prompt by
`address::requesters`, #257), and parses the display text only for rows from
before that column — the text is cut at 1024 characters, and a combined prompt
of held lines can put a requester past the cut.
Incident (2026-09-27, `temp/stall-analysis.md`): `start_turn` REPLACED the
edge with the newest input's senders, so a `[reply]` landing mid-turn erased
the real requester. 27 of 404 turns in 14 hours lost their requester; one was
the #248 final SHIP orchestrator had asked validator for, which reached nobody
for 3h27m. A turn whose end is never observed (an Escape typed in the pane
itself fires no hook) keeps its requesters for the next input, the same limit
status derivation has.

When a managed window's stop hook fires, `maybe_auto_post` always records the
final response in the room. `TeamRoomPoster` then types
`[tmm chat <ts>] <agent>: [reply] <final>` into each stored sender's pane with
the ordinary delivery-receipt bookkeeping. The `[reply]` marker makes delivery
one hop, so two stop hooks cannot ping-pong. An agent is never its own reply
target (board #275): a prompt it sent itself, a self-wake, returns nothing,
because the answer would be typed back into the same pane
(`an_agent_is_never_its_own_reply_target`).

The managed-home gate excludes hand-started agents, final text is capped at
`MAX_REPLY_CHARS = 6144`, and reply targets are removed when used. If the
server restarts mid-turn, the edge is rebuilt by STREAMING every prompt newer
than the previous turn end and keeping only the distinct senders: a newest-N
page dropped the turn's first requester once it held more than N inputs (#256
review), and a never-ending turn (grok, #252) must not be loaded whole. Memory
is bounded by people, not inputs: an edge holds at most `MAX_REPLY_TARGETS`
(32) distinct requesters, keeping the earliest, so the requester who opened
the turn is never the one dropped. An
input after the restart joins the rebuilt edge. `tmm send` does not suppress the final response:
it starts a separate question or handoff.

### Historical auto-reply design (superseded 2026-09-08)

when a managed kiro window's stop hook fires, `consume_file` in `agent_notifications.rs` automatically posts the agent's final reply (`assistant_response` on the v2 engine; on kiro-cli 2.22.1's v3 engine the Stop payload carries NO text and `Backend::reply_fallback` reads the last `assistant` entry with a letter or digit — KAS closes a turn with a `"..."` placeholder row (#213) — of the session file `<KIRO_HOME>/sessions/*/<session_id>/messages.jsonl` — the agent's isolated home first, the global `~/.kiro/sessions` only as the legacy fallback (board #207, #376; agents-overview.md)) to the project room. Four invariants prevent this from misfiring; violating any one breaks the system silently so they are enforced in code, not just in prompts: **(1) Same-turn dedup** — `userPromptSubmit` resets the per-turn flags per window; a `tmm send` sets `sent_this_turn` (the agent already spoke INTO THE ROOM this turn); if the flag is set at stop time the auto-post is skipped so one turn never produces two messages. A `tmm done` does NOT set it: the summary is a report ABOUT the work while the stop hook carries the answer itself, and treating done as send made every turn that ends with the REQUIRED `tmm done` lose its final reply — the chat showed a one-line `[tmm done]` and the answer nowhere (owner, 2026-08-21: "kiro grok 都好像没看到最后返回的消息"). Instead `hub_done` records the summary (`mark_done_this_turn`) and `reply_is_the_done_summary` skips the auto-post only when the reply IS the summary verbatim — the one real duplicate. That reset is the ONLY one, so the turn-start hook has to be installed **in every config that can auto-post** — ALL FOUR backend hook sets in `projects/spawn.rs` (`kiro_hooks`/`claude_hooks`/`codex_hooks`/`grok_hooks`; claude and codex shipped without it until 2026-08-22 and their agents lost the auto-post after their first `tmm send` — `refresh_hooks` backfills on every start) as well as the global `kiro_default.json`. Ship `stop` without `userPromptSubmit` and the flag is sticky: the prompt tells the agent to report progress with `tmm send`, and the first such call kills the auto-post for every later turn of that window.

**(2) Record-only** — every hook-sourced post is passed to `hub_post` with `record_only = true`, which prevents `deliver_mentions` from running; if an auto-post body contains an @-address and delivery were allowed, that would type into the peer's pane, trigger the peer's stop hook, which would auto-post back — a ping-pong loop. Skipping the sender's own window does not prevent this: the peer's window is what triggers the loop, so the fix must be at the call site.

**(3) Managed-only gate** — `maybe_auto_post` checks that `<project_path>/.tmm/agents/<window_name>/` exists before posting; the global `kiro_default.json` (used by direct and adopted windows) also carries the stop hook, so without this gate any kiro the user starts by hand would start posting into project rooms.

**(4) Reply budget** — `MAX_REPLY_CHARS = 6144` is the chat-path ceiling (the old 240-char `MAX_SUMMARY_CHARS` retired with the unread-notification UI, 2026-09-01 — the room is the one notification surface). Wiring: `RoomPoster` trait in `agent_notifications.rs`, implemented by `TeamRoomPoster` in `server/mod.rs`, injected once at server startup via `notifications.set_room_poster(...)`. `None` on mobile (degrades silently — no auto-post).

### Historical done feedback edge (superseded 2026-09-08)

`tmm spawn` records `spawned_by` in the launch recipe, `build_prompt` NAMES the briefer ("briefed by your teammate lead" — the anonymous "your teammate" left the agent with nobody to report back to), and `hub_done` delivers a non-empty summary into the live managed spawner's pane (`[tmm chat <ts>] <name>: [done] <summary>`, same `record_delivery` bookkeeping as an @mention). **At most `MAX_INCIDENTS = 3` incidents start a ladder per agent in any rolling `INCIDENT_WINDOW_SECS = 30 min`** (board #362 e, orchestrator's ruling after the #361 deploy, 10-14 02:3x: two agents showed `1/4` again within 20 s because the resumed turn hit a fresh high-traffic error with a new Request ID, and by the 08-26 rule a different error is a new incident with a full ladder — under a sustained overload, one `continue` per ~20 s per agent forever). The ladder still bounds ONE error (`MAX_ATTEMPTS` sends); the cap bounds how many NEW incidents start a ladder, 3 per agent per rolling 30 minutes, each with its own ladder of at most 4 sends. It is not a hard send-rate ceiling (reviewer P2-1 on 863c4f58): an older incident's ladder can still finish inside a later window, so a 30-minute span can hold a few more sends than 3 × 4. Incidents are counted, not sends: counting every send would quietly retire the ladder's last step. The window lives in the gateway's memory and starts empty after a restart. The next fresh incident in the window is not continued (`Decision::Capped`), and that incident stays a person's for as long as it shows, even after older ladders age out; a fresh one later, once the window has room, is continued. The feed gets ONE `warn` row per capped stretch, `auto-continue paused — 3 errors in 30 min were already continued; <agent> needs a person`, not one per fresh incident (validator P3 on 863c4f58: a fresh error every ~20 s flooded the feed): the stretch ends when a ladder can start again (the window freed) or the agent answers again (a tool call, or a turn end with a real reply, `recovery::note_answered`; a placeholder or an end with no usable text is no answer), and only a cap after that is said again (`Tracker::capped_said`). A capped or given-up incident also records the turn end the hooks missed, once, with the detail `recovery_exhausted` (next rule). The count (`Tracker::starts`) outlives the incident records, which go when their error leaves the screen, and goes with the window.
