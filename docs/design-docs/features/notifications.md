# Message Notifications — design

The implementation lives in `src/lib/hub/notifications.ts`; `Hub.svelte` has two call sites — the `team_message` push handler (primary) and the `hub_log` poll (fallback).

## Where the check runs (board #72)

The first cut checked only after a `hub_log` poll batch. That poll runs inside an effect gated on the Hub page being visible, so the "another page is on screen" half of the away verdict could never fire — a phone user who switched to Terminal got nothing, which is the case the feature exists for. The `team_message` push arrives for every project room whatever page is showing (the listener effect is not gated), so `onPush` is now the primary site:

- a message in the SELECTED room asks the live document (`isAway(visible)`: hidden, unfocused, or the Hub not on screen);
- a message in any OTHER room is away by definition — the reader is not looking at that conversation — and the title names that project (`roomProjectName` over the sidebar rows, recorded `room` first, then `proj:<session>`);
- a push is never "first": it is by construction newer than any loaded page.

The poll keeps its call as the fallback. Both carry the server message id, so `sift` makes push-then-poll alert exactly once. What is still not covered: a suspended mobile webview (app backgrounded) receives no pushes; the missed messages arrive on the next poll, which runs only when the Hub is visible again, i.e. while looking — no alert. Remote push for a closed or backgrounded app is a separate task (native `tauri-plugin-notification` on Android).

## Remember first, then decide

`hub_log(since_ts)` is inclusive, cache-restored rooms re-pull around their cursor, and equal-timestamp messages can return together. Therefore a raw poll batch is not proof of novelty. `sift()` records every message key before applying any alert policy:

1. use the server message id when present;
2. otherwise use the same `(from, ts, body)` identity as feed merging;
3. bound insertion-ordered memory to `SEEN_CAP`;
4. pass only never-seen rows to the news gate.

Recording happens even for initial, watched, or muted batches. This is what prevents later backfill.

## Effects are downstream of pure gates

`notifiable()` filters first-load/watched batches and everything that is not a bell message (`bellKind`, below), then picks by LEVEL. The level is three nested rungs over the bell, stored values unchanged since #72 so nobody's setting moved: `done` (**Finished**, the default since #333 — owner: "默认的 notification 可以是 finish 而不是所有的 reply") — a board move to review/done or a `[tmm done]` note; `replies` (**To me**) — plus every reply addressed to you; `all` (**To me + progress**) — plus status notes addressed to you. Before #334 `replies` rang every agent reply, which is why the owner heard agents talking to each other. `notifyLevel` names all three stored values, so the new default applies only where nothing (or something unknown) is stored; a persisted `replies` keeps ringing as To me.

The cue claims its cooldown before calling `Audio.play()` to prevent same-tick double playback. Rejection rolls the claim back only while that attempt still owns it (`lastCueAt === attemptTime`); an old deferred rejection cannot overwrite a newer successful claim.

## User gesture and platform boundary

The Settings toggle (its own **Notifications** category right after Appearance — owner, 2026-09-02: "应该在一个单独的 notification 二级页面"; On/Off in the segmented dialect) is the only permission and audio-unlock gesture; it persists `tmux_notify`. The category also carries a **Test** row: cue plus one notification on demand, because the real alert fires only while the reader is not looking, so a phone has no other way to confirm the tray shows one. It stood in the Hub header as a bell until board #72: a header keeps no spare switches, and on a phone the extra button was part of what let a long project name push the toggles off-screen (owner, 2026-09-02). Its caption reads the platform back through `notifyPermission()`: `denied` says the site is blocked and only the sound plays; `unsupported` (no `Notification` API — the Tauri Android webview) says the sound is the whole channel. Sending, interrupting, polling, and initial loading never prompt.

### Native tray on Android and the desktop app

The Android and macOS webviews have no Web Notification API of their own. `tauri-plugin-notification` (Cargo `gui` feature, `notification:default` capability, registered in `lib.rs`) injects a `window.Notification` shim into the webview: the constructor becomes `plugin:notification|notify` (the OS tray — the plugin creates Android's default channel itself and its manifest declares `POST_NOTIFICATIONS`), and `requestPermission` becomes the runtime prompt on Android 13+. So the one web path below is the native path inside Tauri; the JS side imports nothing from the plugin (its npm `sendNotification` is literally `new window.Notification`). Two shim facts the code respects: `Notification.permission` reads `denied`, not `default`, before the first ask — so `ensurePermission` asks whenever it is not `granted`, which a browser also tolerates (a re-ask on a denied site returns without prompting) — and the shim settles asynchronously at startup, so a caption read at mount may lag a tick.

What the phone says is what the owner asked for ("什么 project 谁完成了什么任务"): title `<agent> · <project>`, body the excerpt — an agent's reply, its `[tmm done]` summary, or a finished task. `taskFinished()` admits an agent's `[tmm] board #N … → review|done` line through the news gate (a move to doing, a spawn, or the human's own move stay narration) and `excerpt` renders it `#N → review · title`.

`systemNotify` prefers `ServiceWorkerRegistration.showNotification` and falls back to `new Notification`. The order matters on a phone: Android Chrome refuses the page-level constructor (`TypeError: Illegal constructor`), so the PWA showed nothing and the fail-soft catch hid it; `main.ts` already registers `/sw.js` on every non-Tauri secure origin, and the worker path works there. The tag is `tmm:<project>`, so a burst from one room replaces its tray card instead of stacking. The environment (`permission`, `construct`, `registration`) is injectable, and the tests pin all three branches.

Web Notification support varies by browser/webview and normally requires a running page. The design deliberately falls back to the cue and does not present this as service-worker remote push. The placeholder WAV is isolated from policy: the owner can replace the file without touching code.

## The notification centre (board #322)

Owner, 2026-10-09: "我经常听到「嘟嘟」的通知了，但是都不知道是哪个窗口的提示…在整个界面设置一个通知中心，让我能看到到底提示了什么…方便我快速定位到回复我的那条具体消息". The sound and the tray card were the only trace of an alert; nothing in the app said which room rang or let you reach the message.

**One rule for what is news.** `newsKind` (hub.ts) and its Rust twin `rooms::news_kind` share one case table (the Rust test's rows, read by `notifications.test.ts`): own words and app narration are `none`; a board move to review/done and a `done` status note (`[tmm done]`, `[tmm status done]`) are `finished`; other status notes are `status`; anything else an agent says is a `reply`. The roster dot and the sidebar's per-room unread (`hub_unread`, hub-feed.md) read it: they are about reading the room.

**The bell is narrower** (board #334, owner 2026-10-09: "不是每一条 reply 都会在小铃铛里产生一条通知 而是当他最后 @我 或者以 finish 的状态结束时"). `bellKind(m)` is `finished` for a finished task whoever it is addressed to, the `newsKind` of a reply or status note whose `to` includes `human`, and `none` for everything else — agent↔agent replies and unaddressed notes stay room unread and never reach the bell. ONE eligibility for both halves: the centre records exactly the `bellKind` messages, and only those can ring; level, mute and away then decide whether a recorded one sounds (`levelKinds`: `done` = finished, `replies` + reply, `all` + status). A muted or low-level client still records. It is per MESSAGE: a turn that moves an issue to review and then answers you leaves two entries, because a HubMsg carries no turn identity; collapsing a turn into one entry needs that identity first and is not claimed here.

**Record, then ring.** `notifyNews` keeps its order and gains a middle step: (1) `sift` remembers the whole batch, keyed `server|room|#id` so the same id on two servers is two messages; first pages, history and cache restores are remembered and never recorded; (2) every never-seen bell message (`bellKind` not `none`) is RECORDED in the centre, whatever the level, mute or away — so every cue has a row, and a blocked autoplay or a denied permission loses nothing; (3) only then do enabled / level / away decide the cue and the tray. A message that lands while the reader is at that room's visible tail (not away, following, not in a history window) is recorded already viewed. Push and poll share this one entry; `newsCtx` in Hub builds the context for both.

**The centre is an index, not a second history** (`hub/notify-centre.svelte.ts`). Entries `{server, room, session, seq, id, ts, from, toHuman, kind, excerpt, viewed, failed?}`, newest first, one per message, capped at 50 (eviction drops entries only). Clearing removes entries only and says nothing about any room; viewing one entry never moves a room's read mark. An entry is viewed when its jump landed, or when its room is read past its seq (`markSeen` → `centre.markRoomRead`), so a read room never leaves unviewed alerts behind. The list is `tmux_hub_alerts`, one of servers.ts `RESIDENT_KEYS` (in each server's own slot); on load it keeps only bell entries (`bellEntry`: finished, or to you), so a list written before #334 loses its agent↔agent rows without moving any read mark; Since #335 ②b-2-1 the list belongs to a runtime: each server's `ServerState` holds a `createCentre(createAlertLog(storage))`, so a switch builds the target's from its surfaced key, and only the WINDOW's surface — the one bell, popover and jump request, `centreSurface` — is reset (`centreSurface.reset()`), which drops a pending jump (websocket-client.md § One server's state is one value). The shell's bell and popover show the bound server's centre, handed in as a prop. It knows only what this running client received (the running-client limit below; its footer says so).

**The bell is the included servers' UNION** (board #335 ③c-4; `app/centre-union.svelte.ts`). Each server keeps its own bounded list — the union adds no second history — and the window's one bell shows the included members' lists merged, newest first by each entry's own `ts` then `seq` (ties by saved order), every row tagged with its server by the ③c-1 rule (more than one server included; Single includes one, so the union is that server's list, untagged, as before). Every action goes BACK to the source: a row's jump focuses that server (D2, `pickAlert` → `focusMember`, as a union project row does; a server that is not a connected member is not a focus change and the row's state says why) and then lands in THAT tree's Hub — the jump request is the window's one, and a Hub refuses an alert of another server, so only the alert's server's Hub acts on it; `viewed`/`failed` mark the entry in the list it came from; `markRoomRead` is each Hub's own, so `hub_read` reaches only the room's server and another server's same-named room is untouched. D6 (orchestrator 07:55, final text 02:28: INCLUDED members only — an excluded server is not in this view): the shown range, the count and Clear use ONE scope, the included members' lists; a member that is not connected right now — by its DERIVED status (`aggregate.status(id).kind === 'connected'`, the focus by the shell's `connected`), never a socket poll — is still listed, its rows muted (`.nc-row.unavailable`) and its name in the foot ("not reachable: its alerts stay as they are"), but its entries are not counted and Clear does not touch them: unavailable is not read, and a list that cannot be reached is not cleared behind its owner's back. Clear is offered only when a reachable list has entries. The OS notification's `tag` is the room ON ITS SERVER (`tmm:<server>|<room>`, `notifyText`), so two servers' `app` are two tray cards, not one replaced by the other; in Aggregate with several servers included the title names the server (`NewsCtx.serverName`, the Hub's `scope.tag`). Level, mute and the sound cooldown stay the person's settings, unchanged.

**Doors.** Desktop: a bell in the rail's bottom group above the server switcher (a control, never draggable), badge = unviewed count in `--accent-ink`. Phone: the Hub tab wears the static `.unread-dot` (visible from every page), and the Hub header has the bell, so the list is two taps from anywhere; no bell is copied onto other pages and the notify switch stays in Settings. Both open ONE popover in the server picker's dialect (`menu-surface menu-list pop-layer`, `menuPlacement`, outside-pointer / Escape / resize dismissal, focus back to the opener), hosted by App. Default view All, so a heard cue is always a visible row; a reply addressed to you (`to` includes human, #289) is bold with a "to you" tag, and To me narrows to those. A row is three FIXED lines (board #356, owner 2026-10-13, phone screenshot): identity — unviewed dot · project · time; meta — server tag · sender (agent ink) · "to you"; the one-line excerpt; then a failure reason when the last jump did not land. The project is the only shrinkable item of its line (it is never the loser), the time is tiered by `listWhen` (today `HH:MM`, this year `MM-DD HH:MM`, older `YYYY-MM-DD` — never the full date and the time together) so its column is one stable width, and "to you" never wraps. One structure on both screens; no breakpoint changes it.

**The jump.** Tapping a row closes the popover, switches to the Hub, and `centre.requestJump(entry)` hands Hub `{entry, n}`. Hub's `openAt`: a record of another server fails with a reason; `jumpIntent = n` is set BEFORE `selectProject`, which then skips its tail scroll, and `markSeen` refuses while a jump or window is active. If the message is not in the loaded feed, ONE `hub_log {around_seq}` page (half before, half from the message, room-scoped because seq is global) replaces the feed; with `newer_more` it is a HISTORY WINDOW. A room filter that would hide the target is cleared visibly ("Filter cleared…" + Restore, and Back restores it); the feed level is a stored preference and is never changed — the target's id is passed to `feedBlocks` as `reveal`, which keeps that one lifecycle line at chat-only. Every bubble and every sys row carries `data-msg=<id>`; `Feed.showMsg(id)` scrolls it to 8 px from the top and rings it once (`.jump-hit`, an accent box-shadow on the shared tempo). Only a mounted, positioned target marks the entry viewed; a superseded request (a newer jump, a room change, a server switch) changes neither view nor viewed; a gone message or a failed load keeps the entry unviewed with its reason and leaves the feed where it was.

**One reading generation owns the visible feed** (board #322 delivery review). Every write into the feed, its cursors or its anchor — the tail poll, the gap walk, an older page, the around_seq landing, the Back-to-latest completion — captures `readGen` when its request starts and is dropped if it moved by the time the answer lands. A jump, a return and a room switch each mint a new generation (a server switch remounts the page). A dropped poll batch still went through `notifyNews` first, so the centre, the cue and unread lose nothing; only the visible history is isolated. The centre's jump is ONE-SHOT and owns its whole life: `openAt` claims `n` before its first await, every exit — the other-server and no-project refusals included — consumes that same `n` in `finally` (never a newer request), and after each await the claim is re-checked BEFORE a new generation is minted, so a stale continuation (a slow room switch) can never void a newer jump's or a manual switch's reading. A room the READER picks (any `selectProject` call that is not the jump's own, which passes its `n`) consumes a pending jump at once, so it stops holding back that room's `markSeen` immediately; and the claim compares the selection generation the jump's own switch produced, never the room's name, so B → C → B by hand cannot be re-claimed, so returning to the Hub never replays it; leaving the Hub page, or the reader switching rooms by hand, invalidates a pending jump, and `current()` also requires the page to be visible, so a hidden feed is never jumped and nothing is marked viewed there. Pinned by eight mounts (the four below, plus a manual B → C → B during a pending jump, a slow room switch under a stale jump vs. a newer jump, preflight refusals not replayed, and a first-page poll in flight when a jump lands at the tail, which only the generation catches): a poll and an older page in flight when a jump lands (dropped; seen and the window's cursor unchanged; the row still in the centre), a slow return superseded by a same-room jump, a completed jump not replayed after leaving and returning, and a pending jump left behind (not viewed, spent, no forced jump on return); negative controls (no generation on the poll, on the older page, on the return's completion; no consume; no visibility check) each fail one.

**The read mark is the server's** (board #334, owner 2026-10-09: "我一打开，就看到每个会话有几百甚至上千条未读消息…这个已读状态是不是可以由 server 端去统计，保证我不同客户端看到的一致性"). Before #334 the mark lived only in each client's `tmux_hub_seen`, so a fresh browser or the phone counted the whole room. Now state.db holds ONE mark per room (`hub_read` table; one human reader per server) and `hubPrefs.seen` is this client's cache of it:

- **Reading.** `markSeen` updates the cache at once (the cue goes), records the mark as PENDING and sends `hub_read`. The answer is the persisted mark — the ACK. A pending mark clears only when the answer contains THAT room at or above it; an absent room (a failed call, an empty or partial answer) and a lower ACK leave it pending, and every later `refreshUnread` (the 20 s sidebar read, a push, a reconnect) re-sends it. Pending lives in the Hub's memory for its lifetime: a mark still pending at close is re-derived from the server on the next mount (at worst one just-read message shows unread until the next read) — no client push-up.
- **Ordering** (#334 delivery review). Every ACK of a room bumps its confirm generation, and a `hub_unread` answer ASKED before that bump never adopts its marks: it read the persisted mark before the write, and equal cache values do not prove it is newer. Answers also apply in ask order per room, so an older answer landing after a newer one changes neither count nor cache. The legitimate downward correction of an impossible cache still happens: that path has no pending and no newer ACK.
- **Adopting.** `hub_unread` answers `marks`, the server's PERSISTED mark per room (never the effective watermark). A legacy ts-only client mark is resolved to the room's seq on the server before it is compared with the server mark. With nothing pending, the cache becomes it (absent = the server has none), so a client follows another client's reading and an impossible cache (a seq past the room's head, left by a wiped database) is corrected. The server also drops such a mark at its door, so it hides nothing even before the correction. Consistency is on the next read: an idle client agrees on its next 20 s refresh; no instant push is wired.
- **Bootstrap.** Schema v31 seeded every room that already had messages read to its head: upgrading counts as "read up to now", since the old per-client mark was the only read state and the owner had read those rooms. No client pushes its old marks up (one mechanism, no migration state on clients). A room born after the upgrade starts unmarked and every message in it counts. The cost, accepted on #334: whatever was genuinely unread at the moment of the upgrade is marked read once; the bell is untouched by it.
- **Who marks.** Only the human's clients call `hub_read`. `tmm log` never marks read: an agent reading the room is not the human reading it.
- **Servers.** `tmux_hub_seen` stays in `RESIDENT_KEYS`: it is still a per-server cache keyed by session name, in each server's own slot. An answer that lands after a switch (the page remounted, or the current server id moved) writes nothing.
- **What the centre is not.** Clearing or viewing centre entries is centre state and never calls `hub_read`; reading a room past an entry still marks that entry viewed (`markRoomRead`).

Pinned by `hub_rpc.rs` (one monotonic, resolved mark; the server mark as the default watermark; a future seq/ts dropped at the door; persisted `marks`), the v31 migration test (old history read, a later message counts, a later room unmarked) and `Hub.mount.test.ts` (a fresh client inherits; the next client agrees; an idle client converges on its refresh; a failed `hub_read` re-sent until ACKed and not after; an empty and a partial ACK keep the unconfirmed room pending while the ACKed one is not re-sent; a lower ACK keeps a pending mark; an unread answer asked before an ACK cannot roll the cache, sidebar or roster back; an older unread answer landing late is dropped; an impossible cache corrected; a late ACK after a switch writes nothing), each with a negative control.

**Not wired this round:** clicking an OS / web tray notification does not open the message. The tray card still only names the project and sender; the in-app centre is the way to the message. Wiring `Notification.onclick` (and the Tauri shim's equivalent) to `centre.requestJump` is a listed gap, not a second channel.

**The window's rules.** While windowed: no live row merges (push and poll; a push sets the to-tail dot and still goes through record/ring), seen does not move, activity newer than the window's last message is not rendered, the room is never parked in `roomCache`, `loadOlder` walks back from `oldest_seq` as usual, and the to-tail control reads "Back to latest". That control mints a return intent and KEEPS the window until the tail page answers for the same room and intent; then messages, cursors and the activity bound are replaced in one step and the window ends. A failed tail keeps the window and the control for a retry; a superseded return is dropped. `Hub.mount.test.ts` pins the landing, the windowed push, the slow tail with a push in between, the failed return, supersession, another server, a gone message, and a finished-task line at chat-only; negative controls (dropping the windowed push guard, ending the window before the tail answers, ignoring supersession) each fail them.

## Rules and their reasons

### The bell is a union over per-server lists; every action goes back to its source (#335 ③c-4)

- **One list per server, one bell per window.** The union (`centre-union`) merges the included members' bounded lists at read time; it stores nothing. A row carries its server's tag by the ③c-1 rule.
- **A jump lands in the alert's server's Hub.** Picking another server's row focuses it first (D2); the Hub that reads the window's jump refuses an alert of another server. `hub_read` is the Hub's own and goes to the room's server only.
- **D6: shown, counted and cleared by ONE scope — the INCLUDED members** (orchestrator 02:28, the final text; it replaces the 07:55/08:17 wording that listed excluded servers too). An excluded server's centre is not listed and not cleared: exclusion means "not in this view". An included member that is not connected (derived status, not a socket poll) is listed unavailable: shown muted and named, not counted, not cleared. Clear is offered only when a reachable list has entries; it advances no room's read mark.
- **The projection separates index-exists, runtime-eligible and reachable** (reviewer P1-C3 on 018d4fa5). An included member with NO runtime — offline from boot, refusing its token — still has its own slot's alerts: App reads that slot once (`indexOnlyLog`, through the one server store) until a runtime for the id exists and its state owns the slot; it is shown unavailable, never cleared by the union (no second history). The owner of an id among the runtimes the window holds is the FOCUS, else a published member over an orphan (`activeOwners`, pure): a retained editor's old handle never shadows the fresh runtime for the same id. The bell is the WINDOW's: it is reachable when the focus has a Hub, or any member has one, or any index has entries — a focus without a Hub does not take the entry away, on either input: the desktop rail bell and, on a phone whose focus has no Hub (so no Hub header and no Chat tab), a bell in the Chat tab's slot of the tab bar (`.tab-bell`, the same `centreShown`); picking another server's row from it focuses that server (D2). An offline included member's entries are listed and not counted (the orchestrator's 02:28 "counted in the badge" was withdrawn 03:58: a count the person cannot act on is noise).
- **The tray tag names the room on its server**; the title names the server when the tag rule shows sources. A same-named project on another server is another card.

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Local outcomes are not away-message alerts (#167, 2026-09-12)

Copy, download, Git and confirmation outcomes use the local feedback contract
in design-language.md. They do not call this module, request notification
permission, play a cue or create tray notifications. Natural mutation results
need no extra success notification. The local 1500ms completion scheduler and
attempt generations do not replace this module's message identity, away gate,
deduplication or cooldown. `hub/notifications.ts` is unchanged.

### New-message alerts remember BEFORE they notify

(board #57): `hub/notifications.ts` keys every observed message row by id (fallback `from/ts/body`) in a bounded seen set before the first/history/watched/muted/news gates, so inclusive polls and cache restores never replay or backfill alerts. Only an away running client alerts; own/sys/ambient-status rows drop, `[tmm done]` remains news.

**The check runs on the PUSH, not only the poll** (board #72): the `hub_log` poll effect stops with the page (`if (!visible) return`), so a poll-only notifier could never fire for "another page is on screen" — the phone user's whole case. `Hub.onPush` is the primary site: the `team_message` push arrives for EVERY room on every page; the selected room asks `isAway(visible)`, any other room is away by definition and the title names that project (`roomProjectName`); the poll stays as fallback and `sift` makes the pair alert once.

**The switch lives in Settings, in its OWN category, not the Hub header** (owner, 2026-09-02, twice: "放到设置里" then "应该在一个单独的 notification 二级页面"): Settings → Notifications (right after Appearance) holds the On/Off segmented switch — the only permission/audio-unlock gesture — plus a TEST row (cue + one notification on demand, because the real alert only fires while you are NOT looking, so a phone has no other way to check the tray); its caption reads `notifyPermission()` back (not permitted → sound only; no Notification API → sound only).

**Native on the phone and the desktop app**: `tauri-plugin-notification` (in the `gui` feature, `notification:default` capability, `.plugin(...)` in lib.rs) INJECTS a `window.Notification` shim into the webview that routes the constructor to the OS tray and `requestPermission` to Android's runtime prompt — so the one web path IS the native path inside Tauri, with no plugin import on the JS side (the npm package was added and removed the same hour: its `sendNotification` is literally `new window.Notification`). Two shim facts the code respects: its `permission` reads `denied` (not `default`) before the first ask, so `ensurePermission` asks whenever it is not `granted` (a browser answers a re-ask on a denied site without prompting, so this is safe everywhere), and it settles asynchronously at startup.

**The LEVEL is three nested rungs**: Settings → Notifications → `done` (default since #333; board review/done and `[tmm done]`) ⊂ `replies` (every final reply addressed to you, #334) ⊂ `all` (plus `send --status` progress notes).

**"谁完成了什么任务" is news**: `taskFinished()` — an agent's `[tmm] board #N … → review|done` line — passes the news gate alongside replies and `[tmm done]`, and `excerpt` renders it `#N → review · title`; a move to doing, a spawn, or the human's own move stay narration.
