# Task Board — one board per project, kept by humans and agents alike

The `issues`/`issue_notes` board: fixed columns, per-project numbering, dispatch-by-assignment, the review handoff, and how it joins the agents' derived status without merging with it. Requirements for the page are in `../../requirements/pages/hub.md` (Board section) and the CLI verbs in `tmm-cli.md`.

## Rules and their reasons

### The Board's project list is the Hub's union, not a second one (#357, 2026-10-13)

Owner: "在 Terminal 页面和 Board 页面，都没有整合两种或几种不同连接里的所有项目."

Board now publishes its server's slice to a union of the SAME merge —
`createProjectsUnion<S extends ProjectsSlice>` (`app/hub-union.svelte.ts`;
rows in the server's order, its `talk` clock, `answered`/`failed`), with the
Board's slice adding its per-board `counts` (`BoardSlice`) and the Hub's its
unread/states/panes/icon (`HubSlice`). One merge, two instantiations: a
second comparator or poller would drift (tenet 9). Each row is measured and
labelled by ITS server (`r.slice`): the empty-board filter (`visibleBoards`,
board #39) uses that server's counts, the age uses that server's clock, the
tag wears the ③c-1 rule on the row's second line (#360). A foreign row is a
selector: App's `pickServerBoard` focuses that server (D2) and aims the
existing `boardIssueReq` landing at it with `id: 0` — "that board, nothing
opened" — so the cross-server pick is a landing like the Hub's, delivered only
to the tree it names (`landingFor`). The body, issues and notes stay one
server's (D3). D4: a hidden member's Board keeps only the 20 s list refresh
it publishes; the age tick and everything else wait for it to be shown. A
server with no answer is "no list yet", one that failed is "not connected"
with its last good rows (P1-C4). Single hands no union: the Board is as before.

After review (reviewer on 390ba4dd): the Board's slice is published only from
the last COMPLETE pair (projects AND counts — counts decide which boards
exist), a held landing waits for the target's own commit and the newest wins,
`id: 0` leaves an open detail through the existing guard, the head wears the
Hub's `.title-stack`/`.name-line` from app.css, and the width ghost is priced
by the rendered rows. See websocket-client.md § The Board and the phone's
Terminal list.

A card in todo, review or done never shows it, whatever the agent is busy with elsewhere. Nothing on the board lights it: activity on an issue is not work (tenet 8).

### Images go through the chat's pipeline (board #329, 2026-10-09)

Owner, 08:13: "我在 board 里面提新的 issue 时 发现好像没办法添加图片 希望能在内容里直接粘贴图片 类似于聊天窗口一样 把图片传上去 按同样的逻辑去做处理". The new-issue body, the detail's body editor and the note box each own a stager on the chat's ONE pipeline (`attachments.svelte.ts`, hub-composer.md § One attachment pipeline): paste, or the `+` (the composer's `hubAttach` button), uploads into this project's `.tmm/uploads/`, a `[img:n]` token marks the place, and `AttachStrip` shows the chip. Rules (reviewer, plan r1):
- **Staged images are draft state.** A stager that holds a chip or an upload makes its editor dirty, and the note box is a draft too (`noteDirty`): Back, Escape, a project pick, the feed jump and the session follow all go through the EXISTING discard confirm, no image-specific dialog. Stagers clear only on a confirmed discard, a successful save/create/note, a project switch (already guarded), the page's destruction (a server switch remounts it), or a change of the open issue (a confirmed delete is the one exit that skips the guard). `clear()` bumps the stager's generation, so a late upload, its catch and its finally never touch another issue, project or server — tested: an upload for A that lands after opening B writes nothing into B and does not hold B's note button closed.
- **A server switch asks the Board too** (#315): the page registers its confirm with `app/leave-guards.ts` (`guardPage` = `board` on the page, `hub` in the drawer). Dirty = any editor's text, chips, an upload in flight, the note box, or a request running; the walk waits for a running request, then asks the SAME discard confirm (cancel refuses the switch and keeps everything; confirm leaves). The page's destruction on the switch ends a pending question and stops every continuation (`alive`).
- **A request owns a frozen context** (review of 9e39696c): save, create and note freeze `{session, issue id, generation}` plus every field they will use at entry; each follow-on RPC, success, catch, clear and refetch first checks `owns(ctx)` (alive and the generation unchanged — it is bumped by a project switch, a change of the open issue and destruction), and an assignment brief is not typed from a dead page. While a request runs, EVERYTHING of its draft is locked (`submitting`): the title (input and create textarea) and bodies read-only, the status stops (buttons disabled, the pointer drag ignored), both assignee pickers disabled, chip ✕ and `+`/paste refused, and Back/Escape/pick/jump consumed — so no newer input can be cleared by an old answer. A pending DELETE keeps #167's rule (it never blocks a visit). The session follow waits too. With the lock no UI path changes the project or issue under a running request — tested: a pick during a slow note is refused even through the discard question, the answer lands on its own board, and only then does the pick go — so the generation half of `owns(ctx)` is defence in depth (only destruction, covered by `alive` and its own test, can happen mid-request). The file picker remembers the generation it OPENED in (opening or closing the create form is a new generation too), and each viewer tap takes its OWN claim — the generation and a tap sequence number, via ChatImage's `onviewstart` — so only the latest tap's answer, in its own issue, opens the viewer (A→B, A→B→A and two taps answered out of order), and the stager's last `focus` checks staleness like its writes.
- **What was saved is the draft's base.** On success the saved fields of the draft AND its base become the materialized values (refs, not `[img:n]`) before the three-way refetch — the token map is cleared, so a committed token read back as "the user's edit" would overwrite the stored image on the next save (reviewer, c83c5c0d).
- **A body Save is the body's.** With the note box holding a draft (text, chips or an upload) a successful ✓ stays on the detail, rebased on the saved body, the note untouched and still submittable; otherwise it returns to the board. The note text and its stager have ONE owner, the issue: they are cleared together by a confirmed discard, a successful note, or the issue changing.
- **One materialized text per submit.** Save, create and note refuse at the FUNCTION while an upload runs or a failed chip stands (the buttons agree), and freeze `stager.body(raw)` at entry: the same text is what `boardSave`/`boardNote` stores, never a `[img:n]`. An image-only body or note is content — also a chip whose token the person deleted (the stager's `sendable`; the ref is appended). A failed request keeps the chips and tokens for the retry (no second upload); a create that succeeded keeps the "the issue exists, never re-create" rule.
- **Rendering is the feed's.** A body or note with images shows its text and a `.shots` strip of `ChatImage` (signed `/dl` on intersection, re-signed once on error, the viewer signed at the tap; #175) — in an EDITABLE issue too, under the textarea, as the saved images (the chips are only this edit's additions). Tapping opens the shared `ui/Lightbox`; Back and Escape close the viewer before the detail, and a viewer URL arriving after the issue changed is dropped. Text WITHOUT an image is rendered byte-for-byte (the #11/#28 verbatim rule): `splitImages` is applied only when there is an image to split. A card never shows a path: refs leave the preview — a bare path inside a sentence, which the feed keeps as prose, is replaced by `[Image]` there — and an image-only body reads `[Image]` (`hubImage`).
- **CLI parity.** `tmm board add --image <path|url>` and `tmm board note <id> [text] --image …` (repeatable) append `![](ref)` lines exactly like `tmm send` (`with_images`, `absolutize_ref`); a note may be only an image.

`Board.images.mount.test.ts` drives the real Board with the real stager: paste → chip → saved ref; ✓ and Cmd+Enter refused while uploading, an image-only draft guarded; a failed chip blocks and its ✕ removes only itself; the token removed whole; an image-only note; A→B isolation; a failed save retried with one upload and the same text; delete drops the staged images; saved images render via ChatImage and the Lightbox peels first; verbatim text without images; the REAL leave walk asks (upload in flight, failed chip) and cancel keeps everything; editors locked and the frozen session/issue saved during a slow save; a body Save keeps the note draft; A's note text never reaches B; a save answered after destruction writes no assignee and types no brief; one of two tokens (image, file) removed alone.

### A column's label folds it, and the device remembers (board #391, 2026-10-16)

Owner: "在 board 的页面（尤其是在手机上查看时），不是分了 to do、doing 等几个分类嘛。现在可以给这些分类增加一个功能：我点击分类标签名，就可以把它折叠起来，这样方便我浏览". On a phone the four areas stack in one column, and a long DONE list takes height the person is not reading.

- **The label is the control, and the only one.** Each column's `.col-h` is a native `<button type="button">` (Enter and Space for free) carrying the app.css `.chev` caret (▸ folded, ▾ open, the atom's turn on `--t-move`), the status label and the count. `aria-expanded` says the state; the count stays visible while folded, so a folded DONE still reads "312". No toggle beside the label, no tooltip: the caret is the affordance.
- **Nothing is painted.** The label keeps its voice (meta size, 600, uppercase, `--text2`) and its hover turns the ink to `--text`, the Feed tool-lane head's idiom; no wash, so a press never fills a box around it (the #392 complaint). The hit box is `--control-height` (28 px pointer, 44 px touch) across the column.
- **A fold is a turned caret plus a cut** (motion.md principle 10): the folded column's scroller is not rendered, no height animation. In the 1-column base a folded area is `sparse` by the #33 rule, so it hugs its label and the open dense areas share the height (measured at the owner's 347 px phone, touch: DONE folded to its 44 px label, TODO and DOING grew from 192 to 266 px each). In the 2- and 4-column grids its cell keeps its place and shape (never 3 across) with the label alone: the cards are hidden, and the height is not given to another area, because a grid row is shared (a 390 px phone is already 2 columns: its board container is 366 px, past the 350 px step).
- **Per device, one set.** `appPrefs.boardFolded` (`hub-prefs.svelte.ts`, key `tmux_hub_board_folded`, a JSON list of statuses) is a person-and-window preference beside the sidebar collapse: every board on this device, in the page and in the Hub drawer, under any server, reads the same set, through the one reactive owner. It is not a per-server key (`HUB_SERVER_KEYS`). `readBoardFolded` validates at the door: a list of known statuses, each once, in board order, else nothing folded.

Pinned by `Board.mount.test.ts` (open by default; a click folds: `aria-expanded` false, the caret turns, the count stays, the cards cut, the area sparse, another column untouched, the key written; a reload with a stored set keeps both folds and an unfold brings the cards back), `Board.source.test.ts` (the button and its markup, one label per column, the cut, no wash, the token hit box, no local `.chev`) and `hub-prefs.test.ts` (the door, board order, the one key, a reload).

### Note-copy outcomes use the shared model and clipboard (#167 batch 2, 2026-09-12)

After the mechanical move, the same message-action model also accepts Feed
keys and records a failed attempt. Board calls `core/clipboard`, including its
insecure-context fallback, instead of writing through a private navigator API.
The raw note body is unchanged. A successful copy owns its 1500ms completion
expiry; failure is a persistent, retryable local error. Context transitions
cancel the scheduled expiry and invalidate an older clipboard completion.

The error uses the shared OperationFeedback and the local positioning action,
anchored to the live Copy button inside the notes scrollport. It cannot sit
over the note input or the triggering action as the fixed-corner prototype did.
Scroll/resize tracking is local and disposed; the existing outside/Escape
owner includes the error's Close control. No row, footer, global listener,
new clipboard writer or reading-layout change is introduced.

Each entry is a decision with the reason it was made; treat them as normative. They lived in the root `CLAUDE.md` until 2026-09-02 (board #73), when that file became an index and the rules moved next to the design they belong to.

### Delete failure remains in its confirmation (#167, 2026-09-12)

The old executor cleared `pendingDelete` after both success and failure;
Back could also dismiss it during the write. A failed mutation now remains
on its captured session/issue with an alert inside the same ConfirmDialog.
Pending Back is consumed without dismissing it or peeling the detail view,
and duplicate activation remains blocked by the synchronous busy guard.
Room generation and intent identity gate late completions. Only successful
deletion closes the matching detail; refresh errors use the existing board
read-error path and polling, never another destructive retry. Discard remains
neutral and explicitly offers Keep editing/Discard.

Real Board mount tests reproduce the old pending-Back failure and Cancel
wording, then verify retry, duplicate protection and successful-delete/
failed-refresh separation. The latter was already correct and is retained
as a regression guard, not claimed as a new repair.
Once mutation and refresh are separate phases, a second deletion can finish
before the first refresh returns. Review reproduced that old reply restoring
the second deleted card. `load()` now gates publication by its request ID as
well as the room, and successful deletion immediately removes its known row
and updates counts before refreshing. The ordered-promise regression returns
the newer empty list before the older populated list and requires it to stay
empty; no mutation is replayed and no refresh queue is added.

### An assignment is handed over by the server, once (board #377, 2026-10-15)

Found in the #367 review: the page inlined the whole issue and its note thread in a post of its own (`dispatchAssign`, boards #11, #42, #51), while `tmm board assign` posted a pointer. Two wordings and two code paths for one event, and a third gap besides: `tmm board add --assignee` only wrote a label, because only the page woke the agent.

`hub_board_save` now does it, in the handler that saves the assignee. A save that carries `dispatch: true` and NAMES an assignee other than the empty string, `human` and the actor posts ONE line through `post_and_deliver`, the carrier `hub_post` also uses. The page, `tmm board assign` and `tmm board add --assignee` all just save and ask; they differ only in `who` (`human` when the request has none), so the room line and the delivery are the same whichever of them asked. An assignee CHANGE also leaves the `[tmm] assigned <name> — board #N <title>` record (`unassigned <who lost it>` for a clear) beside it.

**The brief is the owner's, in one place.** Owner, 2026-08-29: "Assign 给某个 Agent 去做" means the agent starts with the COMPLETE original issue plus bounded discussion context, not that a label changed. So `board_assign_brief` writes, in plain English (it is input to an agent, not an i18n atom): who assigned it FIRST, then the ENTIRE title and body (never an excerpt: the paste path has no 400-character ceiling), then the note thread in order under a 1200-character budget (`board_assign_notes`, the old `assignNotes` moved server-side with its tests; a cut points to `tmm board show <id>`), and the take instruction LAST (boards #42, #51, #79). It is built from the STORED issue after the save. An earlier cut of #377 shrank it to a pointer for the CLI's reader; the orchestrator ruled that the content is the owner's rule and only the WORDING needed one home. Everything quoted — title, body, notes, authors, `who` — passes through `address::unaddressed` (#367 P1-A), so the only address in the line is the assignee: a title like "修复 @all 的投递" reaches one pane.

Rules and their reasons:

- **Naming the assignee hands the issue over; the assignee does not have to change.** Saving `builder-2` onto an issue `builder-2` already has sends the hand-off again and adds no second record. That is how a person re-sends it to an agent that was offline the first time, and it is the recovery `tmm board assign` documents (#367). The page sends the field only when the picker changed it, so a plain edit never re-sends.
- **`take` tells nobody.** It is a claim: the assignee is the actor, and your own edit is not news. A clear has nobody to tell; `human` reads the board.
- **The issue is named as the save leaves it.** A request that edits the title and assigns in one go announces the new title, in the record and in the brief: both read the stored issue after the write. The record used to read the row from before it.
- **The recipient is validated at the save door, once** (review P1-C). `assignee` is `""`, `human`, or ONE name `agents::valid_name` accepts. `all` (the broadcast), `dev @all`, `@x`, whitespace are `-32602` with nothing saved and nothing posted, through create and patch alike, flag or no flag. The dispatch target is that validated name and is never re-read from text. Only a managed agent DECLARED by this project is posted to; any other valid name is saved and answered `offline`.
- **The save is committed before the telling, so everything after the commit is part of the answer** (review P1-A, and its residual). `hub_board_save` answers `dispatch: "sent" | "offline" | "failed"` (absent when there was nobody to tell) with `dispatch_error` and hub_post's `offline` rows. A failed post is NOT an RPC error, and neither is the read-back that builds the brief: the id always comes back (`HandOff.read` is the seam the test breaks). The page used to keep a create form open on any error, so retrying a save that had landed filed the issue twice. The page closes the create form (or rebases the edit draft) on any saved answer and shows `failed` AND `offline` as a line of its own ("Saved, but alice was not reached (stopped)"), with a **Reassign** button beside it that sends the same assignee again with no draft change (the flagged save `tmm board assign` makes). Reassign is an action of ONE issue in ONE project: it carries the project it was born in and a click goes there, never to whatever the page shows now; a project switch drops it together with the error line (in the effect that resets the rest of the page), a click that outlived its project is dropped, not redirected, and A → B → A does not revive it. It has its own line and lifecycle (validator, live: an ordinary roster refresh used to clear it ~5 s after the agent restarted, before anyone could click): a poll is not the delivery it is waiting for, and an unrelated error does not hide it. Four things end it — a click on Reassign (the new outcome replaces it), Close, a project switch, or a LATER SAVED CHANGE of that issue's assignee (to someone else, or cleared — the server rightly says nothing about a clear, and the old button must not be able to restore what was just removed). While its Board is not the focused one (Aggregate keeps one Board per server and only hides the others) the line is hidden and the action inert, and both return with the board: a hidden page never sends; opening another issue in the same project leaves it, because it names its issue; `tmm` prints the saved line and exits non-zero only for `failed`, and an `offline` agent is a note on stderr, for `add --assignee` as for `assign`. `sent` means the brief was POSTED and delivery found a live pane for the name; it is not proof that it was typed (a pane in copy mode or a held queue is reported separately, as for any message). The two steps (save, tell) moved from two client requests to two server steps; they did not become atomic, and nothing here claims they are.
- **Dispatch is opt-in per request, announced in the login answer, and gated ONCE on the write path** (review P1-B, and its residual). The page and `tmm` send `dispatch: true` only for a save that names an assignee. A request without the flag is what it was before #377 — the record, no hand-off — so an older page or `tmm` that posts its own brief against this server produces exactly one hand-off, not two. The login answer's `caps` carries `board_dispatch`, and the gate is in `ws-api.boardSave`, bound to the socket that will carry the call: `requireCap` is a SYNCHRONOUS check in the same block as the write, so no reconnect can slip between the answer it read and the socket it writes to, and the WAIT for an unanswered login is declared on the method (`boardSave.hold`) and run by the runtime's own gate (`server-runtime.gateApi`), which asks the handle's write right AGAIN in the same synchronous step that sends: a runtime detached or frozen while its write waited sends nothing, the caller gets the refusal and keeps its draft, and nothing is retried after the login (a held write is not owed a second chance by the connection coming up). The existing `live` / `frozen` predicate is the one asked; there is no second `RPC_KIND` list: **an unanswered login is a wait** (the save is held, the draft kept, and after 5 s it is refused as "still connecting"), never a yes; **a login that answered without the capability is a refusal** ("update this server to assign"), before anything is sent. Neither the page nor the CLI has a second check on its submit path; `tmm` reads the same list on the save's own connection, and exits with nothing written. The page only SHOWS the state: the connection announces changes (`onCaps`: the list when a login answers, `undefined` when the socket goes or is replaced), so the pickers and their note follow a reconnect from a modern server to an old one and back on the same mounted page. A plain edit asks for no hand-off and is not gated. No client keeps a second brief; the flag and the cap are the only compatibility surface.

Pinned by `hub_rpc.rs` tests (a body that ends its sentence gets no second full stop; a read-back that fails after the commit still answers saved with the id and one issue; one flagged save through the RPC is exactly one line to exactly the assignee, the same for the page's request and the CLI's; an unflagged save posts none; the brief carries the whole body and the notes in order, de-addressed; the budget cut and its pointer; a refused assignee leaves nothing saved or posted; a post that fails after the save is an answer, the issue exists once, and the same assignee again sends it without a second issue; an undeclared agent is never posted to; a rename-and-assign names the new title; filing with an assignee hands over at birth), `tests/board_assign_cli.rs` (one write, no post of its own, refusal before the write on a server without the cap, `failed` exits non-zero, `offline` is a note), `connection.test.ts` and `login-caps.test.ts` (a REAL connection and ws-api: a flagged save sends nothing before the login answers and goes once it has; one issued after a redial reads the NEW socket, not the old answer; disposing the connection releases a parked wait at once; a redial to a server without the capability refuses it unsent while a plain edit still goes; the observers follow the socket), `Board.source.test.ts` and `Board.images.mount.test.ts` (the real Board: a create with an assignee is one request, a failed or offline hand-off is a line after the form has closed with a Reassign that sends the flagged save again, an edit rebases and a second ✓ sends nothing, one mounted Board follows modern → old → modern, a held or refused save keeps the draft; Reassign from project A is gone on B while B's list is still loading, the CAPTURED Svelte handler invoked after the switch writes nothing, and A → B → A does not revive it; the line is hidden and its handler inert while the host's scope is not eligible, and returns with it; ### The project has ONE task board, and both species keep it

**Board and live state are TWO AXES, never merged**: the board is the ISSUE's lifecycle, while the WINDOW's turn is hook-derived. An agent can be running on something else while its issue sits in review. Every board status change posts a `[tmm] board #N a → b — title` room line, and since board #367 every assignee CHANGE posts `[tmm] assigned <name> — board #N <title>` (or `unassigned <who-lost-it>`) from whichever surface saved it — the picker, `tmm board assign`, `take` — because a reassignment used to be invisible to everyone but its new assignee, which is how #363–#366 came to be moved off a removed agent with nothing in the room to say so; the line is written in the lifecycle grammar `sysParts` already reads (verb, subject, detail), so it needs no new render branch, and the WAKE stays with the dispatchers (the UI's full brief, the CLI's pointer — tmm-cli.md § CLI/UI parity) rather than being doubled here; a move TO REVIEW is a HANDOFF delivered into the REPORTER's pane via `deliver_chat_line`.
