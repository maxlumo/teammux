# WebSocket JSON-RPC API Contract

## Transport
JSON-RPC over WebSocket (`ws://` or `wss://`).

## Authentication

### Encrypted Auth (default, when Web Crypto available)
```
← {"server_nonce": "<hex>", "e2e": 2}                // nonce + newest handshake version
→ {"method": "auth", "params": {"client_nonce": "<hex>", "proof": "<hex>", "e2e": 2}}
← <binary AES-GCM frame: {"result": {"authenticated": true, "machine_id", "hostname", "e2e": 2, "build": {…}, "caps": ["board_dispatch", "board_notify", "spawn_join", "agent_team", "hub_files", "mcp_masked", "backends_check", "board_blocks", "board_agreement"]}}>
```
- The client accepts exactly one first frame: the nonce, `server_nonce` = 32 hex digits (16 bytes). The server sends nothing before it;
  a client ends the attempt on any other first frame or any other length, and delivers nothing (pushes, answers) until the login completes
  (phase table: [disconnect-grace.md](../../design-docs/features/disconnect-grace.md))
- IKM = token, salt = server_nonce ‖ client_nonce (16 + 16 bytes), HKDF-SHA256, 32-byte outputs
- **v2** (current) derives THREE keys, one per job, by `info` label:
  `tmux-mobile-e2e/v2/proof` (HMAC proof key), `tmux-mobile-e2e/v2/c2s`
  (client→server AES-256-GCM key), `tmux-mobile-e2e/v2/s2c` (server→client key)
- **v1** (legacy) derives ONE key with `info` = `tmux-mobile-e2e` and uses it as
  proof key and as the cipher key in both directions. Both directions counting
  from 0 under one key meant client message #n and server message #n shared a
  (key, nonce) pair — the AES-GCM nonce-reuse failure. Kept only so peers that
  predate v2 still connect.
- Negotiation: the server advertises `e2e` in the nonce frame; the client asks
  for a version in its auth params; the server derives with the version the
  CLIENT asked for (no field = v1) and echoes it in the authenticated result. An
  old client never sends `e2e` and gets v1; a new client against an old server
  sees no `e2e` in the nonce frame and uses v1.
- Proof: HMAC-SHA256(proof_key, server_nonce ‖ client_nonce) — both nonces, so a
  captured proof cannot be replayed into a later handshake
- All subsequent messages are binary AES-256-GCM frames; nonce = 4 zero bytes ‖ big-endian u64 counter
- Decrypted payload starts with a one-byte framing tag: raw UTF-8 JSON or raw-deflate JSON (compression is used only when it reduces payload size)
- Each direction uses its own monotonic counter; clients must serialize encrypted sends so wire order matches nonce order
- Server and client derivations are pinned to shared test vectors
  (`src-tauri/src/server/wire.rs` tests ↔ `src/lib/core/ws.test.ts`)

### Legacy Plain Auth (fallback, no Web Crypto)
```
← {"server_nonce": "<hex>"}
→ {"method": "auth", "params": {"token": "..."}}
← {"result": {"authenticated": true, "machine_id": "uuid", "hostname": "my-mac", "build": {…}, "caps": ["board_dispatch", "board_notify", "spawn_join", "agent_team", "hub_files", "mcp_masked", "backends_check", "board_blocks", "board_agreement"]}}
```
`build` (board #368) is the build the server runs, `{"version": "1.0.0", "commit": "46392f16", "built": "2026-10-14 07:40"}`:
the package version, the source commit (`git --short=8`: AT LEAST 8 hex characters, so two sides compare by prefix; `dev` when git was unavailable) and the UTC minute the build ran
(`unknown` when the clock was). It rides the login answer, not a new RPC, in both paths. A server older than #368 sends
none; a client reads that as "unknown", never as a mismatch.

`caps` (board #377) lists what the server can do that a client must know BEFORE it asks (a write, or a read an older server answers wrongly). Today nine: `board_dispatch` —
`hub_board_save` with `dispatch: true` hands the issue to its assignee; `board_notify` (board #507) — `hub_board_note` with `notify` records the note AND announces it in the room in the same call, in that order. An older server ignores the key, which would store the note and announce nothing, so `tmm board note --notify` checks the cap on the connection that would carry the flag and refuses before anything is written (the Hub sends no `notify` today; any client that does must check it the same way); `spawn_join` (board #382) — `hub_spawn` with `join`
puts the agent in that team, one present in this project (a member home here, live or stopped) (an older server ignores the key and spawns it standalone, so the page and `tmm spawn
--join` refuse a join unsent without it; a standalone spawn is not gated); `agent_team` (board #384) — `hub_agent_set_team`
exists (an older server answers method-not-found after the card was dropped, so the page disables the drag and the Move items and
`tmm agent team` exits with nothing changed); `hub_files` (board #432) — `hub_search` with `files: true` lists the files the messages mention. An older server REFUSES an empty `grep` (the default way into Files) as a bad request before it looks at `files`, and answers a worded one with messages, so neither reads as "cannot" from the answer alone: the Hub's Files mode and `tmm log --files` check the cap first and refuse an older server before sending anything ("cannot list files"), and still check the shape of the answer; `mcp_masked` (board #451) — `mcp_list`, `registry_list` and `teams_list` show every MCP `env`/`headers` value as `"<set>"`, and `mcp_save`, `registry_save` and `teams_save` keep the stored value for it. An older server answers those reads WITH the values and would store the marker as a literal, so the Hub (`ws-api`) and `tmm` send none of the six without it ("update the server"; `tmm` exits saying nothing was read or saved); `backends_check` (board #492) — the `backends_check` RPC exists, so the Agents page offers its Backends section only on a server that announces it. The cap says the server can RUN the check, not that any backend is installed or signed in; a gateway with phase 1 of #492 but without this cap hides the section until it is updated, and a method-not-found under the cap is shown as "this server needs an update", never as a missing backend. A server that lacks them sends no `caps` at all, and a; `board_blocks` (board #43) — `hub_board_save` accepts `blocked_by` on a create and `hub_board_block` exists. An older server ignores the key and files the issue with no edges, which reads as a success, so `tmm board add --blocked-by`, `tmm board block|unblock` and the Board page refuse before anything is written when it is absent.; `board_agreement` (board #44) — `hub_board_note` keeps `agreement: true` and `hub_board_get` derives the current agreement. An older server ignores the key and stores a plain note as if it had worked, so `tmm board note --agreement` and the Board page refuse before anything is written when it is absent.; `omp_tools` (board #72) — `registry_save` and `teams_save` keep a definition's `omp_tools` (omp's own plan/ask/goal/out switch). An older server ignores the key and saves the rest as if it had worked, so the Agents page offers the switch only under this cap, and the Hub and `tmm` refuse before sending any save that carries it, on or off. A draft read from an older server holds no value, so its other edits still save.
client that needs one refuses the write (the page's write path refuses it unsent and disables the picker, `tmm board assign` / `add --assignee` exit
with nothing saved); a login that has not answered yet is a wait, never a yes rather than store a label no agent is ever told about. Like `build`, it rides the login answer, in both paths.

### Rate Limiting
- Max auth failures tracked per IP
- Lockout after repeated failures (configurable timeout)

### Filesystem
| Method | Params | Response |
|--------|--------|----------|
| `fs_cwd` | `session` | `{path}` |
| `fs_list` | `path`, `show_hidden?` | `{entries, path}` |
| `fs_stat` | `path` | FileStat object |
| `fs_read` | `path` | `{content, revision}` (≤512KB). `revision` (board #434) is the sha256 hex of exactly the bytes `content` was decoded from: what a review comment anchors to |
| `fs_write` | `path`, `content` | OK |
| `fs_mkdir` | `path` | OK |
| `fs_delete` | `path` | OK |
| `fs_rename` | `from`, `to` | OK |
| `fs_download` | `path` | `{name, data}` base64 (≤50MB). For inline preview; user-initiated downloads use `fs_download_url` + HTTP `/dl` streaming instead. |
| `fs_download_url` | `path`, `stream?` | `{url, name}` where `url` = `/dl?path=…&exp=…&sig=…`. Client GETs it on the same host (http:// for ws://, https:// for wss://) to stream the file; `/dl` honours `Range: bytes=N-` and `bytes=N-M` (206/416). Every 200/206 carries a strong `ETag` (`"<size hex>-<mtime ns hex>"`) and `Last-Modified` (exposed to cross-origin callers); `If-Range` naming that ETag or that date keeps the Range, any other value makes `/dl` ignore Range and answer the whole current file as 200 (RFC 7233), which is how a resuming client learns the file changed (board #305). `OPTIONS` on `/dl` is the CORS preflight a Tauri page sends for `If-Range`: 204, `Allow-Methods: GET`, `Allow-Headers: Range, If-Range`, `Allow-Private-Network: true` (a Chromium webview's Private Network Access asks in the same preflight), no signature check, no file access. A 416 also carries CORS headers, so a cross-origin client can read its `Content-Range`. HMAC-SHA256 over `dl:<path>:<exp>` (download) or `dl:stream:<path>:<exp>` (stream; URL carries `&stream=1`); `exp` is an absolute expiry: 60 s after minting for a download, 4 h with `stream: true` (a `<video>` or `<audio>` re-requests the URL for the whole playback). `stream: true` is refused (invalid params, and 403 at `/dl`) unless the path is a video or audio extension the browser plays (mp4/m4v/webm/mov/mkv/ogv; mp3/m4a/aac/ogg/oga/opus/wav/flac/weba, board #416). `/dl` declares the real `Content-Type` for these (`video/*`, `audio/*`). The name rides `Content-Disposition: attachment; filename="<printable ASCII, others as _>"; filename*=UTF-8''<percent-encoded>` (board #433): never raw, so no control byte reaches the header. No server-side size limit. |
| `fs_preview_base` | `path` (an `.html`/`.htm` file) | `{base}` where `base` = `/dl/s/<exp>/<dev>.<ino>/<sig>/<b64url(root)>/<dir…>/` (board #433): the `<base href>` an HTML preview's relative `<link>`, `<img>`, CSS `url()` and media resolve against. The server derives the ROOT: the longest declared project path that contains the file, else the file's own directory, both canonical; `/` or the home directory is never a root (it falls back to the file's directory, and fails when that is too wide as well). A path whose last component is a symlink is refused. `<dev>.<ino>` pins the root directory; `<dir…>` is the file's directory below it, each segment percent-encoded once. The client prefixes the same http(s) origin as for `/dl`. A GET under it is verified BEFORE the filesystem is touched (HMAC-SHA256 under a key derived as `HMAC(token, "tmm-dl-scope-v1")` over `v1␀exp␀dev␀ino␀root`, so it never verifies as a download or stream signature; 4 h ceiling), each segment is decoded exactly once (empty, `.`, `..`, and `/`, `\` or NUL after decoding refuse), and the target opens from the root's directory handle with no symlink followed: 403 for a refused request, 404 for a missing segment. Only css, images, fonts and the `/dl` media types are served, with their real `Content-Type`, a fixed `Content-Disposition: attachment` (no filename: a resource name never enters a header), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer` and `Content-Security-Policy: sandbox; default-src 'none'; style-src 'unsafe-inline'`; html, js, json and everything else are 403. Range and the validators behave as on `/dl`. |
| `fs_upload_begin` | `path`, `size` (bytes) | `{id, url, chunk, received: 0}`, or `{…, done: true}` with `url: ""` for `size: 0` (the empty file is already committed). `path` goes through `fs::upload_target`, the one upload validator. It must be absolute (after `~`), have no NUL, name a file in an existing directory, and not be a directory; an existing path, or `..` in the parent, resolves canonically. Refused with a reason when another upload to the same destination is live, or when the directory's filesystem has fewer than `size` bytes free. An upload to the same destination that is writing no chunk and has gained nothing for 30 s is abandoned: begin takes it over, removing its part, and its id answers `no such upload`. `id` is 128 random bits in hex. `url` is `/up/{id}?exp=…&sig=…`, made absolute by the client against this connection's origin, as for `/dl`. `chunk` is the size to send per PUT (4 MiB). |
| `fs_upload_resume` | `id` | `{url, received, chunk}`: a freshly signed URL and the bytes the server holds (the part file's real length). For an upload that committed, its receipt: `{done: true, received: size, url: ""}`, for 10 minutes after the commit or until `fs_upload_abort`, so a client whose final `201` was lost learns the file landed. Errors: `no such upload: <id>` (committed, aborted or expired), and `upload busy` while a PUT is still writing (ask again). |
| `fs_upload_abort` | `id` | `{ok: true}`. The part file is removed and the id forgotten; for a committed id, only its receipt is forgotten and the file stays. An unknown id is not an error. |

**The upload door (board #23).** `PUT …/up/{id}?exp=E&sig=S` on the gateway port, plain or TLS. A proxy prefix is allowed; the door is the last `/up/` followed by a 32-hex id. Headers: `Upload-Offset: N` and `Content-Length` (at most 8 MiB; `Transfer-Encoding` is refused with 411). `sig` is hex HMAC-SHA256 under the key `HMAC(token, "tmm-upload-v1")` over `v1\0{id}\0{exp}\0{size}\0{destination}`, with size and destination taken from the server's entry, never from the request. `exp` must be in the future and at most 15 min away. Answers: `204` + `Upload-Offset` (accepted, more to come); `201` + `Upload-Offset` (the last byte: the part file was fsynced, its size checked and renamed onto the destination); `409` + `Upload-Offset` (not the next offset, another PUT for this id is running, or the part's name is no longer the file begin created); `413` (the body would pass the declared size, or is over 8 MiB); `403` (bad, expired or foreign signature, or unknown id); `400` (no `Upload-Offset`); `405` (another method). Every refusal after the signature verifies reads the request's body (up to 8 MiB) before answering, so the client sees the answer instead of a reset; a `403` closes at once. `OPTIONS` is the CORS preflight (`Allow-Methods: PUT`, `Allow-Headers: Upload-Offset, Content-Type`), with no check and no file access. Every answer carries `Access-Control-Allow-Origin: *` and exposes `Upload-Offset`. The local socket refuses the door (400).

### Agent hooks (agent lifecycle telemetry)
The `agent_notifications_list` / `agent_notifications_mark_read` unread-inbox
RPCs and the `agent_notification` push retired 2026-09-01 with the old
notification-dot UI: the project room's auto-post + read cursor and the derived
status dots are the one notification language. The `agent_hooks_status` /
`agent_hooks_install` / `agent_hooks_remove` management RPCs retired
2026-09-20 (board #222): managed agents carry their hooks in the isolated
home's rendered config, so there was nothing left for a client to manage. The
hooks themselves remain — they feed telemetry, status derivation and the
auto-post. All of the retired methods answer METHOD_NOT_FOUND.

## Error Format
```json
{"error": {"code": -1, "message": "description"}}
```

The `message` is the server's ONE sentence for the human and may be
translated or reworded; a client that needs to act on a particular failure
keys on the CODE, never on the text (board #337). An error may also carry
`data`, the facts needed to ACT on it rather than only show it — today only
`-32010` does; `-32011` deliberately does not, because the fact it would
carry has one source and copying it is how a snapshot goes stale twice.

| Code | Name | Meaning |
|---|---|---|
| `-32700` | parse error | the frame was not JSON we could read |
| `-32601` | method not found | unknown method, or one this build does not serve (a phone build answers this for every desktop-only method, which is how the client probes for the projects/hub features) |
| `-32602` | invalid params | a required parameter is missing or the wrong type |
| `-32603` | internal error | the operation failed; `message` carries the reason |
| `-32000` | auth required | the connection has not authenticated, or the token was refused. In reply to the login this is the server's explicit "no" (`invalid proof` on the encrypted path, `invalid token` on the plain one) and it is sent as a PLAIN text frame even when the session is encrypted (the server has no key for a proof it just rejected); the client keeps it as an error carrying this code and classifies the sentence once (`authKindOf`, `core/rpc-codes.ts`): only `invalid token` and `invalid proof` are a refusal its reconnect loop stops on (board #393); `auth required…` (a frame before the login) and `invalid client_nonce` are protocol answers it retries, and the client sends nothing but the login before the login (board #502) |
| `-32010` | scratch name held | `scratch_session` refused because a PROJECT holds the scratch terminal's reserved session name. The one refusal a client can act on, and the only one with `data`: `{projectId, projectName, session}` identifies the holder, so the confirmation names it and `scratch_release` can only touch that project. The panel keys on this code alone, so its copy and its action cannot drift apart (board #337) |
| `-32011` | scratch snapshot stale | `scratch_release` refused because the state the reader confirmed from has moved on — the project they approved is not the holder any more, it has been deleted, or the expectation the write itself carries no longer holds — and nothing was renamed. The panel RECOVERS rather than showing it: the snapshot is dropped and `scratch_session` is asked once, since that is the one path that says who holds the name now (free → it opens; still held → a fresh `-32010` names the current holder and offers the action again). No `data`, for that reason: a holder copied onto this error could be stale again by the time it was used (board #337) |
